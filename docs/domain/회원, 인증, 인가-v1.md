# 테크스펙 문서 작성

# 도메인 - 회원, 인증, 인가 (V1)

# 배경

- **프로젝트 목표:** 카카오 로그인 후 기본 취향을 저장하고 서비스를 이용할 수 있게 한다.
- **핵심 결과:** 회원 식별, 로그인 유지, 취향 변경, 로그아웃·탈퇴, 알림 조회·삭제를 처리한다.
- **문제 정의:** 로그인 여부만 확인해서는 타인 데이터 접근을 막을 수 없다. 회원 상태와 데이터 접근 권한을 함께 확인해야 한다.
- **가설:** 서버 세션으로 회원을 확인하고, 함께 바뀌어야 하는 데이터는 하나의 트랜잭션으로 처리하면 회원 상태를 일관되게 관리할 수 있다.

# 설계 및 기술 자료

## 공통 정책

- 카카오만 지원한다. 외부 provider 경로값은 소문자 `kakao`로 고정하고 내부 DB/Java Enum은 `KAKAO`를 유지한다.
- 로그인 전 검증 정보는 HttpSession, 로그인 후 서비스 세션은 auth_sessions에 저장한다.
- 신규 회원은 ONBOARDING으로 생성하고, 유효한 취향을 처음 저장하면 ACTIVE로 바꾼다.
- ONBOARDING도 내 정보·취향·설정·로그아웃·탈퇴 API를 사용할 수 있다.
- 사용자 ID는 요청 Body가 아니라 검증된 세션에서 가져온다.
- state·PKCE·CSRF·HTTPS 검증은 생략하지 않는다.

### 공통 요청과 응답 규약

- API prefix는 /api/v1이다.
- 기존 API ID와 경로를 유지한다.
- 성공은 {message, data}, 오류는 {message, data:null, error:{code, details, trace_id}} 형식이다.
- BIGINT ID는 양의 십진 문자열로 전달한다.
- 시각은 DB에 UTC DATETIME(6), API에는 ISO 8601 offset 형식으로 전달한다.
- 302와 204 응답에는 JSON Body를 넣지 않는다.
- 인증 오류는 401, 소유권 오류는 403, 미존재는 404, 내부 오류는 500이다.
- 변경 요청은 CSRF를 검증한다.
- 인증 실패와 CSRF 실패가 겹칠 때 응답 순서는 실제 필터 구성으로 확인한다.
- 각 API의 응답 필드는 기존 명세를 유지한다.
- language_code는 기존 기본값 ko를 유지한다.

### 인증·인가 공통 처리

~~~text
요청 쿠키 KGB_SESSION 확인
쿠키 원문을 SHA-256으로 해시
auth_sessions 조회
  없거나, 폐기됐거나, expires_at <= 현재 시각 또는 last_used_at(없으면 created_at)+30분 <= 현재 시각이면 401
members 조회
  없거나 deleted_at이 있으면 401
principal에 memberId, status, sessionRowId 설정
API 접근 권한과 대상 데이터의 회원 관계 확인
업무 처리
~~~

- 인증 DB 조회 장애는 세션 만료와 구분해 500으로 처리한다. 
- DB를 읽지 못했다고 인증을 통과시키지 않는다. 
- 상태 변경 시에는 트랜잭션 안에서 회원의 삭제 여부를 다시 확인한다.

## 데이터베이스 스키마(ERD)

### 주요 테이블과 임시 저장소

| 저장 대상 | 사용 내용 |
|---|---|
| members | KAKAO 식별자, 가입 시 프로필, status, push_enabled, deleted_at |
| auth_sessions | member_id, session_id_hash, expires_at, revoked_at, last_used_at |
| member_preferences | member_id, preference_type, preference_code |
| notifications | recipient_member_id, type, title/body, reference_type/id, created_at |
| 로그인 전 HttpSession | state별 provider, verifier 원문, 고정 redirect_uri, 생성·만료 시각 |

- 회원 식별은 UNIQUE(oauth_provider, oauth_subject)로 보호한다.
- 세션 ID는 원문 대신 SHA-256 해시를 BINARY(32)에 저장한다.
- 취향 선택은 UNIQUE(member_id, preference_type, preference_code)로 중복을 막는다.
- 취향 옵션은 Enum으로 관리한다. 
- DB에는 회원이 선택한 결과만 저장한다.
- language_code는 기존 기본값을 유지한다.
- nickname은 최대 50자, profile_image_url은 최대 2048자 또는 null이다.
- email은 nullable VARCHAR(254), 없으면 FE ‘이메일 정보 없음’. 닉네임 누락은 사용자, 초과는 첫 50 code point, 이미지 URL 부적합/초과는 null이다.

## 구현 구조와 계층 책임

### 패키지 구조

V1은 도메인 안에서 기술 계층을 나누는 구조로 구현한다. 구현 중 패키지나 클래스 이름을 바꾸면 이 문서의 호출 흐름도 함께 갱신한다.

~~~text
com.ktb10.kgb
├── common
│   ├── config
│   ├── error
│   ├── response
│   └── security
└── member
    ├── controller
    ├── service
    ├── repository
    ├── entity
    └── dto
        ├── request
        └── response
~~~

| 계층 | 책임 | 하지 않는 일 |
|---|---|---|
| `controller` | Path·Query·Body와 인증 Principal을 받고 형식 검증 후 Service를 호출하며 HTTP 응답을 결정 | Repository 직접 호출, Entity 직접 반환, 트랜잭션·비즈니스 규칙 처리 |
| `service` | 업무 규칙, 트랜잭션, Entity 상태 변경, Repository 조합, DTO 변환을 담당 | HTTP 객체에 의존, 공급자 오류 원문을 응답에 노출 |
| `repository` | Entity 저장과 명시된 조건의 DB 조회·잠금·삭제를 담당 | 접근 권한과 화면 분기 같은 업무 판단 |
| `entity` | Flyway 스키마 매핑과 자신의 유효한 상태 변경을 담당 | API Request/Response 모델 역할 |
| `dto` | API 입력·출력 계약을 표현하고 Bean Validation으로 단일 필드 형식을 검증 | Entity로 재사용, Repository 조회 수행 |
| `common.security` | 쿠키 추출, 인증 Filter, SecurityContext Principal, 401·403 진입점을 담당 | OAuth 회원 가입, 회원·세션 Entity 변경 |
| `common.error/response` | 공통 응답과 예외 매핑을 담당 | 도메인 상태를 직접 조회하거나 변경 |

의존 방향은 `Controller → Service → Repository → Entity`로 고정한다. 다른 도메인은 `Member` Entity나 `MemberRepository`를 직접 변경하지 않고 검증된 `memberId` 또는 합의된 Service 경계를 사용한다.

- 외부 카카오 DTO는 API Response DTO나 `Member` Entity로 재사용하지 않는다.

## 인증 회원 ID 전달 흐름

Controller가 쿠키를 파싱하거나 `auth_sessions`를 직접 조회하지 않는다. 인증 Filter와 Service가 아래 순서로 회원을 확인한 후 Controller에는 검증이 끝난 Principal만 전달한다.

~~~text
SessionAuthenticationFilter.doFilterInternal(request)
  rawSessionId = CookieResolver.find(request, "KGB_SESSION")
  rawSessionId가 없으면 AuthenticationEntryPoint -> 401 AUTH_SESSION_REQUIRED

  principal = ServiceSessionService.authenticate(rawSessionId, now)
    sessionHash = SHA-256(rawSessionId)
    AuthSessionRepository에서 session_id_hash로 세션 조회
    revoked_at IS NULL, expires_at > now 확인
    last_used_at 또는 created_at 기준 유휴 30분 확인
    MemberRepository에서 id와 deleted_at IS NULL 조건으로 회원 조회
    성공 인증 시 last_used_at 갱신
    AuthenticatedMember(memberId, memberStatus, sessionRowId) 반환

  SecurityContext에 Authentication(principal) 저장
  다음 Filter 또는 Controller 호출

Controller
  @AuthenticationPrincipal AuthenticatedMember에서 memberId 추출
  memberId를 Service에 전달
~~~

- 인증용 Repository 조회와 `last_used_at` 갱신은 `ServiceSessionService`의 짧은 트랜잭션 안에서 수행한다.
- 세션 없음·폐기·절대 만료·유휴 만료·탈퇴 회원은 모두 401 `AUTH_SESSION_REQUIRED`로 반환한다.
- DB 연결 장애나 예상하지 못한 조회 실패는 세션 만료로 숨기지 않고 500 `INTERNAL_SERVER_ERROR`로 반환한다.
- 인증 Principal의 `memberId`를 Request Body나 Query의 회원 ID로 덮어쓰지 않는다.
- 소유 자원은 항상 인증 `memberId`를 Repository 조건에 포함해 조회·변경한다.

## 예외 변환 기준

Service와 Repository는 HTTP Response를 직접 만들지 않는다. 도메인·애플리케이션 예외를 발생시키고 `GlobalExceptionHandler`, `AuthenticationEntryPoint`, `AccessDeniedHandler`가 아래 계약으로 변환한다.

| 발생 조건 | 처리 위치 | HTTP | `error.code` 또는 복귀 코드 |
|---|---|---:|---|
| 요청 필드 누락·자료형·길이·페이지 범위 오류 | Bean Validation·Controller 바인딩 | 400 | `COMMON_VALIDATION_ERROR` |
| 세션 쿠키 없음·잘못됨·만료·폐기, 탈퇴 회원 | 인증 Filter·EntryPoint | 401 | `AUTH_SESSION_REQUIRED` |
| 인증됐지만 다른 회원 자원 접근 | Service 소유권 검사·AccessDeniedHandler | 403 | `RESOURCE_FORBIDDEN`. 현재 알림 삭제는 회원 조건부 삭제로 존재를 숨기고 204 사용 |
| 정책 등 공개 자원 없음 | Service | 404 | `RESOURCE_NOT_FOUND` |
| 취향 코드·개수·부모 관계·중복 위반 | PreferenceService | 422 | `PREFERENCE_INVALID` |
| OAuth state·브라우저·provider·만료 검증 실패 | OAuth 콜백 Handler | 302 | `OAUTH_INVALID_REQUEST` |
| 카카오 사용자 취소 | OAuth 콜백 Handler | 302 | `OAUTH_ACCESS_DENIED` |
| 코드 교환·PKCE·사용자 인증 실패 | KakaoOAuthClient·콜백 Handler | 302 | `OAUTH_AUTHENTICATION_FAILED` |
| 카카오 timeout·통신 장애·5xx | KakaoOAuthClient·콜백 Handler | 302 | `OAUTH_PROVIDER_UNAVAILABLE` |
| DB 장애·예상하지 못한 내부 오류 | GlobalExceptionHandler 또는 콜백 Handler | 500 또는 302 | `INTERNAL_SERVER_ERROR` 또는 `OAUTH_INTERNAL_ERROR` |

- 302 OAuth 실패는 공통 JSON 오류가 아니라 허용된 FE 오류 경로로 이동한다.
- 204 응답에는 Body를 넣지 않는다.
- 내부 예외 메시지, SQL, 세션 원문, 인가 코드, state, verifier와 공급자 토큰을 응답·로그에 남기지 않는다.

### API별 코드 구성

아래 이름은 구현을 시작할 때 사용할 기본 계약이다. 역할을 합치거나 이름을 바꾸면 계층 책임과 테스트가 유지되는지 확인하고 문서를 함께 수정한다.

| API | Controller 메서드 | Service 메서드 | Repository·저장소 | Request / Response DTO |
|---|---|---|---|---|

| MEM-15 | Spring Security OAuth Login Filter·성공/실패 Handler | `OAuthAttemptStore.consume(...)`, `KakaoOAuthClient.authenticate(...)`, `OAuthMemberService.loginOrRegister(...)` | `HttpSession`, `MemberRepository`, `AuthSessionRepository` | Query code·state 또는 error·state / 302 Body 없음 |

### Request DTO 검증 위치

| DTO·입력 | 웹 계층(Filter·Controller)에서 형식 검증 | Service에서 업무 규칙 검증 |
|---|---|---|
| `provider` | Authorization Endpoint Filter에서 빈 값·Path 바인딩 | V1 외부 값은 소문자 `kakao`만 허용, 내부 `KAKAO`로 변환하고 저장된 로그인 시도 provider와 일치 |
| OAuth 콜백 Query | OAuth Login Filter에서 성공이면 code/state, 실패면 error/state 형식 | state의 브라우저 결속·만료·일회성 소비, 공급자 응답 신뢰 여부 |
| `UpdatePreferencesRequest` | selections와 각 필드 필수, 문자열 최대 50자, 배열 구조 | Enum 존재, 중복, THEME 1~3, 선택 THEME별 DETAIL 1~3, 부모 관계, 스타일 0~8 |
| `UpdateMemberSettingsRequest` | `push_enabled` 필수 Boolean, null·빈 객체·미지원 필드 거절 | 삭제되지 않은 회원인지 확인하고 전달된 값을 그대로 적용 |
| 알림 page·size | page 양수, size 1~20, 정수 형식 | 인증 회원 범위로만 조회하며 범위 밖 page는 빈 목록 |
| `notification_id` | 양의 BIGINT 문자열로 변환 가능한지 확인 | 인증 회원 ID와 함께 조건부 삭제, 본인 범위에 없으면 멱등 204 |

단일 필드 형식은 DTO의 Bean Validation으로 검사하고, 여러 필드·현재 DB 상태·Enum 부모 관계가 필요한 검증은 Service에서 처리한다.

### Response DTO 데이터 출처

| Response DTO 필드 | 출처·계산 기준 |
|---|---|
| `MemberResponse.member_id` | 인증 회원과 같은 `members.id`, API에서는 십진 문자열 |
| `nickname`, `email`, `profile_image_url`, `language_code`, `status` | `members`의 같은 이름 컬럼. email과 이미지 URL은 null 허용 |
| `MemberResponse.unread_count` | `notifications.recipient_member_id=memberId` 행 개수. 읽은 알림은 삭제되므로 전체 행 수와 같음 |
| 취향 `selections[].preference_type`, `preference_code` | `member_preferences`에서 `member_id=memberId`인 행 |
| 취향 저장 응답 `status` | 같은 트랜잭션에서 확인·변경한 `members.status` |
| 취향 옵션 `code`, `label`, `parent_code`, `sort_order` | DB가 아니라 승인된 V1 Enum Registry와 코드표 |

| 알림 `notification_id`, `type`, `title`, `body`, `reference_type`, `reference_id`, `created_at` | `notifications` 각 컬럼. ID는 십진 문자열, 시각은 ISO 8601 offset 형식 |
| 알림 `page`, `size` | 검증이 끝난 요청값 또는 기본값 1·4 |
| 알림 `total_items`, `unread_count` | 목록과 같은 읽기 트랜잭션에서 계산한 회원별 전체 행 수 |

Controller는 Entity를 반환하지 않고 위 출처를 사용해 Service가 만든 Response DTO를 공통 `{message, data}` 응답으로 감싼다.

### Repository 조회·변경 계약

구현 메서드명은 Spring Data 파생 쿼리나 명시적 JPQL 중 선택할 수 있지만 조건을 줄이거나 Controller에서 대신 검사하지 않는다.

| Repository 작업 | 필수 조건·정렬·잠금 |
|---|---|
| 서비스 세션 조회 | `session_id_hash = SHA-256(cookie)`로 단건 조회. Service가 `revoked_at IS NULL`, 절대·유휴 만료를 함께 검사 |
| 회원 인증 조회 | `members.id=memberId AND deleted_at IS NULL` |
| OAuth 회원 조회 | `oauth_provider='KAKAO' AND oauth_subject=검증된 카카오 id`. 이메일로 병합하지 않음 |
| 활성 세션 목록 | 로그인 성공 TX에서 회원 행 잠금 후 `member_id=memberId AND revoked_at IS NULL`인 기존 유효 세션을 모두 폐기하고 새 세션 1개 발급 |
| 취향 조회 | `member_id=memberId`, 응답 비교가 가능하도록 `preference_type`, `preference_code`, `id`의 안정된 순서 사용 |
| 취향 전체 교체 | 회원 행을 비관적 쓰기 잠금으로 확인한 뒤 해당 member의 기존 행을 삭제하고 검증된 전체 집합 저장 |
| 회원 설정 변경 | `members.id=memberId AND deleted_at IS NULL` 행을 쓰기 잠금으로 조회 후 변경 감지 사용 |
| 알림 목록 | `recipient_member_id=memberId`, `created_at DESC, id DESC`, OFFSET·LIMIT 적용 |
| 알림 개수 | `recipient_member_id=memberId` count. 목록과 같은 읽기 트랜잭션에서 실행 |
| 알림 개별 삭제 | `id=notificationId AND recipient_member_id=memberId` 조건부 DELETE. 영향 행 0개도 성공 |
| 알림 전체 삭제 | 트랜잭션 첫 조회에서 `recipient_member_id=memberId`인 ID를 최대 20개 확보한 후 같은 memberId와 ID 집합으로 DELETE |
| 회원 탈퇴 | `members.id=memberId AND deleted_at IS NULL`을 쓰기 잠금으로 조회하고, 모든 `auth_sessions.member_id=memberId`를 폐기 |

- Repository의 `Optional.empty()`를 무조건 500으로 처리하지 않는다. 인증 과정의 회원·세션 부재는 401, 공개 정책 부재는 404, 멱등 알림 삭제의 부재는 204로 Service가 문맥에 맞게 변환한다.
- API 요청으로 정해진 소유 자원을 조회할 때는 가져온 뒤 회원 ID를 비교하지 말고 가능한 한 Repository 조건에 `memberId`를 포함한다.
- 목록 정렬은 동률을 고려해 항상 `id`를 마지막 정렬 키로 포함한다.

### 트랜잭션 경계

| 처리 | Service 트랜잭션 기준 |
|---|---|
| OAuth 시작 | 업무 DB 트랜잭션 없음. HttpSession 로그인 시도 생성·개수 제한은 동기화해 원자 처리 |
| OAuth 콜백 | 카카오 코드 교환·사용자 정보 조회는 DB 트랜잭션 밖. 검증된 프로필을 받은 뒤 회원·지갑·무료 지급·서비스 세션 저장만 짧은 쓰기 트랜잭션 |
| 세션 인증 | 세션·회원 확인과 `last_used_at` 갱신을 짧은 트랜잭션으로 처리. 외부 호출 없음 |
| 로그아웃 | 현재 세션 `revoked_at` 저장까지 쓰기 트랜잭션. 커밋 후 응답 쿠키 만료 |
| 내 정보·설정·취향·알림 조회 | `readOnly=true`. 서로 연관된 목록과 count는 같은 트랜잭션에서 조회 |
| 취향 전체 저장 | 회원 잠금, 기존 선택 삭제, 새 선택 저장, 최초 ACTIVE 전환을 하나의 쓰기 트랜잭션으로 처리 |
| 설정 변경 | 회원 확인·잠금과 `push_enabled` 변경을 하나의 쓰기 트랜잭션으로 처리 |
| 알림 개별·전체 삭제 | 인증 회원 조건의 삭제를 각각 하나의 쓰기 트랜잭션으로 처리 |
| 회원 탈퇴 | 회원 삭제 표시·OAuth 식별자 해제·세션 폐기·생성권 회수·작업 취소 요청을 정해진 잠금 순서의 하나의 트랜잭션으로 처리. 외부 AI 호출 없음 |
| 정책 조회 | 정적 Registry·Markdown 조회이므로 DB 트랜잭션 없음 |

트랜잭션 메서드는 같은 객체 내부의 `this.method()` 호출로 우회하지 않고 Spring Proxy를 통과하는 public Service 경계로 둔다. 외부 HTTP 호출 중 DB 잠금을 유지하지 않는다.

### 소셜 로그인 시작 API

- **API 명세:** GET /auth/oauth/authorize/kakao (API-MEM-01)
- **권한:** 공개
- **구현 상세**
  - **요청:** Path provider=`kakao`. Query/Body 없음. 내부 처리에서 `KAKAO` Enum으로 변환한다.
  - **처리 로직:**
    1. provider가 소문자 `kakao`인지 검사한다.
    2. state와 PKCE verifier를 만들고 challenge=S256(verifier)를 계산한다.
    3. HttpSession에 브라우저별 로그인 시도를 저장한다. 10분 후 만료되며 연장하지 않는다.
    4. 동시에 보관하는 시도는 최대 5개다. 초과하면 가장 오래된 시도를 지운다.
    5. 등록된 카카오 인증 URL로 302 이동한다. Cache-Control은 no-store로 설정한다.
- **트랜잭션:** 업무 DB 트랜잭션은 없다. 임시 시도 저장·개수 제한은 원자적으로 처리한다.
- **응답 상태**
  - 302: 카카오 로그인 화면
  - 400 COMMON_VALIDATION_ERROR: 소문자 `kakao` 이외 provider
  - 500 INTERNAL_SERVER_ERROR: 내부 오류

### 콜백·회원 가입 API

- **API 명세:** GET /auth/oauth/callback/kakao (API-MEM-15)
- **권한:** 공개 경로지만 로그인 시도 검증 필요
- **구현 상세**
  - **요청:** Path provider=`kakao`. 성공 Query code/state, 취소 Query error/state. Body 없음.
  - **처리 로직:**
    1. 브라우저·provider·state·만료를 확인하고 시도를 원자적으로 한 번 소비한다.
    2. 저장한 verifier로 카카오에 코드를 교환한다. 받은 토큰으로 사용자 정보 id를 확인한다. 카카오 토큰·사용자 정보 요청은 연결 3초, 응답 5초를 넘기면 공급자 장애로 처리한다.
    3. (KAKAO, 사용자 id)로 회원을 찾는다. 신규이면 ONBOARDING으로 만들고 닉네임·이메일·이미지를 저장하며 같은 TX에서 지갑과 가입월 무료 3회를 지급한다.
    4. 기존 회원의 프로필 재동기화는 하지 않는다. 취향·설정도 유지한다.
    5. 회원 행을 잠그고 기존 유효 세션을 모두 폐기한 뒤 새 서비스 세션 ID의 해시와 만료 시각을 auth_sessions에 저장한다.
    6. 커밋 후 KGB_SESSION 쿠키를 발급한다. 정식 FE가 없는 개발 단계에는 같은 백엔드의 `/api/v1/members/me`로 302 이동해 세션과 회원 응답을 확인한다.
    7. 콜백은 취향 옵션이나 지도 콘텐츠 API로 직접 이동하지 않는다. FE가 준비되면 설정 기반 `/auth/complete`로 이동하고, FE는 /members/me를 조회해 ONBOARDING이면 PREF-01, ACTIVE이면 MAP-01로 이동한다.
- **트랜잭션:** 카카오 호출은 DB TX 밖, 신규 회원·지갑·가입월 FREE_GRANT·세션은 하나의 짧은 TX다.
- **응답 상태**
  - 302: 개발 단계 성공 시 `/api/v1/members/me`, 실패 시 `/api/v1/auth/oauth/error?code=허용값`; FE 연동 후에는 설정 기반 `/auth/complete`, `/auth/error`로 교체

| 콜백 실패 code | 처리 |
|---|---|
| OAUTH_INVALID_REQUEST | state 누락·만료·재사용·브라우저 불일치. 새 로그인 시작 |
| OAUTH_ACCESS_DENIED | 검증된 카카오 취소 응답. 로그인 화면 복귀 |
| OAUTH_AUTHENTICATION_FAILED | 코드 교환·verifier 검증 실패 |
| OAUTH_PROVIDER_UNAVAILABLE | 카카오 연결·응답 타임아웃, 통신 장애, 5xx. 잠시 후 재시작 |
| OAUTH_INTERNAL_ERROR | 회원·세션 저장 실패. 트랜잭션 롤백 |

- 신규 가입이 겹치면 DB UNIQUE로 중복을 막는다. 
- 실패한 트랜잭션을 끝내고 검증된 사용자 정보로 회원을 다시 조회하는 방식은 구현 시 시험한다.
- 같은 인가 코드를 무조건 재교환하지 않는다.
- 로그인 전 HttpSession의 인증 정보만으로 업무 API를 통과시키지 않는다.
- 서비스 세션 검증이 필요하다. 
- 커밋 후 응답이 유실되면 DB를 되돌릴 수 없으므로 새 로그인으로 복구하고 전달되지 못한 세션은 만료 처리한다.

**로그인 화면의 성공·실패 처리**

- 확인 중에는 로그인 버튼을 숨기고 로딩을 표시한다. 
- 서비스 세션 저장과 `/members/me` 확인이 끝난 뒤 이동한다. 
- 로딩 화면 자체를 위한 DB 테이블이나 API는 만들지 않는다.
- ACTIVE는 MAP-01, ONBOARDING은 PREF-01로 이동한다. 
- 이미 가입했어도 취향 저장 전 종료한 회원은 PREF-01로 보낸다.
- 인증 취소: ‘사용자에 의해 로그인이 취소되었습니다.’
- 인증 후 로그인 정보를 확인하지 못함: ‘로그인 정보를 확인하지 못했어요. 다시 시도해 주세요.’
- 네트워크·서버 오류: ‘일시적인 오류가 발생했어요. 잠시 후 다시 시도해 주세요.’
- 실패 안내는 약 2초 표시하고 AUTH-01 초기 화면으로 돌아가 버튼을 다시 활성화한다. 서버 오류 원문은 화면에 노출하지 않는다.

### 전체 알림 삭제 API

- **API 명세:** DELETE /notifications (API-NOT-03)
- **권한:** 본인 세션 + CSRF
- **구현 상세**
  - **요청:** Body 없음.
  - **처리 로직:**
    1. 첫 DB 조회 시점에 존재하는 본인 알림 ID를 확보한다. 최대 20개다.
    2. 확보한 ID와 본인 회원 조건으로만 삭제한다.
    3. 그 이후 생성된 알림은 유지한다. 요청 시작을 첫 DB 조회로 해석하는 시점은 FE와 맞춘다.
- **트랜잭션:** 확보한 ID 집합만 삭제한다. 회원의 모든 행을 조건 없이 다시 삭제하지 않는다.
- **응답 상태**
  - 204: 완료 또는 빈 목록
  - 401 AUTH_SESSION_REQUIRED
  - 500 INTERNAL_SERVER_ERROR

## 비동기 처리 설계

### 내부 알림 생성

1. 가이드북 원본 업무가 커밋된 뒤 알림 생성을 호출한다.
2. 별도 트랜잭션에서 수신 회원의 삭제 여부와 알림 필드를 확인한다.
3. 알림을 저장하고 20개를 넘으면 오래된 순서(created_at, id)로 지운다.
4. 알림 실패로 원본 가이드북 생성을 롤백하지 않는다.

- 회원별 생성·정리는 같은 회원 잠금 규칙을 사용하도록 맞춘다.
- 커밋 후 호출이라는 이유만으로 별도 스레드에서 실행되는 것은 아니다.
- Outbox를 두지 않으므로 서버 종료 시 알림 누락 복구는 보장하지 않는다.
- 커밋 여부가 불명확한 실패를 무조건 재시도하면 중복될 수 있어 재시도 범위는 합의가 필요하다. 
- 푸시 설정 저장과 실제 기기 푸시 발송은 별개다.

### Notification 발생 이벤트 예시

| 알림 제목 예시 | 전달할 참조 | 이동 대상 |
|---|---|---|
| 여행 일정이 곧 시작돼요 | 가이드북 ID | GUIDE-06 |
| 가이드북 생성이 완료됐어요 | 가이드북 ID | GUIDE-06-1 |
| 가이드북의 행사 정보가 변경됐어요 | 행사 ID | INFO-02 |

- 처음에는 최신 미읽음 4개를 보여주며 최대 20개, 5페이지다. 
  - 발생 시각은 API의 ISO 8601 값을 한국 시간 `YYYY/MM/DD HH:mm`으로 표시한다.
- 클릭한 알림의 참조 정보를 보관하고 읽기·삭제 API 성공 후 목록에서 제거하고 이동한다.
  - 이동 대상 API는 해당 자원의 권한과 존재 여부를 다시 검사한다. 
  - 참조만으로 접근을 허용하지 않는다.
- 읽기 실패는 목록을 유지하고 ‘읽음 처리에 실패했습니다. 다시 시도해 주세요.’를 표시한다. 
  - 전체 읽음도 같은 규칙이며 알림이 없으면 버튼을 비활성화한다.
- 빈 목록은 ‘새로운 알림이 없어요’, 조회 실패는 ‘알림 조회에 실패했어요’와 ‘페이지에 다시 접속해주세요’를 표시한다. 
  - 실패를 빈 목록으로 처리하지 않는다.
- 상세 화면에서 돌아오면 읽은 항목을 다시 표시하지 않는다. 
  - 목록의 뒤로가기는 MYPAGE-01이다.
- GUIDE-06-1은 확인한 가이드북 뷰어 정의 GUIDE-06과 ID가 다르다. 
  - 동일 화면인지 확인 전 임의 매핑하지 않는다. 
  - 일정 시작 알림의 선행 시간과 행사 변경 판단 필드도 별도로 정해야 한다.

### 설정·정책 화면의 FE 처리

- SETTING-01의 ‘여행 일정 알림’ 토글은 계정의 push_enabled를 읽는다. 
  - 변경 실패 시 이전 값으로 되돌리고 오류를 안내한다. 
  - false여도 인앱 알림·토스트는 표시한다.
- OS 알림 권한과 계정 설정은 별개다. 
  - push_enabled=true만으로 OS 권한이 허용됐다고 판단하지 않는다. 
  - MAP-01 권한 요청과 설정 화면의 상태를 함께 맞춘다.
- AUTH-01의 이용약관·개인정보 처리방침은 모달로 표시하고 확인 버튼 또는 바깥 영역 클릭으로 닫는다. 
  - 기존 정책 API를 사용할 수 있지만 별도 동의 저장 API는 만들지 않는다.

## 보안 및 운영

### 인증과 권한

- 서비스 요청은 DB 세션으로 확인한다.
- 별도 access/refresh token은 발급하지 않는다.
- 역할은 일반 회원 하나다. 
- ONBOARDING/ACTIVE는 역할이 아니라 회원 상태다.
- /auth 전체를 공개하지 않고 로그인 시작·콜백과 정책 조회만 필요한 메서드로 공개한다.
- 알림은 수신 회원 ID, 가이드북은 활성 보관 관계 등 실제 테이블 관계로 접근 권한을 확인한다.
- 로그인 성공 후 새 서비스 세션 ID를 발급한다. 
- 임시 세션 ID를 재사용하지 않는다.

### 세션과 쿠키

- 로그인 시도는 10분, 최대 5개, 한 번만 소비한다.
- 서비스 세션은 절대 8시간·유휴 30분, 연장 없음, 회원당 최대 1개다. 새 로그인 성공 TX에서 기존 유효 세션을 모두 폐기하고 새 세션을 발급한다.
- 로그인 시도 TTL을 그대로 쓰지 않는다.
- KGB_SESSION은 운영에서 HttpOnly, Secure, SameSite=Lax, Path=/, Domain 미지정으로 설정한다.
- expires_at과 revoked_at은 서버에서 검사한다. 
- 쿠키가 남아 있어도 만료 세션은 거절한다.
- last_used_at 기록은 세션 연장과 별개다. 
- 발급 시 last_used_at 초기화, 성공 인증마다 갱신. 만료/폐기 후 30일 경과 행은 매일 정리한다. 상세 V1-03 참조.

### CSRF와 배포

- 변경 요청에 Spring Security CSRF 검증을 적용한다. `XSRF-TOKEN` 쿠키 값을 `X-XSRF-TOKEN` 헤더로 전달한다.
- `GET /api/v1/auth/csrf`는 인증 없이 토큰 계약을 조회하고 쿠키를 발급한다. 응답은 캐시하지 않는다.
- XSRF-TOKEN은 FE가 읽어야 하므로 HttpOnly=false이며 서비스 인증 수단이 아니다. KGB_SESSION은 계속 HttpOnly다.
- 로그인·로그아웃 성공 시 기존 XSRF-TOKEN을 만료하고, 완료 화면에서 CSRF 조회 API를 호출해 새 토큰을 받는다.
- PKCE/state는 일반 API의 CSRF 보호를 대신하지 않는다.
- FE·BE origin이 다르면 `CORS_ALLOWED_ORIGINS`에 정확한 origin을 쉼표로 열거하고 FE는 credentials를 포함한다. 와일드카드는 사용하지 않는다.
- 운영은 `https://kguidebook.site`의 동일 호스트에서 CloudFront가 `/api/*`를 백엔드로 전달하는 구성을 전제로 한다. 따라서 FE가 Domain 미지정 `XSRF-TOKEN` 쿠키를 읽어 헤더로 반환할 수 있다.
- 로컬에서 FE·BE 포트가 다를 때도 쿠키 host를 맞추기 위해 둘 다 `localhost`를 사용한다. `localhost`와 `127.0.0.1`을 섞지 않는다.
- FE·BE가 서로 다른 호스트면 FE JavaScript가 BE의 host-only 쿠키를 읽을 수 없으므로 credentials와 CORS만으로 해결되지 않는다. 이 경우 동일 호스트 프록시 또는 토큰 원문 응답 방식 중 하나를 보안 검토 후 다시 확정한다.
- CORS preflight는 상태 변경에 필요한 `Content-Type`, `X-XSRF-TOKEN`과 생성 요청의 `Idempotency-Key`를 허용한다.
- Preflight는 인증보다 먼저 처리한다.
- 운영은 HTTPS를 사용한다. 프록시 설정·TLS 종료 지점·HSTS는 배포 환경에 맞춰 확인한다.
- 로그에 세션 원문, 인가 코드, state, verifier, 공급자 토큰을 남기지 않는다.
- client secret은 소스 코드나 FE에 넣지 않는다.
- 여러 서버를 사용하면 로그인 전 HttpSession도 공유해야 한다. 
- 공용 MySQL 업무 세션만으로 해결되지 않는다.
- 카카오 PKCE 연동이 실패하면 plain이나 검증 생략으로 낮추지 않고 원인을 확인한다.

#### FE·Postman 전달 순서

1. 브라우저 또는 Postman에서 `GET /api/v1/auth/csrf`를 호출한다.
2. 응답 Cookie Jar의 `XSRF-TOKEN` 값을 읽는다. JSON에는 값이 아니라 쿠키·헤더 이름만 반환한다.
3. POST/PUT/PATCH/DELETE 요청에 `KGB_SESSION` 쿠키와 `XSRF-TOKEN` 쿠키를 함께 보내고, `X-XSRF-TOKEN` 헤더에는 쿠키 값을 그대로 넣는다.
4. 누락·변조 시 `403 RESOURCE_FORBIDDEN`인지와 DB 변경이 없는지 확인한다.
5. 로그인 또는 로그아웃 완료 뒤에는 이전 값을 계속 쓰지 않고 1번부터 다시 수행한다.

정식 FE는 로그인 완료 화면과 로그아웃 완료 처리에서 같은 순서를 수행한다. 로컬 HTTP에서는 `SESSION_COOKIE_SECURE=false`, 운영 HTTPS에서는 `true`를 사용한다. 환경별 Origin은 `CORS_ALLOWED_ORIGINS`에 쉼표로 구분해 넣으며 빈 값은 별도 cross-origin을 허용하지 않는다는 뜻이다.

배포 전 실제 브라우저에서 `GET /api/v1/auth/csrf` 응답 쿠키 확인, 허용 origin의 preflight, `X-XSRF-TOKEN`·`Idempotency-Key` 헤더가 포함된 변경 요청 성공, 비허용 origin과 변조 토큰 거절을 순서대로 검증한다.
