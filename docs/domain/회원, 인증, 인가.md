# 테크스펙 문서 작성

# 도메인 - 회원, 인증, 인가

# 배경

- **프로젝트 목표:**
  - OAuth로 사용자 정보를 확인하고 서비스 세션을 발급하며 회원의 기본 취향, 설정, 알림을 관리한다.
  - **핵심 결과 1:** 로그인 시도와 서비스 세션을 분리하고 검증된 회원만 보호 API에 접근하게 한다.
  - **핵심 결과 2:** 최초 취향 입력, 일반 이용, 로그아웃, 탈퇴 흐름과 상태 변경을 일관되게 처리한다.
  - **핵심 결과 3:** 다른 도메인에 공통 인증, 인가 경계를 제공하고 회원별 데이터 접근을 제한한다.


- **문제 정의:**
  - 외부 OAuth 로그인과 서비스 로그인 유지 수단을 혼용하면 세션 검증, 폐기 책임이 불명확해진다.
  - ONBOARDING 접근을 일괄 차단하면 최초 취향을 저장할 수 없고 로그인 여부만 확인하면 타인 데이터에 접근할 수 있다.
  - 동시 가입, 취향 변경, 탈퇴, 알림 삭제 시 중복 또는 불일치가 발생하지 않도록 처리 순서가 필요하다.


- **가설:**  
  - 서버 세션 인증, 회원 상태 및 소유권 검증, 짧은 트랜잭션 경계를 명시하면 정상 및 예외 흐름을 일관되게 구현할 수 있다.

# 목표가 아닌 것

이번 도메인에서 직접 구현하지 않는 내용이다.

- 여러 OAuth 계정 연결
- 이메일 기반 계정 병합
- 이메일/비밀번호 회원가입
- 서비스 JWT access/refresh token
- 기기별 세션 관리
- 관리자 권한 기능
- 약관 동의 저장
- 프로필 직접 수정
- 생성권 내부 구현(회원 가입/탈퇴 오케스트레이터에서는 생성권 서비스 호출)
- PG
- 가이드북 생성의 내부 구현 (필요한 협업 호출만 명시)
- Redis
- Outbox
- 푸시 공급자 신규 도입

# 설계 및 기술 자료

## 공통 정책

- 기존 계약 유지
- 새 보안 설정의 제안과 미정값은 확정 정책과 구분
- FR-MEM-02와 API-DEC-01은 별도 갱신 API와 서비스 access/refresh token을 제공하지 않는다.
- 현재는 갱신 API를 추가하지 않는다. 
- 가이드북 문서의 ACTIVE 접근 정책을 회원 전체 API에 복사하지 않는다.
- 최초 취향 입력을 위한 ONBOARDING 접근을 유지하며 개별 API 권한은 아래에 명시한다.

### 공통 요청과 응답 규약

- member_id는 Body에서 받지 않고 검증된 세션 principal에서 결정
- BIGINT ID는 API에서 양의 십진 문자열
- 사건 시각은 ISO 8601 offset
- DB는 UTC DATETIME(6)
- 성공은 { message, data }
- 오류는 { message, data: null, error: {code, details, trace_id} }
- 302/204에는 JSON Body가 없다
- 형식 오류 400 COMMON_VALIDATION_ERROR
- 세션 오류 401 AUTH_SESSION_REQUIRED
- 소유권 403 RESOURCE_FORBIDDEN
- 미존재 404 RESOURCE_NOT_FOUND
- 내부 오류 500 INTERNAL_SERVER_ERROR
- 세부 API 표에 400이 누락된 경우 공통 입력 검증 규약을 적용하되 제출 전 API 오류표 동기화
- 제안한 검증 순서는 보안 필터의 실제 실행 순서와 통합 시험
- 인증 실패, CSRF 실패가 동시에 있는 요청의 우선 응답을 임의로 보장하지 않음

### 인증·인가 공통 처리

~~~text
authenticate(request):
  cookie KGB_SESSION이 없거나 형식/길이 정책 위반이면 401
  digest = SHA256(cookie 원문)
  auth_sessions를 digest로 조회
  세션 없음 / revoked_at != null / expires_at <= now 이면 401
  members 조회
  회원 없음 / deleted_at != null 이면 401
  principal = { memberId, status, sessionRowId }
  요청 컨텍스트에만 principal 설정
  last_used_at 기록은 M-Q01 정책에 따라 처리
  업무 handler로 전달

authorizeOwned(resource, principal):
  resource 없음 또는 삭제됨 -> 404
  resource.owner != principal.memberId -> 403
  필요한 업무 상태 검증 -> 해당 API 계약 오류
~~~

- ONBOARDING을 전 API에서 막으면 최초 취향을 저장할 수 없다.
- /me, 취향, 설정, 로그아웃, 탈퇴는 이용 경로가 있어야 한다.
- 생성은 기존 계약상 ACTIVE 필수다.
- 평가, 랭킹에 새로운 ACTIVE 제한을 추가하지 않고 해당 명세의 인증, 소유권, 종료일 조건을 사용한다.
- 역할 테이블이 없는데 ADMIN bypass를 추가하지 않는다.
- 상태 변경은 트랜잭션 안에서 회원 deleted_at과 필요한 업무 상태를 재확인한다.  
- 필터 검사 직후 탈퇴하는 경합을 막기 위한 공통 회원 잠금 제안은 트랜잭션, 협업 경계에서 다룬다.

## 데이터베이스 스키마(ERD)

### 주요 테이블과 임시 저장소

| 저장 대상 | 사용 필드·제약 | 역할 |
|---|---|---|
| members | (oauth_provider, oauth_subject) UNIQUE, status, deleted_at, 프로필·설정 컬럼 | 회원 신원, 업무 상태 |
| auth_sessions | session_id_hash BINARY(32) UNIQUE, expires_at, revoked_at | 로그인 후 인증 |
| member_preferences | UNIQUE(member_id, preference_type, preference_code) | 현재 선택 집합 |
| notifications | recipient_member_id, created_at, id, reference_type/id | 미읽음 목록 |
| 로그인 전 HttpSession | state별 provider/verifier/nonce/시각/고정 URI | 가입 전 단기 데이터. 업무 테이블 아님 |

### 예상 구현 구성

| 구현 이름 | 역할 |
|---|---|
| OAuthAttemptStore | 임시 시도의 저장, 만료, 원자 소비 |
| OAuthMemberService | 검증된 공급자 식별 → 회원 조회/가입, 프로필 동기화 | 
| ServiceSessionService / SessionAuthenticationFilter | 해시 세션 조회, 발급, 폐기 |
| MemberService / PreferenceService / NotificationService | 업무와 트랜잭션 경계 |
| MemberAccessPolicy | principal의 member_id와 리소스 소유권 검증 |
| Clock | UTC 사건 시각과 테스트용 시간 주입 |
| SecurityFilterChain | URL 공개 범위, 세션 인증, CSRF, 인가 실패 응답 설정 |

- Spring oauth2Login의 resolver/repository/성공·실패 처리 지점을 사용한다.  
- 프로토콜 검증 전체를 컨트롤러에 새로 구현하지 않는다.  
- 다만 현재의 다중 시도·10분 TTL·원자 소비·custom auth_sessions는 기본 설정만으로 자동 구현되지 않는다.  
- 참고자료: [Spring OAuth 구성](https://docs.spring.io/spring-security/reference/servlet/oauth2/login/advanced.html)

### 소셜 로그인 시작 API

- **API 명세:** `GET /auth/oauth/authorize/kakao` (API-MEM-01)
- **권한**
  - 공개. 
  - 공급자별 로그인 시도 검증 정보를 생성한다.
- **구현 상세**
  - **요청:**  
    외부 provider 경로값은 소문자 `kakao`, Query/Body 없음. 내부 DB·Java Enum만 `KAKAO`를 사용한다.
    V1은 카카오만 지원하고 V2/V3에서 Google을 별도 경로로 추가한다.

  - **처리 로직·검증:**

    ~~~text
    startOAuth(provider, browser):
      지원 공급자인지 확인 -> 아니면 400
      등록된 client/redirect_uri/scope를 서버 설정에서 선택
      state = 암호학적 난수
      verifier = base64url(32바이트 난수, padding 없음)
      challenge = base64url(SHA256(verifier))
      Google이면 nonce도 생성
      browser 임시 세션에서 만료된 시도를 정리
      원자 구간:
        시도가 5개이면 가장 오래된 시도 폐기
        state별 provider, 고정 URI, verifier 원문, nonce, createdAt, expiresAt 저장
        expiresAt = createdAt + 10분 (연장하지 않음);
      공급자 authorize URL 구성
      Cache-Control: no-store와 Location으로 302
    ~~~
    - 이 단계는 members/auth_sessions를 생성하지 않는다.  
    - 임의 return_url·redirect_uri를 입력받지 않는다.  
    - 임시 쿠키는 HttpOnly·Secure·SameSite=Lax·host-only다.  
    - state/verifier를 로그에 쓰지 않는다.
- **트랜잭션**
  - 업무 DB 트랜잭션 없음.
  - 임시 시도 저장, 개수 제한은 원자적으로 처리한다.
- **응답 상태**
  - 302 Found: 공급자 인증 화면 이동
  - 400 COMMON_VALIDATION_ERROR: 지원하지 않는 provider
  - 500 INTERNAL_SERVER_ERROR: 내부 오류

### callback, 가입 API

- **API 명세:** `GET /auth/oauth/callback/kakao` (API-MEM-15)
- **권한**
  - 공개 경로이나 로그인 전 브라우저·state·provider 결속 및 공급자 검증이 필수다.
- **구현 상세**
  - **요청:**  
    Path provider, 성공 query code/state.  
    공급자 거절 query error/state.  
  - **처리 로직·검증:**

    ~~~text
    callback(provider, query, browser):
      브라우저 임시 세션에서 query.state의 시도를 찾음
      누락/만료/provider·브라우저 불일치 -> OAUTH_INVALID_REQUEST
      해당 시도의 검증과 소비를 한 번에 원자 처리
      같은 state의 두 번째 callback은 거절
      다른 정상 state는 삭제하지 않음
      결속이 검증된 error 응답이면 OAUTH_ACCESS_DENIED 등 허용 코드로 매핑

      DB 트랜잭션 없이:
        저장된 verifier로 code를 공급자에 교환
        Google: 
            서명/iss/aud/exp/nonce 검증 후 subject 추출
        Kakao:
            서버가 얻은 토큰으로 사용자 정보 id 확인
        provider+subject, nickname, nullable image를 내부 DTO로 변환
        토큰·코드·verifier를 FE에 전달하지 않음

      짧은 DB 트랜잭션:
        provider+subject로 회원 확인
        기존 회원:
            잠금 후 삭제/식별자 변화 재확인
        신규 회원:
            ONBOARDING 회원 INSERT
        nickname/image를 현재 공급자 값으로 동기화
        기존 회원의 취향·language/push 설정은 덮어쓰지 않음
        새 불투명 서비스 sessionId 생성, SHA256만 auth_sessions에 INSERT
        해당 회원 행을 잠그고 기존 유효 세션을 모두 revoke
        expires_at=created_at+8시간, last_used_at=현재 시각인 새 세션 1개 발급(V1-03)
      COMMIT 후:
        Set-Cookie: KGB_SESSION=원문; 
        HttpOnly; 
        Secure; 
        SameSite=Lax; 
        Path=/
        Location:{FRONTEND_ORIGIN}/auth/complete, no-store, 302
      FE:
        GET /members/me
        ONBOARDING -> PREF-01
        ACTIVE -> MAP-01
        401 -> 로그인
    ~~~

    **경합:**  
    - 신규 가입 동시 INSERT의 UNIQUE 위반은 실패한 트랜잭션을 종료하고 새로운 트랜잭션에서 회원을 다시 조회하는 제안이다.  
    - 외부 code 교환을 다시 하지 않고 이번 요청 메모리의 검증된 DTO를 사용한다.  
    - 무한 재시도하지 않는다.  
    - 중복 가입과 동시 탈퇴 경로를 통합 시험한다.  

    **중요:**  
    - AttemptStore에서 소비한 값을 Spring 기본 repository가 다시 소비해 실패하지 않도록 token 교환에 전달할 요청 문맥을 한 곳에서 소유한다.  
    - custom 서비스 세션 외에 로그인 전 HttpSession의 SecurityContext만으로 업무 인증이 우회되지 않게 구성한다.  
    - 성공 후 다른 탭의 유효 시도 보존과 임시 세션 회전 전략은 M-Q03에서 확인한다.

   | 실패 | 복귀 code | 처리 |
   |---|---|---|
   | state 등 실패 | OAUTH_INVALID_REQUEST | 새 로그인 시작 |
   | 결속된 사용자 취소 | OAUTH_ACCESS_DENIED | 로그인 복귀 |
   | 교환/ID token 실패 | OAUTH_AUTHENTICATION_FAILED | 새 시도 |
   | 공급자 timeout/5xx | OAUTH_PROVIDER_UNAVAILABLE | 잠시 후 새 시도 |
   | DB 저장/내부 오류 | OAUTH_INTERNAL_ERROR | 미커밋 전체 롤백 |

   - 실패는 고정 FRONTEND_ORIGIN의 /auth/error?code=허용값으로 302한다.  
   - 공급자 원문 오류는 노출하지 않는다.  
   - COMMIT 후 네트워크 단절은 DB를 롤백할 수 없으며 사용자는 새 로그인으로 복구하고 전달되지 못한 세션은 만료/정리 대상이다.


- **트랜잭션**
  - 공급자 호출은 DB 트랜잭션 밖에서 수행한다. 
  - 회원 생성/동기화와 서비스 세션 INSERT는 짧은 단일 트랜잭션으로 처리한다.
- **응답 상태**
  - 302 Found:
    - 성공 시 /auth/complete
    - 실패 시 /auth/error?code=허용값.

### 회원 탈퇴 API

- **API 명세:** `DELETE /members/me` (API-MEM-06)
- **권한**
  - 유효한 세션 + CSRF. principal의 회원만 탈퇴 처리한다.
- **구현 상세**
  - **요청:**  
    - Body 없음.
    - 확인 모달은 FE 책임.
  - **처리 로직·검증:**

    ~~~text
    withdraw(principal):
      TX:
        members 행 잠금, 미삭제 여부 재확인
        deleted_at = now
        oauth_subject = 공급자 실제 subject와 충돌하지 않는 폐기용 값
        해당 회원의 모든 활성 auth_sessions.revoked_at = now
        가이드북 담당의 내부 취소요청 서비스 호출
          진행 job의 cancel_requested_at을 같은 DB TX에 기록하는 경계 합의
          외부 AI HTTP는 이 TX 안에서 호출하지 않음
      COMMIT:
        현재 쿠키 만료
        외부 취소 전파는 가이드북 worker/복구 경로가 수행
        204
    ~~~
    
    - 폐기값은 deleted:{memberId}, 실제 provider subject에서 해당 namespace를 수용하지 않는다(V1-16).
    - 새 subject로 기존 소셜 식별자를 해제하고 재가입은 새 회원이다.  
    - deleted_at만 두고 인증 필터를 빠뜨리지 않는다. 
    - 30일 후 서비스 데이터 정리는 별도 배치가 FK와 법정 보존 참조를 고려해 삭제/비식별화한다.  
    - 단순 members DELETE나 cascade 전파로 원장까지 삭제하지 않는다.  
    - 정리 순서, 배치 재시도는 M-Q05.  
    - 결제 중 탈퇴는 팀원과 PG 계약 후 합의한다.

- **트랜잭션**
  - 회원 잠금, 소프트 삭제, 소셜 식별자 해제, 전체 세션 폐기를 함께 처리한다.  
  - 생성 취소 요청 기록의 동일 트랜잭션 참여는 담당자와 합의한다.
- **응답 상태**
  - 204 No Content: 탈퇴 완료
  - 401 AUTH_SESSION_REQUIRED: 세션 오류
  - 500 INTERNAL_SERVER_ERROR: 내부 오류

### 취향 전체 저장 API

- **API 명세:** `PUT /members/me/preferences` (API-MEM-09)
- **권한**
  - 유효한 세션 + CSRF. 
  - ONBOARDING의 최초 저장과 ACTIVE의 변경 모두 허용한다.
- **구현 상세**
  - **요청:**

    ~~~json
    {"selections":[{"preference_type":"THEME","preference_code":"HEALING"}]}
    ~~~

    ~~~text
    replacePreferences(req, principal):
      selections 배열·필수 필드·문자열 길이/타입 검증 -> 형식 오류 400
      동일(type,code) 중복 거절 -> 422 PREFERENCE_INVALID
      registry에 없는 코드/type 조합 -> 422 PREFERENCE_INVALID
      THEME 개수 1-3 검증 -> 422
      각 DETAIL의 부모가 이번 제출 THEME 집합에 있는지 -> 아니면 422
      선택 THEME마다 DETAIL 1~3, TRAVEL_STYLE 0~8 검증 -> 422 PREFERENCE_INVALID

      TX:
        회원 행 잠금, deleted_at 재검증

        요청에 없는 행 삭제, 새 행 삽입

        최초 유효 저장이면 status=ACTIVE
      200 preference_update_success
      data={selections: 저장된 전체 집합, status: "ACTIVE"}
    ~~~

    - 요청에 고아 DETAIL이 남아 있으면 조용히 지우지 않고 거절한다.

    - 같은 요청은 같은 집합을 유지하고 일부 INSERT 실패는 전체 롤백한다. 
    - 가이드북 생성 접수 담당은 이 변경과 경합할 때 찢어진 취향 집합을 읽지 않도록 동일 회원 잠금/일관된 조회 경계를 합의한다.  
    - 이미 저장한 생성 입력 스냅샷은 변경하지 않는다.
- **트랜잭션**
  - 회원 잠금·선택 집합 교체·ACTIVE 갱신을 하나로 처리한다.

- **응답 상태**
  - 200 OK: preference_update_success
  - 400 COMMON_VALIDATION_ERROR: 형식 오류. 중복 조합은 422 PREFERENCE_INVALID
  - 401 AUTH_SESSION_REQUIRED: 세션 오류
  - 422 PREFERENCE_INVALID: 코드·대분류 개수·상하위 관계 위반

    COMMIT -> 204
    ~~~

    - 단순 created_at<=now 또는 id<=max 조건은 늦게 커밋한 새 알림을 잘못 포함할 수 있다. 
    - 명시 ID 집합을 사용하는 제안이다. 
    - “요청 시작”은 첫 DB 스냅샷으로 선형화하는 해석이며 정확한 시점을 FE/BE와 합의한다. 
    - 그 이후 생성된 ID는 유지한다.

- **트랜잭션**
  - 첫 읽기 스냅샷에서 확보한 ID 집합만 수신 회원 조건과 함께 삭제한다. 
  - 선형화 시점은 M-Q09에서 합의한다.
- **응답 상태**
  - 204 No Content: 전체 삭제 또는 빈 목록
  - 401 AUTH_SESSION_REQUIRED: 세션 오류
  - 500 INTERNAL_SERVER_ERROR: 내부 오류

## 비동기 처리 설계

### 내부 알림 생성 — 연동 제안

~~~text
원본 업무 COMMIT 후 NotificationService 호출
입력: recipient, 승인된 type, title/body, nullable reference pair
TX:
  recipient 회원 잠금·미삭제 확인
  필드 길이/type/reference 쌍 검증
  notification INSERT
  해당 회원 목록을 created_at ASC,id ASC로 정렬
  20개 초과분 ID만 DELETE
COMMIT
푸시가 필요하고 수신 허용이면 별도 공급자 경계로 처리
~~~

- 회원별 삽입·정리를 직렬화해 동시 INSERT의 개수 초과를 방지하는 제안이다. 
- 모든 생산자가 같은 규칙을 따라야 한다. 
- Outbox는 없다. 
- 커밋 직후 프로세스 종료 시 알림 누락 복구는 보장하지 않는다. 
- 커밋 여부를 모르는 오류를 무조건 재시도하면 중복 알림이 생길 수 있고 현재 notifications에는 원인 UNIQUE가 없다. 
- 확정 롤백만 재시도할지 원인 식별 제약을 추가할지 M-Q07에서 합의한다. 
- 원본 업무를 롤백하지 않는다.

## 트랜잭션, 협업 경계

**V1 확정 잠금 순서:**
  - 회원 → 지갑 → 생성 작업 → 가이드북 → 종속 행. 같은 테이블은 PK 오름차순.
  - 평가 문서도 같은 순서를 제안한다. 
  - 외부 호출은 DB TX 밖에 둔다. 
  - V1 회원·지갑·가이드북 쓰기는 V1-11을 공통 적용한다. 평가·결제 확장은 해당 버전 구현 전에 추가한다.

| 연동 | 합의할 계약 |
|---|---|
| 신규 가입 → 생성권 | 가입 TX에서 지갑 및 가입월 무료 3회 지급(V1-07/11) |
| 탈퇴 → 가이드북 | 취소 요청 DB 기록의 TX 참여·외부 전달·늦은 완료 거절 |
| 탈퇴 → 결제 | 진행 PG 승인과 탈퇴 경합·법정 보존 |
| 취향 → 가이드북 | 현재 취향의 원자적 스냅샷 읽기 |
| 평가 → 회원 | 회원 잠금/탈퇴 재검증, 완료 알림을 커밋 후 처리 |
| 알림 → 원본 | 업무 원인 식별·중복·허용 손실 경계 |

- 인증 필터에 통과한 요청도 이후 탈퇴할 수 있다. 
- 상태 변경이 회원 잠금을 공유하면 먼저 잠근 TX의 커밋을 기준으로 순서가 정해진다.
- 외부 완료 처리도 삭제 회원을 다시 확인해야 한다.
- 로그아웃과 이미 실행 중인 요청의 허용 경계는 M-Q01에서 명시한다.

## 보안 및 운영

### 사용자 식별 방식과 선택 근거

- OAuth/OIDC는 외부 공급자를 통해 신원을 확인하는 로그인 과정
- 서비스 세션은 로그인 이후 우리 API 요청자를 확인하는 수단
- 두 가지를 대체 관계로 설명하지 않음

| 구분 | 식별·검증 방식 | 책임 |
|---|---|---|
| 외부 계정 | oauth_provider + oauth_subject | 같은 공급자의 같은 사용자를 식별하며 이메일로 계정을 합치지 않는다. |
| 로그인 시도 | 로그인 전 HttpSession에 연결한 state, PKCE 정보 | 기존 정책인 10분·최대 5개·일회성 소비로 콜백을 검증한다. |
| 서비스 요청 | KGB_SESSION 원문 → 해시 → auth_sessions 조회 | 만료·폐기·회원 상태를 확인한다. |
| 업무 권한 | 현재 회원 상태 + 대상의 소유권 + 업무 조건 | 로그인 성공과 별개로 각 기능의 실행 가능성을 판단한다. |

- DB 세션을 선택한 이유는 기존 MySQL과 auth_sessions를 이용하고, 로그아웃·탈퇴 시 서버에서 접근을 폐기하기 쉽기 때문이다. 
- 반면 인증 시 DB 조회 비용과 DB 가용성에 의존한다. 
- JWT 자체 검증은 조회를 줄일 수 있지만 즉시 폐기와 변경된 권한 반영을 별도로 설계해야 한다. 
- JWT가 본질적으로 안전하지 않아서 제외한 것은 아니다.
- 우리 서비스는 access/refresh token을 발급하지 않으므로 해당 토큰의 만료시간·rotation·갱신 API는 적용 대상이 아니다. 
- 공급자의 access token과 Google ID token은 외부 로그인 검증에 사용하는 값이며, 우리 API의 Bearer 인증 수단으로 받지 않는다. 
- 오프라인 공급자 접근도 현재 범위가 아니므로 공급자 토큰을 불필요하게 영속 저장하지 않는다. 
- Spring의 AuthorizedClient 저장 설정도 구현 시 확인한다.

### 역할(Role)·권한(Permission)과 접근 제어

현재 업무 역할은 일반 회원 하나다. 관리자는 범위 밖이며 새로운 roles/permissions 테이블을 추가하지 않는다.  
미인증은 인증 상태, ONBOARDING/ACTIVE는 회원 상태, 소유자는 리소스와 회원의 관계다.  
이들을 각각 별도 역할로 만들지 않는다.

구현에서는 유효한 회원 principal에 ROLE_MEMBER 같은 공통 authority를 부여할 수 있다.  
이는 구현 이름 제안이지 신규 DB 컬럼이나 API 응답 필드가 아니다.  
아래 권한 이름도 설명용이며 저장할 permission 코드가 아니다.

| 권한 | 대상 API | 허용 조건 |
|---|---|---|
| 공개 로그인·정책 접근 | MEM-01, MEM-12, MEM-13 | 세션 없이 접근 가능 |
| OAuth 콜백 완료 | MEM-15 | 공개 경로지만 브라우저에 연결된 로그인 시도와 공급자 검증 필수 |
| 본인 정보·취향·설정 조회 | MEM-04, MEM-07, MEM-08, MEM-10 | 유효한 세션. ONBOARDING도 취향 입력을 위해 접근 가능 |
| 본인 취향·설정 변경 | MEM-09, MEM-11 | 세션 + CSRF + 각 입력 검증 |
| 본인 로그아웃·탈퇴 | MEM-03, MEM-06 | 세션 + CSRF. 대상 회원 ID는 principal에서 결정 |
| 본인 알림 조회·삭제 | NOT-01-3 | 조회는 세션, 삭제는 CSRF 추가. 다른 회원 알림은 접근 불가 |
| 본인 가이드북 평가 | 평가 API | 세션과 소유권. 목록·상세·제출 각각의 상태·여행 종료 조건은 평가 테크스펙 적용 |
| 랭킹 조회 | 랭킹 API | 현재 API의 세션 요구 조건 적용 |
| 가이드북 생성 | GDE-02 | ACTIVE·기본 취향·생성권 등 생성 도메인 조건을 추가 검증 |

인가 처리 순서는 다음과 같다.

1. SecurityFilterChain에서 HTTP 메서드와 경로를 함께 기준으로 공개 API를 한정한다.
2. 나머지 업무 API는 세션 인증을 요구한다. /auth/** 전체를 공개하면 로그아웃까지 공개할 수 있으므로 사용하지 않는다.
3. 서비스 계층에서 principal의 회원 ID로 데이터를 조회하고 대상 소유권을 검증한다. 요청 body의 member_id를 신뢰하지 않는다.
4. 상태 변경은 트랜잭션 안에서 회원 상태와 업무 조건을 다시 확인한다. 인증 필터 통과가 커밋 시점 권한까지 보장하지 않는다.
5. 운영·헬스 체크 경로를 전체 공개하지 않는다. 필요한 경로와 네트워크 접근을 별도로 제한한다.

PG·AI 시스템 콜백이 필요하면 별도의 시스템 인증을 설계한다. 일반 회원 역할을 부여하거나 세션 검증을 무조건 생략하는 것으로 대체하지 않는다.

근거: [Spring Security 요청 단위 인가](https://docs.spring.io/spring-security/reference/servlet/authorization/authorize-http-requests.html).  URL 접근 제어만으로 객체 소유권 검증이 끝나지 않으므로 서비스 계층 검증을 병행한다.

### 세션 수명·발급·폐기·장애 정책

| 항목 | 현재 계약 또는 추가 제안 | 확정 상태 |
|---|---|---|
| 로그인 시도 | 10분, 최대 5개, 일회성 소비 | 기존 계약 |
| 서비스 세션 ID | 암호학적 난수로 생성. SecureRandom 32바이트를 Base64URL(no padding)로 인코딩 | V1-03 확정 |
| DB 저장 | 원문 대신 SHA-256 해시를 BINARY(32)에 저장. expires_at·revoked_at 검증 | 기존 계약 |
| 절대 만료 | 발급 후 8시간, 자동 연장 없음(V1-03). | M-Q01 |
| 유휴 만료·슬라이딩 연장 | 유휴 30분, 성공 인증마다 기록. 절대8시간은 연장하지 않는다. | M-Q01 |
| 브라우저 쿠키 수명 | Max-Age=28800. 유휴 30분 만료는 서버에서 별도 거부한다. | M-Q01 |
| last_used_at | 활동 기록이며 값을 변경한다고 세션이 자동 연장되는 것은 아니다. | 성공 인증마다 기록 |
| 로그아웃·탈퇴 | 로그아웃은 현재 세션, 탈퇴는 해당 회원의 전체 세션 폐기 | 기존 계약 |
| 동시 로그인 | 기기별 관리 UI 없이 회원당 최대 1개, 새 로그인 시 기존 활성 세션 모두 폐기 | M-Q01 |
| 만료 데이터 정리 | 정리 작업이 늦어져도 인증 단계에서 만료를 거부한다. 만료/폐기 후30일 경과 행을 매일 정리 | M-Q01 |

로그인 성공 시 서버가 새 서비스 세션 ID를 발급한다. 로그인 전 세션 ID나 클라이언트가 정한 값을 그대로 서비스 세션으로 승격하지 않는다. 회원 ID·이메일처럼 추측 가능한 값을 세션 ID에 넣지 않는다. 이는 세션 고정 공격과 추측 위험을 줄이기 위한 것이다.

[OWASP 세션 관리 지침](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)은 예측 불가능한 식별자, 서버 측 만료, 인증 전후 세션 관리의 중요성을 설명한다. 난수 길이와 운영 수치는 V1-03에서 선택한 프로젝트 기준이며 표준 의무값은 아니다.

auth_sessions 조회 실패 시 인증을 통과시키지 않는다. DB 장애를 토큰 만료로 오인해 401로 처리하지 않고 기존 서버 오류 계약인 500으로 구분한다. 상태 변경은 TX에서 요청 세션·회원 상태를 재검증한다(V1-03). 이미 끝난 읽기 응답은 소급 취소하지 않는다.

로그인 전 HttpSession의 만료 설정은 직접 관리하는 auth_sessions의 만료 정책을 대신하지 않는다. 다중 인스턴스에서는 로그인 시도 저장소 접근 방식도 별도로 보장해야 한다.

### 비밀번호·비밀값·HTTPS 보안

현재 서비스는 비밀번호를 입력받거나 저장하지 않는다. 비밀번호 검증은 공급자 화면에서 수행하며 자체 password 컬럼·비밀번호 재설정 API를 추가하지 않는다.

세션 원문의 SHA-256 해시 저장은 고엔트로피 난수 보호 방식이지 사용자 비밀번호 저장 방식이 아니다. 향후 자체 비밀번호 인증이 추가된다면 salt와 비용 조절이 가능한 전용 password encoder를 검토해야 한다. 현재 bcrypt 등을 사용하는 것으로 기재하지 않는다.  
근거: [Spring Security 비밀번호 저장](https://docs.spring.io/spring-security/reference/features/authentication/password-storage.html).

| 항목 | 적용 내용과 이유 | 상태 |
|---|---|---|
| HTTPS·Secure | 운영 환경은 HTTPS를 사용하고 서비스 쿠키에 Secure 적용 | 기존 계약 |
| HttpOnly | 서비스 쿠키를 JavaScript에서 읽지 못하게 한다. XSS 자체를 막는 것은 아니다. | 기존 계약 |
| SameSite·범위 | Lax, host-only, Path=/ 계약 유지. SameSite를 CSRF 검증의 대체재로 보지 않는다. | 기존 계약 |
| TLS 버전 | TLS 1.3 우선, 필요한 호환성에 한해 1.2 허용 검토 | 배포 제안, M-Q10 |
| TLS 종료 지점 | LB/프록시에서 종료할지와 이후 BE·DB 구간의 암호화·네트워크 신뢰 경계를 결정 | M-Q10 |
| 프록시 헤더 | 신뢰한 프록시의 Forwarded/X-Forwarded-*만 사용하여 scheme·host 위조 방지 | 배포 제안, M-Q10 |
| HSTS | HTTPS 구성이 검증된 후 max-age·서브도메인 적용 범위를 결정. preload를 무조건 켜지 않는다. | M-Q10 |
| 공급자 통신 | 인증서·호스트 검증을 끄지 않는다. 실패 시 로그인 실패로 처리한다. | 보안 구현 원칙 |
| 캐시 | 기존 OAuth 응답의 Cache-Control: no-store 계약 유지 | 기존 계약 |
| 비밀 관리 | client secret 등을 Git·이미지·FE 번들에 넣지 않고 실행 환경에서 주입 | 저장·교체 절차는 M-Q11 |

HTTP에서 HTTPS로 redirect하더라도 최초 HTTP 요청으로 노출된 비밀을 되돌릴 수 없다. 로컬 개발 예외와 운영 설정은 분리한다.   
근거: [OWASP TLS 지침](https://cheatsheetseries.owasp.org/cheatsheets/Transport_Layer_Security_Cheat_Sheet.html).

감사 로그에는 로그인 성공/실패 유형, 세션 폐기, 접근 거부, 추적 ID 등 필요한 사건을 남기되 Cookie·Set-Cookie·인가 코드·state·verifier·공급자 토큰·세션 원문을 남기지 않는다. 애플리케이션뿐 아니라 프록시 access log와 APM의 URL query/header 수집도 점검한다.

세션 유출 시 해당 세션 또는 회원 세션들을 폐기하고 재로그인을 요구할 수 있어야 한다. 이 설명은 공개 관리자 API 추가를 의미하지 않는다. 로그 접근·보관 기간·비밀 교체·사고 대응 절차는 M-Q11에서 정한다.

### CSRF 구현 경계

- 현재 POST/PUT/PATCH/DELETE는 CSRF 검증 대상
- Spring의 token 생성, 검증을 사용
- API JSON 오류와 맞춤
- OAuth callback의 state/PKCE는 일반 CSRF token을 대체하지 않는다.
- FE에 token을 전달하는 헤더/쿠키/엔드포인트 계약은 아직 미정이다.
- 새 API를 임의로 추가하지 않는다.
- 세션 수명·token 회전·로그인 직후 최초 변경 요청까지 M-Q02 승인 후 구현한다.
- HttpOnly 서비스 세션 ID를 JS에 공개하는 방식은 사용하지 않는다.
- 참고자료: [Spring CSRF](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)

### CSRF·CORS·인증 오류 구현 상세

CSRF 구현 경계의 요구사항을 구현할 때는 다음 흐름을 적용한다. FE에 토큰을 전달하는 구체적 계약은 M-Q02 확정 전까지 신규 API로 단정하지 않는다.

1. FE가 합의된 방식으로 CSRF 토큰을 확보한다. HttpOnly 서비스 세션 쿠키를 JavaScript로 읽는 방식은 사용하지 않는다.
2. 상태 변경 요청에 서비스 쿠키와 CSRF 토큰 헤더를 함께 전송한다.
3. 서버는 토큰을 검증한 뒤 서비스 로직을 실행한다. Spring 기본 설정을 그대로 썼다고 가정하지 말고 커스텀 세션 인증과 토큰 저장소의 연결을 확인한다.
4. 로그인·로그아웃 시 토큰 재발급/재조회와 여러 탭의 동작을 시험한다.
5. 인증된 요청에서 CSRF 토큰 누락·불일치는 변경 없이 거부한다. 403 및 오류 message 계약은 M-Q02에서 확정한다. 미인증과 CSRF 오류가 동시에 발생할 때의 우선순위도 맞춘다.

OAuth 콜백의 state·PKCE 검증과 일반 상태 변경 API의 CSRF 검증은 적용 경계가 다르다. 공급자 콜백을 처리하기 위해 서비스 전체의 CSRF 보호를 끄지 않는다. 브라우저 쿠키를 사용하지 않는 PG 등의 콜백 예외도 대상 경로·메서드와 별도 인증 방식이 확인된 경우에만 둔다.

FE와 BE가 다른 origin이면 허용 origin을 정확히 열거하고 credentials 사용 시 *를 사용하지 않는다. 필요한 메서드·헤더만 허용한다. 브라우저 preflight OPTIONS에는 세션 쿠키가 없을 수 있으므로 CORS 처리를 인증보다 먼저 수행한다. OPTIONS 허용은 실제 업무 요청의 인증·인가 면제를 의미하지 않는다.

SameSite의 site와 CORS의 origin은 다른 개념이다. 서브도메인 구성이 same-site여도 cross-origin일 수 있으므로 각각 검증한다.  
근거: [Spring Security CORS](https://docs.spring.io/spring-security/reference/servlet/integrations/cors.html), [Spring Security CSRF](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html).

업무 API는 미인증 401, 권한 부족 403, 존재하지 않는 대상 404, 서버 장애 500을 현재 응답 계약에 맞춰 구분한다. 세션이 없다는 이유로 JSON API를 HTML 로그인 화면으로 302 이동시키지 않는다. OAuth 로그인 경로의 302 계약은 별개다.

### 셀프 리뷰

- [ ] 각 API의 입력·출력과 실패 분기를 직접 설명했다.
- [ ] PKCE·세션 수치 확정과 실제 보안 연동 검증을 구분했다.
