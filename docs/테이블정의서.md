# V3 테이블 정의서

> 이 문서는 `docs/요구사항정의서.md`를 기준으로 V3에서 영속화할 테이블, 컬럼, 키와 무결성 규칙을 정의한 ERD 설계 초안이다.
>
> MySQL 8.x와 InnoDB 기준이며, JPA 매핑 시 문자열 상태값은 애플리케이션 Enum과 `VARCHAR`로 저장한다.

## 1. 공통 설계 원칙

- 테이블은 반복 행, 독립적인 생명주기, 다른 데이터의 참조, 이력 또는 유일 제약이 필요한 경우에 만든다.
- 모든 사건 시각은 타임존 정보가 없는 MySQL `DATETIME(6)`에 UTC 값으로 저장하고 DB 세션과 JDBC 타임존도 UTC로 고정한다. 한국 사용자에게 표시할 때만 `Asia/Seoul`로 변환하며 API는 ISO 8601 오프셋을 포함해 전달한다.
- 외부에 노출하는 가이드북·생성 작업 ID는 추측하기 어려운 문자열 ID를 사용한다.
- 삭제는 `deleted_at`으로 소프트 삭제하고, 삭제가 아닌 업무 상태 변화는 `status`로 관리한다. 별도의 공통 상태 변경 시각은 두지 않는다.
- JSON 컬럼은 AI 요청·응답처럼 구조 변경이 잦은 스냅샷에만 사용한다. 검색, 조인, 유일성 검사가 필요한 값은 일반 컬럼으로 분리한다.
- 생성권·결제 원장은 회원 탈퇴 후에도 정산과 감사에 필요한 범위에서 보존한다.

## 2. DOM-01 회원

### 2.1 `members`

회원, OAuth 식별 정보, 기본 프로필과 설정을 관리한다. V1은 KAKAO만, V2 이상(V3 포함)은 KAKAO·GOOGLE을 모두 지원한다. 이는 서비스가 지원하는 공급자의 수이며 회원당 하나의 OAuth 계정만 연결하는 현재 모델과 모순되지 않는다. 별도 소셜 계정 연결/통합 기능은 제공하지 않으므로 별도 소셜 계정 테이블을 두지 않는다.

| 컬럼 | 타입 | NULL | 키/기본값 | 설명 |
| --- | --- | --- | --- | --- |
| `id` | BIGINT | N | PK, AUTO_INCREMENT | 회원 식별자 |
| `oauth_provider` | VARCHAR(20) | N |  | 허용 코드 `KAKAO`, `GOOGLE`. V1 KAKAO만, V2 이상 둘 다 지원 |
| `oauth_subject` | VARCHAR(255) | N |  | 공급자가 발급한 사용자 고유 식별자 |
| `nickname` | VARCHAR(50) | N |  | OAuth 계정에서 받아온 표시 이름. 별도 닉네임 설정은 제공하지 않음 |
| `profile_image_url` | VARCHAR(2048) | Y |  | OAuth 계정에서 받아온 프로필 이미지 URL |
| `language_code` | VARCHAR(10) | N | `'ko'` | 표시 언어 |
| `status` | VARCHAR(20) | N | `'ONBOARDING'` | 필수 취향 입력 전 `ONBOARDING`, 이용 가능 `ACTIVE` |
| `push_enabled` | BOOLEAN | N | `TRUE` | 푸시 수신 여부 |
| `deleted_at` | DATETIME(6) | Y |  | 회원 탈퇴에 따른 소프트 삭제 시각 |
| `created_at` | DATETIME(6) | N |  | 생성 시각 |
| `updated_at` | DATETIME(6) | N |  | 수정 시각 |

제약 및 인덱스:

```text
UNIQUE (oauth_provider, oauth_subject)
INDEX (status)
```

지원 공급자는 애플리케이션 Enum/검증으로 제한한다. 현재 SQL의 VARCHAR 자체가 허용 코드까지 강제하는 것은 아니다. 회원 식별은 `(oauth_provider, oauth_subject)`이며 서로 다른 공급자의 동일 이메일은 자동 병합하지 않는다.

OAuth의 `state`, PKCE `code_verifier`는 가입 전 로그인 시도의 단기 검증 데이터다. `members`에 영구 저장하거나 로그인 성공 후 refresh 세션인 `auth_sessions`와 혼용하지 않는다. 저장 위치·TTL·일회 소비·다중 인스턴스 방식은 API-DEC-01 결정 대상이며 현재 테이블만으로 이 흐름이 완성됐다고 보지 않는다. verifier는 공급자 토큰 교환에 원문이 필요하므로 refresh_token_hash처럼 해시만 저장하는 방식과 구분한다.

트레이드오프: 여러 OAuth 계정 연결이 필요해지면 `oauth_provider`, `oauth_subject`를 `social_accounts`로 분리해야 한다.

### 2.2 `auth_sessions`

리프레시 토큰 단위의 로그인 세션과 폐기 상태를 관리한다.

| 컬럼 | 타입 | NULL | 키/기본값 | 설명 |
| --- | --- | --- | --- | --- |
| `id` | BIGINT | N | PK, AUTO_INCREMENT | 세션 식별자 |
| `member_id` | BIGINT | N | FK | 회원 식별자 |
| `refresh_token_hash` | VARCHAR(255) | N | UNIQUE | 리프레시 토큰 해시 |
| `expires_at` | DATETIME(6) | N |  | 만료 시각 |
| `revoked_at` | DATETIME(6) | Y |  | 로그아웃·탈퇴로 폐기된 시각 |
| `last_used_at` | DATETIME(6) | Y |  | 마지막 갱신 시각 |
| `created_at` | DATETIME(6) | N |  | 발급 시각 |

제약 및 인덱스:

```text
FK (member_id) REFERENCES members(id)
UNIQUE (refresh_token_hash)
INDEX (member_id, revoked_at, expires_at)
```

리프레시 토큰은 원문 대신 해시만 저장한다. 다중 인스턴스 운영이나 빠른 만료 조회가 필요해지면 Redis로 이전할 수 있지만, Redis 도입 자체의 근거로 삼지는 않는다. 기기별 세션 제어를 제공하지 않으므로 기기 식별자는 저장하지 않는다.

### 2.3 `member_preferences`

회원이 실제로 선택한 기본 취향의 Enum 코드를 행 단위로 저장한다. 취향 선택지는 관리자 운영 데이터가 아니므로 별도 옵션·그룹 테이블을 만들지 않는다.

| 컬럼 | 타입 | NULL | 키/기본값 | 설명 |
| --- | --- | --- | --- | --- |
| `id` | BIGINT | N | PK, AUTO_INCREMENT | 회원 취향 선택 식별자 |
| `member_id` | BIGINT | N | FK | 회원 식별자 |
| `preference_type` | VARCHAR(20) | N |  | `THEME`, `DETAIL`, `TRAVEL_STYLE` |
| `preference_code` | VARCHAR(50) | N |  | 백엔드 Enum으로 정의한 취향 코드 |

제약 및 규칙:

```text
UNIQUE (member_id, preference_type, preference_code)
FK (member_id) REFERENCES members(id)
INDEX (preference_type, preference_code)
```

- 대분류는 최소 1개, 최대 3개까지 선택할 수 있다.
- 중분류 코드는 연결된 대분류 코드가 선택된 경우에만 저장한다.
- 대분류를 해제할 때 소속 중분류 선택도 같은 트랜잭션에서 삭제한다.
- 허용 코드, 대분류·중분류 관계와 화면 표시 순서는 백엔드 Enum·코드 설정으로 관리한다.

예:

| member_id | preference_type | preference_code |
| ---: | --- | --- |
| 1 | `THEME` | `HEALING` |
| 1 | `THEME` | `CULTURE` |
| 1 | `DETAIL` | `QUIET_PLACE` |
| 1 | `TRAVEL_STYLE` | `RELAXED` |

트레이드오프: 옵션을 추가·삭제하거나 계층을 변경하려면 프론트엔드와 백엔드 코드를 함께 배포해야 하며, DB FK만으로 유효한 취향 코드와 상하위 관계를 검증할 수 없다.

### 2.4 `notifications`

회원에게 아직 읽지 않은 인앱 알림을 관리한다. 현재 정책에서는 알림을 읽으면 행을 삭제한다.

| 컬럼 | 타입 | NULL | 키/기본값 | 설명 |
| --- | --- | --- | --- | --- |
| `id` | BIGINT | N | PK, AUTO_INCREMENT | 알림 식별자 |
| `recipient_member_id` | BIGINT | N | FK | 수신 회원 |
| `type` | VARCHAR(30) | N |  | 알림 유형 |
| `title` | VARCHAR(100) | N |  | 제목 |
| `body` | VARCHAR(500) | N |  | 본문 |
| `reference_type` | VARCHAR(30) | Y |  | 이동 대상 종류 |
| `reference_id` | VARCHAR(50) | Y |  | 이동 대상 식별자 |
| `created_at` | DATETIME(6) | N |  | 생성 시각 |

제약 및 인덱스:

```text
FK (recipient_member_id) REFERENCES members(id)
CHECK ((reference_type IS NULL) = (reference_id IS NULL))
INDEX (recipient_member_id, created_at DESC)
```

`reference_type`, `reference_id`는 복합 PK가 아니라 화면 이동을 위한 다형 참조값이다.

트레이드오프: 읽은 알림을 물리 삭제하므로 읽은 시각과 알림 이력을 복원할 수 없다. 읽은 알림 보관 요구가 생기면 `read_at`을 추가하고 보존 정책을 변경한다. 메시지 큐를 사용하지 않는 MVP에서는 범용 `source_event_id`를 두지 않고, 알림을 발생시키는 원본 업무의 상태 전이와 동일 트랜잭션 내 생성으로 중복을 통제한다.

| `id` | BIGINT | N | PK, AUTO_INCREMENT | 지역 식별자 |

### 3.2 `tourism_contents`

장소·행사·문화유산·명소의 공통 원본 정보를 관리한다.

| 컬럼 | 타입 | NULL | 키/기본값 | 설명 |
| --- | --- | --- | --- | --- |
| `id` | BIGINT | N | PK, AUTO_INCREMENT | 콘텐츠 식별자 |
| `category` | VARCHAR(30) | N |  | 콘텐츠당 하나의 분류: `EVENT`, `CULTURAL_HERITAGE`, `ATTRACTION` |
| `source_provider` | VARCHAR(30) | N |  | 관광공사 등 데이터를 제공한 외부 시스템 |
| `source_content_id` | VARCHAR(100) | N |  | 외부 시스템이 부여한 콘텐츠 식별자 |
| `title` | VARCHAR(200) | N |  | 콘텐츠명 |
| `description` | TEXT | Y |  | 설명 |
| `region_id` | BIGINT | N | FK | 행정구역 식별자 |
| `address` | VARCHAR(500) | Y |  | 주소 |
| `location` | POINT SRID 4326 | N | SPATIAL INDEX | 반경·영역 조회용 경도·위도 좌표 |
| `phone` | VARCHAR(50) | Y |  | 전화번호 |
| `homepage_url` | VARCHAR(2048) | Y |  | 홈페이지 URL |
| `thumbnail_url` | VARCHAR(2048) | Y |  | 대표 이미지 URL |
| `status` | VARCHAR(20) | N | `'ACTIVE'` | 노출 상태 `ACTIVE`, `INACTIVE` |
| `deleted_at` | DATETIME(6) | Y |  | 소프트 삭제 시각 |
| `created_at` | DATETIME(6) | N |  | 생성 시각 |
| `updated_at` | DATETIME(6) | N |  | 수정 시각 |

제약 및 인덱스:

```text
UNIQUE (source_provider, source_content_id)
INDEX (region_id, category)
SPATIAL INDEX (location)
```

URL은 서비스 입력 계약으로 최대 2,048자를 허용한다. 외부 데이터에서 사라져 일시적으로 노출하지 않는 콘텐츠는 `status=INACTIVE`, 관리자 또는 정책상 삭제는 `deleted_at`으로 구분한다. 비활성·삭제 콘텐츠는 검색·신규 가이드북 후보·신규 랭킹에서 제외하되 기존 가이드북과 평가 참조는 유지한다. 좌표는 `POINT SRID 4326 NOT NULL`로 저장해 MySQL 공간 함수와 SPATIAL INDEX를 사용한다. 원본 좌표가 없으면 지오코딩 후 활성화하거나 수집·노출 대상에서 제외한다.

## 4. DOM-03 가이드북

### 4.1 `generation_jobs`

최초 생성·재생성 요청, 생성 입력 스냅샷과 비동기 작업 상태를 관리한다. 백엔드가 작업 ID를 생성하고 같은 ID를 AI 요청에 전달한다.

| 컬럼 | 타입 | NULL | 키/기본값 | 설명 |
| --- | --- | --- | --- | --- |
| `id` | VARCHAR(50) | N | PK | 작업 ID, 예: `job_...` |
| `member_id` | BIGINT | N | FK | 요청 회원 |
| `guidebook_id` | VARCHAR(50) | Y | FK | 생성 결과 또는 재생성 대상 가이드북 |
| `job_type` | VARCHAR(20) | N |  | `INITIAL`, `REGENERATION` |
| `status` | VARCHAR(20) | N | `'PENDING'` | `PENDING`, `PROCESSING`, `COMPLETED`, `FAILED` |
| `request_payload` | JSON | N |  | 지역·기간·동행·인원·취향 등 요청 스냅샷. 재생성은 공백이 아닌 `title`과 자연어 `feedback`을 모두 포함 |
| `error_payload` | JSON | Y |  | 최종 실패 코드와 메시지 |
| `attempt_count` | SMALLINT | N | `0` | AI 호출 시도 횟수 |
| `idempotency_key` | VARCHAR(100) | N | UNIQUE | 중복 생성 요청 방지 키 |
| `started_at` | DATETIME(6) | Y |  | 처리 시작 시각 |
| `completed_at` | DATETIME(6) | Y |  | 성공 또는 최종 실패 시각 |
| `created_at` | DATETIME(6) | N |  | 생성 시각 |
| `updated_at` | DATETIME(6) | N |  | 수정 시각 |
| `active_member_id` | BIGINT | Y | GENERATED | `PENDING`·`PROCESSING`일 때만 `member_id`, 그 외 `NULL` |

제약 및 규칙:

```text
UNIQUE (idempotency_key)
CHECK (attempt_count BETWEEN 0 AND 3)
INDEX (member_id, status, created_at)
INDEX (guidebook_id, created_at)
UNIQUE (active_member_id)
```

- 최초 생성 처리 중에는 `guidebook_id`가 `NULL`이며 성공 트랜잭션에서 생성된 ID를 기록한다.
- 재생성은 요청 시점부터 기존 `guidebook_id`를 참조한다.
- 최초 생성 실패 시 가이드북을 만들지 않는다. 재생성 실패 시 기존 가이드북을 변경하지 않는다.

### 4.2 `guidebooks`

## 5. DOM-04 평가·랭킹

### 5.1 `guidebook_evaluations`

가이드북 단위의 평가 안내와 최종 제출 상태를 관리한다. 작성 중 별점은 프론트엔드에서 관리하고 최종 제출 시 한 번에 서버로 전송한다. `다음에 하기`는 평가 권리 포기가 아니라 자동 모달 재노출 중단 시각으로 표현한다.

| 컬럼 | 타입 | NULL | 키/기본값 | 설명 |
| --- | --- | --- | --- | --- |
| `id` | BIGINT | N | PK, AUTO_INCREMENT | 평가 진행 식별자 |
| `guidebook_id` | VARCHAR(50) | N | FK | 평가 대상 가이드북 |
| `member_id` | BIGINT | N | FK | 평가 회원 |
| `status` | VARCHAR(20) | N | `'PENDING'` | `PENDING`, `SUBMITTED` |
| `prompt_dismissed_at` | DATETIME(6) | Y |  | `다음에 하기` 선택 시각 |
| `submitted_at` | DATETIME(6) | Y |  | 최종 제출 시각 |
| `created_at` | DATETIME(6) | N |  | 생성 시각 |
| `updated_at` | DATETIME(6) | N |  | 수정 시각 |

```text
UNIQUE (guidebook_id, member_id)
INDEX (member_id, status)
```

트레이드오프: 제출 전 입력값을 서버에 저장하지 않으므로 앱이 종료되면 작성 중 평가가 유실될 수 있다. 초안 복구가 필요해지면 장소별 임시 평가 저장 API와 상태를 추가한다.

### 5.2 `place_ratings`

회원이 관광 콘텐츠에 부여한 현재 별점을 관리한다. 요청에 따라 이번 버전에서는 평가를 특정 여행 일정 항목과 연결하지 않는다.

| 컬럼 | 타입 | NULL | 키/기본값 | 설명 |
| --- | --- | --- | --- | --- |
| `id` | BIGINT | N | PK, AUTO_INCREMENT | 별점 식별자 |
| `member_id` | BIGINT | N | FK | 평가 회원 |
| `tourism_content_id` | BIGINT | N | FK | 평가 콘텐츠 |
| `score` | SMALLINT | Y |  | 0~5 정수점, `NULL`은 건너뛰기 |
| `created_at` | DATETIME(6) | N |  | 생성 시각 |
| `updated_at` | DATETIME(6) | N |  | 수정 시각 |

```text
UNIQUE (member_id, tourism_content_id)
CHECK (score IS NULL OR score BETWEEN 0 AND 5)
INDEX (tourism_content_id, created_at)
```

트레이드오프: 같은 회원이 같은 장소를 여러 여행에서 평가한 이력을 구분할 수 없다. 여행별 평가 이력이 필요해지면 `guidebook_evaluation_id` 또는 `itinerary_item_id`를 추가하고 유일 제약을 변경한다.

### 5.3 `ranking_snapshots`

일간·주간·월간 랭킹 집계 단위와 집계 메타데이터를 관리한다.

| 컬럼 | 타입 | NULL | 키/기본값 | 설명 |
| --- | --- | --- | --- | --- |
| `id` | BIGINT | N | PK, AUTO_INCREMENT | 랭킹 스냅샷 식별자 |
| `period_type` | VARCHAR(20) | N |  | `DAILY`, `WEEKLY`, `MONTHLY` |
| `period_start` | DATE | N |  | 집계 시작일 |
| `period_end` | DATE | N |  | 집계 종료일 |
| `region_id` | BIGINT | Y | FK | 지역 랭킹의 지역, 전체는 `NULL` |
| `scope_region_id` | BIGINT | N | GENERATED | 전국은 `0`, 지역은 `region_id` |
| `calculated_at` | DATETIME(6) | N |  | 집계 완료 시각 |


`region_id IS NULL`은 전국 랭킹을 의미한다. MySQL UNIQUE의 복수 `NULL` 허용을 피하기 위해 `scope_region_id = COALESCE(region_id, 0)` 생성 컬럼을 사용한다. 실제 지역 ID는 1 이상으로 제한한다. 계산식의 C·m·버전은 MVP에서 애플리케이션 설정으로 관리한다.

## 6. DOM-05 생성권·결제

### 6.1 `credit_wallets`

회원별 생성권 잔액을 관리한다. 한 회원의 진행 중 생성 작업은 하나만 허용하며 예약 여부는 `generation_jobs`에서 판단한다.

| 컬럼 | 타입 | NULL | 키/기본값 | 설명 |
| --- | --- | --- | --- | --- |
| `id` | BIGINT | N | PK, AUTO_INCREMENT | 지갑 식별자 |
| `member_id` | BIGINT | N | FK, UNIQUE | 회원 식별자 |
| `credit_balance` | INT | N | `0` | 보유 생성권 총수량 |
| `created_at` | DATETIME(6) | N |  | 생성 시각 |
| `updated_at` | DATETIME(6) | N |  | 수정 시각 |

```text
UNIQUE (member_id)
CHECK (credit_balance >= 0)
```

생성 요청 접수 시 지갑 행을 잠그고 잔액이 1개 이상인지 확인한 뒤 진행 중 생성 작업을 만든다. 생성 성공 트랜잭션에서 잔액을 1개 차감하고, 실패하면 잔액을 변경하지 않는다. 진행 중 작업이 있는 동안 회수·관리자 조정 등 다른 감소 연산은 성공 차감에 필요한 마지막 1개를 침범하지 않아야 한다.

### 6.2 `credit_transactions`

생성권 무료 지급·구매 지급·사용·회수·조정 이력을 불변 원장으로 보존한다.

| 컬럼 | 타입 | NULL | 키/기본값 | 설명 |
| --- | --- | --- | --- | --- |
| `id` | BIGINT | N | PK, AUTO_INCREMENT | 원장 식별자 |
| `wallet_id` | BIGINT | N | FK | 생성권 지갑 |
| `type` | VARCHAR(30) | N |  | `FREE_GRANT`, `PURCHASE_GRANT`, `CONSUME`, `REVOKE`, `ADJUSTMENT` |
| `credit_delta` | INT | N |  | 총잔액 증감량 |
| `credit_balance_after` | INT | N |  | 처리 후 총잔액 |

```text
INDEX (order_id, created_at)
```

`pg_transaction_id`가 승인 전까지 `NULL`일 수 있으므로, PG 웹훅 멱등 처리는 값이 존재할 때의 유일 제약과 별도 웹훅 처리 키를 함께 사용한다.

## 8. 원자적 처리 범위

### 8.1 최초 가이드북 생성 성공

하나의 트랜잭션에서 다음을 수행한다.

1. 백엔드가 `guidebooks.id`를 생성한다.
2. `guidebooks`, `itinerary_days`, `itinerary_items`를 저장한다.
3. `generation_jobs.guidebook_id`를 기록하고 상태를 `COMPLETED`로 변경한다.
4. 생성권 1개를 차감하고 `CONSUME` 원장을 기록한다.

하나라도 실패하면 전체를 롤백한다.

### 8.2 가이드북 재생성 성공

1. 기존 `guidebooks` 행을 갱신하고 `version`을 증가시킨다.
2. 기존 일정 일자·항목을 새 결과로 교체한다.
3. 생성 작업을 `COMPLETED`로 변경한다.
4. 생성권 1개를 차감하고 `CONSUME` 원장을 기록한다.

저장에 실패하면 기존 가이드북과 일정은 그대로 유지한다.

### 8.3 생성 실패

1. 최종 실패 정보를 `generation_jobs.error_payload`에 기록한다.
2. 생성 작업을 `FAILED`로 확정한다.

생성 요청 단계에서는 잔액을 변경하지 않았으므로 실패 보상 원장은 만들지 않는다.

## 9. 삭제·보존 정책 초안

- 회원 탈퇴 시 활성 세션을 즉시 폐기한다.
- 가이드북 삭제는 `deleted_at`을 기록하는 소프트 삭제로 처리하고 목록·상세·공유 링크 접근을 차단한다.
- 삭제된 원본의 이미 가져간 독립 복사본, 생성 작업·원장, 제출된 평가는 유지한다.
- `itinerary_days` 삭제 시 소속 `itinerary_items`는 함께 삭제할 수 있다.
- 결제, 생성권 원장과 PG 식별자는 법적·운영 보존 정책에 따라 회원 데이터와 분리하여 보존한다.
- 외부 관광 콘텐츠가 비활성화되어도 기존 가이드북의 `place_snapshot`은 유지한다.

## 10. 현재 결정과 보류 사항

### 확정

- 작업 ID와 가이드북 ID는 백엔드가 생성한다.
- 백엔드는 작업 ID를 AI 요청에 전달하고, AI가 반환한 최종 JSON을 검증한 후 가이드북을 저장한다.
- 최초 생성 성공 전에는 가이드북 행을 만들지 않는다.
- 재생성은 기존 가이드북을 갱신하며 실패 시 기존 결과를 보존한다.
- 알림 이동 대상 컬럼은 복합 PK가 아니며, 현재 역방향 조회 요구가 없어 별도 인덱스를 두지 않는다.
- 취향 선택지는 관리자 운영 테이블을 두지 않고 Enum으로 관리하며 회원이 선택한 코드만 `member_preferences`에 저장한다.
- 이용약관·개인정보 처리방침은 정적 콘텐츠로 제공하며 `members`에 동의 여부를 추가하거나 별도 동의 이력 테이블을 만들지 않는다.
- 주문 하나에 여러 결제 시도가 가능하므로 `payment_attempts`를 사용한다.
- 생성권 예약 여부는 진행 중 생성 작업에서 파생하며, 생성 성공 시에만 잔액 차감 원장을 기록한다.
- 별점은 0~5 정수만 허용하므로 `SMALLINT`로 저장한다.
- 외부 URL은 `TEXT`로 저장하고 API 계층에서 입력 상한을 검증한다.
- 가이드북은 소프트 삭제하며, 가져오기 중복은 링크가 아닌 최초 원본과 회원 조합으로 판단한다.
- 관광 콘텐츠는 외부 원본에서 사라져도 물리 삭제하지 않고 비활성화한다.
- 환불은 MVP 범위에서 제외하고 환불 상태·원장 유형·테이블을 초기 스키마에 두지 않는다.

### 보류 또는 트레이드오프

- `place_ratings`는 현재 여행·일정 항목과 연결하지 않는다. 반복 방문 평가 이력이 필요해지면 스키마를 확장한다.
- 회원에게 여러 OAuth 계정을 연결하는 기능이 생기면 `social_accounts`를 분리한다.
- 취향 옵션의 운영 중 추가·비활성화·다국어 관리가 필요해지면 `preference_groups`, `preference_options`를 도입한다.
- 공유 링크의 기본 만료 기간과 재발급 정책은 기획 확정이 필요하다.
- 소프트 삭제된 가이드북의 물리 삭제·개인정보 제거 시점과 결제·원장 보존 기간은 별도 확정이 필요하다.
