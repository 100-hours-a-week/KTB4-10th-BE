# REST API 예시 및 Best Practice

> 2026-09-04 · 현재 요구사항/테이블/ERDCloud SQL 및 V3 API 명세서 기준 학습 노트
> 실제 호출 계약은 [V3 API 명세서](./V3%20API%20명세서.md), 엔드포인트별 FR/BR 연결과 선택 이유는 [API 설계 근거](./API%20설계%20근거.md)를 확인한다.
> 아래에서 ‘설계안’인 정책은 팀이 확정한 요구사항과 구분한다. HTTP 개념을 외우는 것보다 서비스 사례와 실패 상황까지 설명하는 것이 목적이다.

## 1. API 명세서와 설계 근거를 왜 분리하는가?

명세서는 프론트엔드와 백엔드가 지켜야 하는 계약이다. Method·URL·인증·Body·필드 타입·필수 여부·제약·응답·오류가 있어야 한다. 이 정보는 엑셀의 설명 칼럼에도 남긴다.

근거 문서는 “왜 이 메서드인가?”, “어느 요구사항인가?”, “어떤 대안을 포기했나?”를 설명한다. 이를 API ID로 연결하면 표를 짧게 유지하면서 선택의 이유도 추적할 수 있다. 별도 근거 문서를 만드는 것은 검토를 생략하는 것이 아니라 계약과 학습 자료의 역할을 나누는 것이다.

## 2. REST, 리소스, HTTP 메서드

REST는 URL 이름 규칙만을 뜻하지 않는다. 클라이언트와 서버를 분리하고, 요청마다 필요한 인증·처리 정보를 전달하며, 일관된 인터페이스로 리소스 표현을 다루는 설계 스타일이다. 서버에 DB나 로그인 세션이 있다고 해서 무조건 무상태 제약 위반은 아니다. 이전 화면 이동 순서를 서버가 기억해야만 다음 요청을 처리할 수 있는 설계를 피한다.

| 메서드 | 이 프로젝트 예시 | 의도 |
|---|---|---|
| GET | `/contents`, `/rankings` | 조회. 사용자가 요구한 업무 상태를 바꾸지 않음 |
| POST | `/guidebook-generations` | 서버가 새 생성 작업을 만들도록 요청 |
| PUT | `/members/me/preferences` | 지정 리소스의 전체 선택 집합 교체 |
| PUT | `/members/me/favorites/101` | 알고 있는 URI의 관계가 존재하도록 설정 |
| PATCH | `/members/me/settings` | 보내온 설정만 변경 |
| DELETE | `/notifications/301` | 해당 알림 제거 |

HTTP의 안전성과 멱등성, 메서드 의미는 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2), PATCH의 부분 변경 의미는 [RFC 5789](https://www.rfc-editor.org/rfc/rfc5789.html) 기준이다.

### Q. “POST 대신 PUT으로 생성하면 안 되나요?”

가능한 경우가 있다. 회원은 관심 장소의 콘텐츠 ID를 알고 있으므로 `/members/me/favorites/{content_id}`라는 대상 URI를 지정할 수 있다. 반면 가이드북 생성은 서버가 새로운 job_id를 정하므로 POST가 자연스럽다. ‘생성은 무조건 POST’라고 외우지 않는다.

**꼬리 질문: DB에 대리키가 생기면 POST로 바꿔야 하나요?**

아니다. 현재 favorite_contents의 PK는 id이고 회원·콘텐츠 조합은 UNIQUE다. API가 식별하는 대상은 해당 관계이므로 URL을 유지할 수 있다. DB의 물리 키와 외부 리소스 식별 방식은 반드시 같지 않다.

### Q. “설정 PATCH에서 누락과 false는 어떻게 다른가요?”

```json
{
  "push_enabled": false
}
```

푸시만 끄고 언어는 유지한다. `false`는 명시적 변경값이며, 필드 누락은 유지다. null은 해당 API에서 허용하지 않는다. 빈 객체도 변경 내용이 없으므로 400으로 처리한다. PATCH 자체가 언제나 멱등적인 것은 아니지만 이처럼 값을 대입하는 계약은 반복해도 같은 설정이 된다.

## 3. 멱등성과 동시성은 같은 말인가?

멱등성은 동일 요청을 반복했을 때 의도된 서버 효과가 한 번 수행한 것과 같다는 뜻이다. 응답 상태 코드와 본문까지 항상 똑같다는 뜻은 아니다. 동시성 제어는 여러 요청이 겹쳐도 데이터 불변식이 유지되게 하는 수단이다.

관심 장소 PUT은 복합 UNIQUE로 중복 관계를 방지한다. 애플리케이션에서 SELECT로 중복 확인만 하면 두 요청이 동시에 “없음”을 보고 INSERT할 수 있다. DB 제약 위반을 정상 중복 요청으로 변환하되, 전혀 다른 오류까지 성공으로 숨기면 안 된다.

POST 생성 작업은 `Idempotency-Key`와 generation_jobs 저장값으로 중복 접수를 통제한다. 같은 키라도 다른 회원·다른 Body면 409다. 키가 같다는 이유로 다른 회원의 결과를 반환하면 보안 문제가 된다.

### Q. “모든 POST에 Idempotency-Key만 넣으면 되나요?”

아니다. 서버가 키·요청 비교값·작업 결과를 저장하고 원자적으로 처리해야 한다. 현재 필수 키 대상은 최초 생성, 재생성, 주문 생성이다. 공유 링크나 결제 시도에는 요청 키 컬럼이 없어 동일 보장을 적지 않았다. 가져오기는 회원+최초 원본의 유일성으로 중복 복사를 막는다.

**꼬리 질문: 생성 도중 응답이 끊기면요?**

클라이언트는 같은 키로 접수를 재시도한다. 서버는 기존 작업을 반환하고 AI를 새 작업으로 중복 실행하지 않는다. 새로운 사용자 재생성 의도에는 새 키가 필요하다. 키 확인은 현재 취향으로 입력 스냅샷을 새로 만드는 것보다 먼저 해야 한다.

## 4. 200, 201, 202, 204의 차이

| 코드 | 의미 | 현재 사례 |
|---|---|---|
| 200 | 요청 처리 결과 반환 | 조회, 기존 가져오기 반환, 동기 PDF |
| 201 | 리소스 생성 완료 | 주문, 공유 링크, 첫 가져오기 |
| 202 | 처리를 접수했으나 아직 완료되지 않음 | AI 생성/재생성 |
| 204 | 성공, 응답 본문 없음 | 관심 장소 해제, 알림 삭제, 탈퇴 |

202는 AI 생성 성공이 아니다. 이후 상태 조회에서 FAILED가 될 수 있다. 204에 `{message: ...}`를 함께 보내지 않는다. 첫 가져오기 201, 중복 가져오기 200이어도 복사본은 하나이므로 멱등한 결과다. [HTTP 상태 코드 의미](https://www.rfc-editor.org/rfc/rfc9110.html#section-15)

### Q. “왜 PDF는 202가 아니죠?”

최신 요구사항이 MVP에서 동기 생성으로 정해졌다. POST `/guidebooks/{id}/exports`는 `{ "format": "PDF" }`를 받고 성공하면 200과 PDF 바이너리를 반환한다. JSON 안에 PDF 파일 내용을 넣거나 없는 export_id를 반환하지 않는다. 실패는 JSON 오류이며 원본 가이드북은 유지한다.

**꼬리 질문: 느려지면요?**

응답 시간·메모리·동시 처리량을 측정해 임계값을 정한다. 비동기로 바꿀 때는 작업 ID·상태·소유권·만료·재시도 저장과 상태 조회 API를 함께 설계해야 한다. 상태 코드만 202로 바꾸는 것으로 충분하지 않다.

## 5. 요청·응답을 구체적으로 읽기

```http
POST /api/v1/guidebook-generations
Authorization: Bearer access_token
Content-Type: application/json
Idempotency-Key: request_unique_key
```

```json
{
  "region_code": "47",
  "start_date": "2026-10-12",
  "end_date": "2026-10-14",
  "companion": "FRIEND",
  "people_count": 2
}
```

```json
{
  "message": "guidebook_generation_accepted",
  "data": {
    "job_id": "job_example",
    "job_type": "INITIAL",
    "status": "PENDING",
    "guidebook_id": null
  }
}
```

지역은 17개 광역 시·도의 행정코드다. 기간은 양끝 포함 1~7일이다. 취향은 서버가 현재 기본 취향을 읽어 요청 스냅샷에 보존하므로 Body로 별도 취향을 받지 않는다. companion 전체 Enum과 인원 상한은 아직 팀 합의가 필요하다.

`job_id`는 생성 작업이고 `guidebook_id`는 결과 가이드북이다. 최초 생성 중에는 가이드북이 없어 null이다. 재생성은 기존 guidebook_id를 참조하는 새 job_id이며 성공하면 같은 가이드북의 version을 증가시킨다.

### Q. “생성권은 화면에 진입할 때 차감하나요?”

현재 서버 요구사항은 성공한 결과 저장 시 차감이다. 작업 접수 시에는 지갑 잠금과 활성 작업으로 생성권 하나를 논리적으로 확보한다. 성공 시 가이드북·일정·COMPLETED·지갑 -1·CONSUME를 함께 커밋한다. 실패 시 잔액을 변경하지 않는다. 프론트 화면 진입 이벤트는 차감의 신뢰 근거가 아니다.

**꼬리 질문: AI 호출 중 DB 트랜잭션을 열어두나요?**

아니다. 접수 트랜잭션을 끝낸 다음 AI를 호출한다. 오래 잠금을 보유하면 다른 요청을 막는다. 대신 완료 시 작업 상태·멱등 키를 다시 검사하고 결과 반영 트랜잭션을 실행한다.

## 6. 인증과 인가

인증은 “누구인가”, 인가는 “이 작업을 해도 되는가”다. 유효 토큰만 확인하고 `/guidebooks/{id}`를 반환하면 ID를 아는 타인의 가이드북을 볼 수 있다. 조회·편집·삭제·PDF 모두 소유권을 검사한다.

회원 ID를 Body에서 받지 않고 인증 세션에서 결정한다. 추측하기 어려운 gb/job ID도 인가를 대체하지 않는다. 탈퇴 시 세션을 폐기하고, 삭제된 회원의 기존 액세스 토큰이 남아 있더라도 보호 API를 사용할 수 없도록 검증해야 한다.

OAuth 지원 범위는 **V1 KAKAO만, V2 이상(V3 포함) KAKAO·GOOGLE 모두**로 확정됐다. 이는 서비스 출시 단계이며 /api/v1이라는 URL 버전과 별개다. 회원당 하나의 소셜 계정 연결을 유지하므로 두 공급자를 지원한다고 social_accounts 테이블이 반드시 필요한 것은 아니다. 공급자+subject로 식별하고 이메일만으로 자동 병합하지 않는다.

OAuth 동의는 우리 서비스의 별도 동의 이력 저장과 동일하지 않다. 현재 서비스는 자체 동의 API를 제공하지 않고 정책을 정적 안내로 제공한다.

### Q. “state/PKCE에서 무엇을 확정해야 하나요?”

공급자 지원이 아니라 로그인 보안 흐름의 책임 분담이다.

- 로그인 시작과 콜백을 프론트/백엔드 중 누가 처리할지.
- state를 요청 전에 누가 만들고, 원래 브라우저·공급자와 어떻게 연결하며, 어디에 얼마나 보관하고 한 번만 소비할지.
- 공급자/SDK별 PKCE S256 지원과 code_verifier 생성·보관·토큰 교환 담당.
- 리다이렉트 주소·OIDC 검증·실패 처리·쿠키/Body 전달·서비스 토큰 TTL과 회전.

state는 ‘내가 시작한 로그인 응답인가’를 연결하고, PKCE는 ‘이 코드를 교환하는 쪽이 최초 요청의 verifier를 아는가’를 확인한다. challenge는 인가 요청에 보내고 verifier는 토큰 교환에 사용한다. 둘을 같은 기능으로 설명하지 않는다. [PKCE 규격](https://www.rfc-editor.org/rfc/rfc7636.html)

**꼬리 질문: state 필드를 Body에 추가하면 끝인가요?**

아니다. 요청 전에 저장한 값과 브라우저 결속을 확인해야 한다. 프론트가 보낸 state_valid=true는 증거가 아니다. 백엔드 콜백 방식이면 브라우저가 현재 POST Body에 state/verifier를 직접 보낼 필요가 없을 수 있으므로 먼저 흐름을 정한다. 상세 결정표는 V3 API 명세서의 API-MEM-01에 있다.

**꼬리 질문: auth_sessions에 저장하면 되나요?**

현재 auth_sessions는 로그인 후 refresh 세션이며 가입 전 임시 인가 요청 저장소가 아니다. 단기 저장 위치·TTL·다중 서버·일회 소비를 별도 설계하고 실패 시 서비스 토큰을 발급하지 않는다.

## 7. 오류와 빈 결과

```json
{
  "message": "invalid_request",
  "data": null,
  "error": {
    "code": "COMMON_VALIDATION_ERROR",
    "details": [{"field": "q", "reason": "max_length_10"}],
    "trace_id": "req_example"
  }
}
```

400은 형식·타입·범위 오류, 401은 인증, 403은 권한, 404는 미존재/삭제, 409는 현재 상태나 멱등성 충돌, 422는 유효한 형식이지만 업무 조건 불충족에 사용한다. 우리 프로젝트의 분류 규약이며 경계 사례도 팀에서 통일해야 한다.

검색 결과가 없는 것은 정상 200과 빈 items다. 랭킹도 유효 요청에 데이터가 없으면 빈 결과를 제공한다. 생성 접수 후 AI 실패는 이미 반환한 202를 나중에 500으로 바꿀 수 없으므로 작업 상태 FAILED와 안전한 오류 코드로 전달한다.

## 8. 페이지네이션·정렬·필터

콘텐츠는 번호 페이지 UI에 맞춰 page/size를 사용한다. 검색어·지역·월·카테고리 조건은 AND다. q 최대10자, 지역 조건 생략은 전체다. month=YYYY-MM은 계약 제안이며 연도 제한과 상시 장소 혼합 처리는 미확정이다. 단일 category는 EVENT/CULTURAL_HERITAGE/ATTRACTION이고, 취향 THEME/DETAIL/TRAVEL_STYLE과 다른 개념이다.

가이드북·알림·원장은 최신순 커서를 사용한다. created_at만 커서로 쓰면 같은 시각의 항목을 놓칠 수 있어 id를 보조 정렬로 묶는다. 같은 필터·정렬에서 발급한 커서만 유효하도록 검증한다. 커서에 담긴 member_id를 신뢰해서 소유권 조건을 생략하지 않는다.

### Q. “커서는 언제나 offset보다 빠르죠?”

적절한 인덱스와 범위 조건으로 구현하면 깊은 페이지에서 유리할 수 있다. 하지만 임의 페이지 이동이 어렵고 정렬 키 변경에도 주의해야 한다. 작은 데이터에서는 차이가 작을 수 있다. 데이터 규모·실제 SQL·실행 계획으로 확인한다.

**꼬리 질문: ERD의 복합 인덱스가 이 API를 다 해결하나요?**

아니다. WHERE·ORDER BY·LIMIT을 실제로 구성해서 확인해야 한다. `(region_id,category)` 인덱스는 `%검색어%` 부분 검색과 제목 정렬까지 자동 해결하지 않는다. 지도 좌표는 공간 인덱스가 있더라도 사용하는 함수와 조건에 따라 실행 계획이 달라진다.

## 9. API DTO와 MySQL 저장 모델

| DB/내부 표현 | API 표현 | 이유 |
|---|---|---|
| location POINT SRID4326 | latitude, longitude Number | 프론트 지도에서 명시적 좌표로 사용 |
| member_preferences 행 | selections 배열 | 사용자의 전체 선택 집합 |
| favorite_contents.id + 복합 UNIQUE | favorites/{content_id} | 회원이 아는 콘텐츠로 관계 식별 |
| DATETIME(6) UTC | ISO8601 오프셋 시각 | 타임존 없는 문자열 오해 방지 |
| BIGINT 식별자 | 10진 문자열(설계안) | JavaScript 안전 정수 범위 초과 방지 |
| generated active_member_id | active_job_id, can_generate 파생 | DB 제약 구현 컬럼 자체는 노출 불필요 |

MySQL 지리 좌표는 `ST_Longitude`와 `ST_Latitude`로 읽는다. X/Y를 무조건 경도/위도로 해석하지 않고 실제 삽입·조회 축 순서를 테스트한다. [MySQL Point Property Functions](https://dev.mysql.com/doc/refman/8.4/en/gis-point-property-functions.html)

URL의 2048자는 이 프로젝트의 컬럼 한도이지 인터넷 전체의 보편적인 최대 URL 길이가 아니다. API 외부 입력과 관광 데이터 수집에서도 초과값을 검증하고 임의 절단하지 않는다. 실제 배포 MySQL 버전에 맞춰 공간 함수·제약 동작을 확인해야 한다.

## 10. 평가 초안과 최종 평가

PENDING은 평가가 아직 제출되지 않았다는 상태이지 장소별 입력값이 아니다. 초안은 프론트가 관리하고 최종 제출에서 ratings 배열을 보낸다. 앱 종료 복구가 필요하면 로컬 저장 정책을 정해야 하며 현재 서버가 초안을 보관한다고 설명하면 안 된다.

```json
{
  "ratings": [
    {"content_id": "101", "score": 0},
    {"content_id": "102", "score": null}
  ]
}
```

0은 유효 점수이고 null은 건너뛰기다. score가 빠진 것은 null과 다르다. 최종값은 회원·콘텐츠당 하나라 다른 여행에서 재평가하면 기존 값을 어떻게 처리할지 정해야 한다. 부분 제출과 제출 후 수정도 미확정이다.

### Q. “제출 성공이면 랭킹도 즉시 바뀌나요?”

아니다. 최신 요구사항은 커밋 후 변경 지역과 전국을 비동기 재집계한다. 응답은 평가 제출 완료만 보장한다. 랭킹은 calculated_at과 함께 이전 완료 결과를 보여줄 수 있다. 스냅샷과 entries는 한 트랜잭션으로 교체해 절반만 갱신된 순위를 노출하지 않는다.

**꼬리 질문: updated_at만 보면 과거 랭킹도 재현되나요?**

아니다. updated_at은 변경 탐지에 쓰고 기간 귀속 규칙은 따로 정한다. 현재 값 덮어쓰기와 공식 설정 변경 후 과거 결과 완전 재현은 별도 이력 없이는 어렵고, 요구사항도 완전 재현을 MVP에서 제외했다.

## 11. 삭제·공유·캐시에서 놓치기 쉬운 점

- HTTP DELETE가 SQL DELETE를 강제하지 않는다. 가이드북은 deleted_at으로 숨기며 알림은 실제 행 삭제다.
- 가이드북 삭제 시 공유 미리보기도 차단한다. 이미 가져간 독립 복사본은 유지한다.
- 가져오기 중복 기준은 링크 ID가 아니라 최초 원본 ID다. 다른 링크를 썼다고 새 복사본을 만들면 안 된다.
- version은 재생성 성공 때 증가하는 값이다. 사용자에게 제목이나 일정을 직접 수정하는 API는 제공하지 않는다.
- 회원별 응답을 공용 캐시에 저장하지 않는다. HTML은 저장값이라고 신뢰하지 말고 정제·격리해 표시한다.
- 알림 전체 삭제를 재시도하면 그 사이 새로 생긴 알림까지 대상이 될 수 있다. 개별 삭제와 똑같은 재시도 UX라고 가정하지 않는다.

## 12. 결제 API는 왜 일부 보류인가?

PG를 정하지 않은 상태에서는 서명 헤더, 승인 확인, 웹훅 원문 필드와 응답 조건을 확정할 수 없다. 명세의 PAY-06/07은 경계만 잡은 보류 항목이다. 가짜 공통 JSON 예제를 실제 PG 계약처럼 제공하지 않는다.

공통 원칙은 서버 가격으로 주문을 생성하고, 검증된 PG 승인만 PAID 및 PURCHASE_GRANT에 반영하는 것이다. 환불은 MVP 이후다. 서명 검증만으로 중복 지급을 막을 수 없으며 거래 ID·원장 멱등 키·트랜잭션이 추가로 필요하다.

## 13. 미팅 전 스스로 점검하기

1. 각 API의 사용 화면·사용자 행동을 설명할 수 있는가?
2. 필드가 없거나 null/빈 배열/0/false일 때 동작을 구별하는가?
3. 같은 요청이 두 번 오거나 순서가 바뀌면 어떻게 되는가?
4. 토큰은 맞지만 다른 사람의 ID일 때 차단하는가?
5. DB 저장 성공 후 AI·PG·푸시가 실패하면 어떻게 복구하는가?
6. 202 접수와 실제 업무 완료, 평가 저장과 랭킹 반영을 구분하는가?
7. 프론트 계약·AI 내부 API·DB 스키마의 책임 차이를 설명할 수 있는가?
8. 설계안과 확정 요구사항을 구분하고 모르는 정책은 확인 대상으로 말할 수 있는가?

이 문서는 설명 준비용이다. 실제 구현 검증에는 중복 요청·동시 요청·실패 복구 테스트와 SQL 실행 계획 확인이 필요하다. 키워드를 그대로 외우기보다 한 API를 선택해 정상 요청에서 실패 복구까지 직접 설명해 보는 것이 좋다.
