# TourAPI 상세 동기화 파이프라인

![TourAPI 일일 상세 동기화 파이프라인](architecture/tour-api-detail-sync-pipeline.svg)

## 이번 구현 범위

- 매일 실행하는 기존 목록 동기화가 완료되면 이번 실행에서 신규 적재된 콘텐츠와 전날 `createdtime` 또는 `modifiedtime`에 해당하는 콘텐츠를 합쳐 상세 대상으로 선별한다.
- 신규 적재 콘텐츠는 TourAPI 목록에 늦게 노출될 수 있으므로 원본 생성·수정일과 관계없이 상세 대상으로 포함한다.
- 선별 대상은 서비스에서 사용하는 대분류(`NA`, `HS`, `VE`, `EX`, `LS`, `EV`)로 제한한다.
- 모든 대상은 `detailCommon2`, 행사(`EV`)는 `detailIntro2`까지 호출한다.
- 원본 응답은 실행 ID와 콘텐츠 ID 단위로 로컬 또는 S3에 저장한다.
- 공통 상세는 `tourism_contents`, 행사 상세는 `event_details`에 정규화한다.
- 한 콘텐츠의 상세 조회가 실패해도 나머지 대상은 계속 처리하고 성공·실패 건수를 로그로 남긴다.
- 목록·행사·상세의 이전값과 신규값을 비교해 실제로 달라진 필드만 만든다.
- 같은 콘텐츠에서 발견한 목록·행사·상세 변경을 하나의 `ContentChangeSet`으로 병합한다.
- 정기 동기화에서 감지한 변경은 `run_id + source_provider + source_content_id`를 고유 키로 하는
  `tour_api_content_change_occurrences`에 저장한다. 기준정보와 상세정보를 갱신하는 각각의
  트랜잭션 안에서 같은 occurrence에 병합하므로 중간 실패 시 데이터 변경과 변경 이력이 함께
  롤백된다.
- 상세 backfill은 정기 동기화 실행 이력이 아니므로 변경 occurrence와 후속 알림을 만들지 않는다.
- 병합된 변경 중 제목·소개·연락처·행사 기간·운영 정보·상태처럼 사용자에게 의미 있는 필드만 관심 콘텐츠 변경 알림 후보로 선별한다.
- 신규 콘텐츠는 일일 신규 행사 집계 정책에서 다루기 위해 관심 콘텐츠 변경 후보에서 제외한다.
- 동기화 성공 기록 후 관심 행사 변경 이벤트를 발행하고, 전용 bounded executor가 회원별 알림 생성을 순차 처리한다.
- 회원×행사별 `EVENT_CHANGED` 알림을 저장하면 기존 커밋 후 리스너가 SSE와 Web Push를 발송하며, 실패한 회원은 로그를 남기고 다음 회원 처리를 계속한다.
- 목록 반영은 신규, 기존 갱신, 응답 누락에 따른 비활성화의 세 경우로 구분한다. 비활성 콘텐츠가 다시 응답에 들어오면 별도 재활성 사건으로 관리하지 않고 기존 콘텐츠 갱신으로 처리하여 `status=ACTIVE`, `deleted_at=NULL`로 복구한다.
- 지도 응답에 영향을 주는 변경만 선별해 이전·현재 좌표의 타일 캐시를 DB에서 다시 조회해 교체한다.
- 데이터 변경이 없어도 날짜 경과로 노출에서 빠지는 행사가 있으므로, 전날 종료된 행사의 좌표도 부분 갱신 대상에 포함한다.
- 캐시 초기 스냅샷이 준비되지 않은 경우에만 전체 갱신으로 fallback하고, 부분 갱신 타일 수와 fallback 여부를 로그로 남긴다.

## 후속 구현 범위

- 영속 변경 occurrence를 기준으로 소개·운영정보 변경 필드 중 사용자에게 의미 있는 필드만
  행사 알림 후보로 변환하고, 후속 알림 재실행의 안정적인 occurrence key로 사용한다.
- 당일 신규 행사는 개별 알림 대신 일 단위로 집계하여 알림과 신규 행사 목록에 사용한다.
- 실패한 콘텐츠와 미처리 기준일을 영속화하여 다음 실행에서 재처리한다.

## 운영 DB 상세 backfill

- 운영 DB 구조 변경 등으로 기존 활성 콘텐츠의 상세 필드를 다시 적재해야 할 때는
  `tour-api.detail-backfill.enabled=true`인 일회성 애플리케이션 프로세스를 사용한다.
- 대상은 `tourism_contents.id` 오름차순의 키셋 커서로 나눠 조회한다. 실행마다
  `start-after-id`, `batch-size`, `max-batches`를 지정하고 로그의 `nextAfterId`를 다음
  실행의 `start-after-id`로 사용한다.
- 각 대상은 기존 상세 동기화와 동일하게 `detailCommon2`를 호출하고, 행사(`EV`)는
  `detailIntro2`도 호출한 뒤 기존 정규화 로직으로 upsert한다.
- 한 건이 실패해도 같은 배치의 다음 대상은 계속 처리하며 실패한 TourAPI 콘텐츠 ID를
  완료 로그에 남긴다. 전체 커서 실행이 끝난 뒤 실패 ID는 별도 재실행 대상으로 확인한다.
- 기본값은 비활성화이며 정기 스케줄러와 동시에 실행하지 않는다.

## 선택 근거

- `modifiedtime`은 무엇이 바뀌었는지를 알려주지 않으므로 상세 API 응답과 현재 DB 값을 비교해야 한다.
- `detailInfo2`의 행사소개·행사내용은 `detailCommon2.overview`와 중복 가능성이 있어 이번 수집 대상에서 제외한다.
- 원본 JSON은 변경 추적과 재처리를 위해 보존하되, MySQL에는 공통 소개·홈페이지·연락처와 행사 운영시간·주최자·주최자 연락처·장소만 정규화한다.
