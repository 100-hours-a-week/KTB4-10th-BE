# 3단계 기술 검토 및 스택 선정

## 1. 공통 백엔드 기반

### Java 21

Java 21은 LTS 버전으로 장기간 지원되며 Spring 생태계와 관련 자료가 충분하다. Java 25보다 프로젝트 적용 사례와 라이브러리 호환성을 확인하기 쉽다. 기존 Java 17 시스템과의 호환이 필요 없는 신규 프로젝트이므로 Java 21을 선택한다.

### Spring Boot

Spring Boot는 Spring 기반 애플리케이션의 의존성, 설정, 내장 서버와 운영 기능을 일관된 방식으로 구성할 수 있게 한다. Spring Framework를 직접 조합하는 것보다 초기 설정이 단순하고 Actuator와 테스트 환경도 쉽게 통합할 수 있어 선택한다.

### Spring MVC

MySQL과 Spring Data JPA가 Blocking I/O 기반이므로 WebFlux를 도입해도 데이터 접근 구간의 블로킹은 제거되지 않는다. AI 생성은 요청 스레드에서 완료를 기다리지 않고 작업 접수 후 별도 워커에서 처리한다.

현재 서비스는 관계형 데이터의 CRUD와 트랜잭션이 중심이므로 JPA 연동과 운영이 단순한 Spring MVC를 선택한다. 향후 SSE·스트리밍이나 대규모 동시 외부 호출이 주요 부하가 되면 해당 구간에 한해 리액티브 방식을 다시 검토한다.

### Gradle

Gradle은 Task 단위의 증분 빌드와 Build Cache를 지원하며 Kotlin DSL을 이용해 빌드 설정을 관리할 수 있다. Spring Boot 프로젝트의 의존성과 테스트 작업을 유연하게 구성할 수 있고 빌드 스크립트도 비교적 간결하게 관리할 수 있어 선택한다.

Maven도 증분 처리와 병렬 실행을 지원하므로 Gradle이 항상 빠르다는 것을 주요 근거로 삼지 않는다. Gradle Wrapper를 저장소에 포함해 로컬과 CI에서 같은 버전을 사용한다.

미확정 항목은 Spring Boot·Gradle의 정확한 버전과 Gradle Kotlin DSL·Groovy DSL 선택이다.

## 2. 회원·인증 도메인

### Spring Security

로그인 여부와 가이드북·평가·결제 API의 접근 권한을 검증한다. 인증뿐 아니라 사용자가 자신의 자원에만 접근하도록 인가 처리를 공통화하기 위해 사용한다.

### Spring Security OAuth2 Client

카카오와 구글의 Authorization Code 로그인을 백엔드에서 처리한다. OAuth 공급자별 사용자 정보를 내부 회원 모델로 변환하며, 이메일이 아닌 공급자와 공급자 회원 ID 조합으로 회원을 식별한다.

### 서버 세션

로그인 이후에는 액세스·리프레시 토큰을 발급하지 않고 HttpOnly 쿠키 기반 서버 세션을 사용한다. 로그아웃과 회원 탈퇴 시 서버에서 세션을 즉시 폐기할 수 있다.

현재 `auth_sessions` 테이블을 직접 사용할지, `Spring Session JDBC`와 표준 세션 테이블을 사용할지는 미확정이다. 두 방식을 중복 구현하지 않는다. 세션 유지 기간·연장 방식·동시 로그인 개수도 추가로 정해야 한다.

## 3. 관광 콘텐츠·검색·지도 도메인

### MySQL Spatial과 Hibernate Spatial

관광 콘텐츠의 위도와 경도를 MySQL `POINT SRID 4326`으로 저장하고 공간 인덱스를 사용한다. 백엔드에서 공간 타입을 매핑하기 위해 Hibernate Spatial을 사용한다. 지도 SDK는 화면을 표시하는 프론트엔드 기술이므로 백엔드 기술 스택과 구분한다.

### 검색

초기에는 MySQL의 `LIKE` 검색을 사용한다. 현재 데이터 규모에서 별도 검색 엔진을 운영하는 비용보다 단순한 DB 검색이 적합하다고 판단한다. 실제 성능과 한국어 검색 품질을 측정한 후 MySQL FULLTEXT ngram 적용 여부를 검토한다. Elasticsearch나 OpenSearch는 MySQL로 요구를 충족하지 못할 때 재검토한다.

## 4. 가이드북·AI 생성 도메인

### Spring RestClient

백엔드가 별도 AI 서버에 가이드북 생성과 작업 취소를 요청하기 위해 사용한다. Spring MVC 기반 애플리케이션과 실행 방식이 일치하며 연결 시간과 응답 시간 제한을 설정할 수 있다.

### DB 작업 테이블과 워커

AI 생성 요청을 `generation_jobs`에 먼저 저장하고 별도 워커가 처리한다. API 요청과 장시간 AI 호출을 분리해 사용자 요청 스레드가 오랫동안 점유되지 않도록 한다.

AI 생성은 1회당 최대 300초이며 최초 호출 이후 최대 3회 재시도한다. 잘못된 입력에는 재시도하지 않고 타임아웃이나 일시적인 AI 서버 장애에만 적용한다.

### Resilience4j

AI·관광 API 등 외부 시스템의 일시적인 장애에 대한 재시도와 장애 격리를 위해 검토한다. 모든 요청을 자동 재시도하지 않고 멱등성이 보장된 요청에만 적용한다.

미확정 항목은 AI 실패 후 재시도 간격, 단일·다중 워커, 중단된 `PROCESSING` 작업의 복구 방식, AI 서버의 작업 조회·취소 API 계약과 Resilience4j 적용 범위다.

## 5. 평가·랭킹 도메인

### Spring Scheduling

평가 제출 요청마다 전체 랭킹을 다시 계산하지 않고 10분 단위로 랭킹을 갱신하기 위해 사용한다.

### ShedLock

서버가 여러 대일 때 각 서버의 스케줄러가 같은 랭킹 집계를 중복 실행하는 것을 막기 위해 사용한다. MySQL에 잠금 정보를 저장해 특정 시점에 하나의 서버만 작업을 실행하게 한다. 단일 서버로 운영하는 동안에는 필수가 아니므로 다중 서버 운영 시 도입하는 조건부 기술로 분류한다.

Message Queue는 ShedLock의 단순한 다음 단계가 아니다. 작업 전달 보장, 처리량 확장 또는 여러 소비자가 필요할 때 Kafka나 RabbitMQ를 별도로 검토한다.

미확정 항목은 초기 서버 인스턴스 수, ShedLock 도입 시점, 랭킹 공식의 `C` 산정 범위와 `m` 값이다.

## 6. 알림 도메인

### 인앱 알림

인앱 알림은 `notifications` 테이블에 저장하고 Spring Data JPA로 조회·삭제한다. DB에 저장되는 기능이므로 별도 알림 라이브러리는 필요하지 않다.

원본 업무가 성공한 뒤 알림을 별도 트랜잭션으로 생성한다. 알림 실패가 가이드북 생성이나 평가 제출 같은 원본 업무를 롤백시키지 않도록 한다.

### FCM 웹 푸시

브라우저가 닫힌 상태에서도 웹 푸시를 제공한다면 Firebase Cloud Messaging을 사용한다. 백엔드는 Firebase Admin SDK로 브라우저의 FCM 등록 토큰에 푸시를 전송한다.

푸시 실패는 인앱 알림 저장과 원본 업무에 영향을 주지 않는다. 만료되거나 유효하지 않은 토큰은 비활성화하고, 일시적인 FCM 장애만 제한적으로 재시도한다.

MVP의 웹 푸시 포함 여부, FCM 토큰 저장 구조, 여러 브라우저의 중복 구독 처리와 푸시 실패 재시도 횟수·간격은 미확정이다. MVP가 인앱 알림만 제공하면 Firebase Admin SDK는 도입하지 않는다.

## 7. 생성권·결제 도메인

### Spring Transaction과 MySQL 행 잠금

가이드북 생성 결과 저장, 생성권 차감과 원장 기록을 하나의 트랜잭션으로 처리한다. 동일 회원의 동시 생성 요청으로 생성권이 중복 차감되지 않도록 지갑 행 잠금과 유일 제약을 사용한다. 멱등성은 별도 라이브러리보다 `Idempotency-Key`, DB 유일 제약과 트랜잭션으로 보장한다.

실제 PG사, PG SDK·RestClient 직접 연동, 승인 API와 웹훅 검증, 중복·역순 이벤트 처리와 결제 중 회원 탈퇴 처리는 미확정이다. PG사가 정해지기 전에는 특정 결제 SDK를 확정하지 않는다.

## 8. PDF·HTML 도메인

### HTML Sanitizer

AI가 생성한 HTML에 스크립트나 위험한 속성이 포함될 수 있으므로 저장 또는 출력 전에 정제해야 한다. 이를 위해 OWASP Java HTML Sanitizer를 검토한다.

### PDF 렌더러

현재 PDF API는 요청 중 생성한 PDF를 `200 application/pdf`로 반환하는 동기 방식이다. HTML과 CSS 표현력이 높은 Playwright·Chromium 계열과 JVM 안에서 실행하기 쉬운 OpenHTMLtoPDF를 실제 가이드북 템플릿으로 비교한다.

한국어 글꼴·이미지·페이지 분할, 최대 생성 시간·파일 크기·동시 생성 한도와 최종 PDF 라이브러리는 미확정이다.

## 9. API 문서화·DB 마이그레이션

### springdoc-openapi

작성한 API 명세와 실제 구현의 요청·응답 차이를 줄이기 위해 사용한다. Swagger UI를 통해 프론트엔드 개발자가 API 형식과 오류 응답을 확인할 수 있다. Spring Boot와 호환되는 springdoc 버전을 선택해야 한다.

### Flyway

테이블과 인덱스 변경 이력을 코드로 관리한다. 개발·테스트·운영 환경에 같은 스키마 변경을 같은 순서로 적용할 수 있다. JPA의 `ddl-auto`로 운영 DB를 변경하지 않고 Flyway migration을 기준으로 관리한다.

## 10. 테스트

### Spring Boot Test·MockMvc

서비스 로직과 API 요청·응답을 검증한다. 상태 코드, 요청값 검증, 세션 인증과 소유권을 테스트한다.

### Testcontainers MySQL

H2는 MySQL의 `POINT`, 생성 컬럼, 공간 인덱스와 행 잠금을 동일하게 재현하지 못한다. 실제 MySQL 컨테이너를 사용해 DDL과 트랜잭션을 검증한다.

### WireMock·Awaitility

WireMock으로 AI·OAuth·관광 API·PG 같은 외부 시스템의 성공·실패·타임아웃을 재현한다. Awaitility로 AI 생성과 랭킹 집계 같은 비동기 작업을 고정된 `sleep`없이 테스트한다.

사용 후보는 `spring-boot-starter-test`, `spring-security-test`, `testcontainers-junit-jupiter`, `testcontainers-mysql`, `wiremock`, `awaitility`다.

## 11. 운영·모니터링

### Spring Boot Actuator

클라우드 로드밸런서가 서버 상태를 확인할 수 있도록 `GET /actuator/health`를 제공한다. 애플리케이션과 MySQL 상태를 확인하고 정상은 200, 비정상은 503을 반환한다. AI·PG·FCM 장애는 백엔드 인스턴스를 트래픽에서 제거할 이유가 아니므로 헬스체크에 포함하지 않는다.

### Micrometer

API 응답 시간, 오류율, AI 생성 시간, 재시도 횟수와 랭킹 갱신 지연을 측정한다. 실제 Prometheus 환경을 사용한다면 `micrometer-registry-prometheus`를 추가한다.

클라우드 모니터링 제품, Prometheus 사용 여부, 로그 수집 제품과 경보 기준은 미확정이다.

## 12. 배포

### Docker

개발과 운영 환경에서 같은 JDK와 애플리케이션 실행 환경을 사용하기 위해 선택한다. 이미지에 비밀키를 포함하지 않고 실행 환경에서 주입한다.

### GitHub Actions

빌드, 테스트와 배포 과정을 자동화하는 CI/CD 도구 후보로 사용한다.

실제 클라우드 공급자, 단일·다중 서버, 배포 방식, MySQL 운영 방식, 백업 주기와 복원 목표, 로그·메트릭 저장 위치는 미확정이다.

## 14. 추가 결정 필요 항목

- Spring Boot·Gradle의 정확한 버전과 Gradle DSL
- `auth_sessions` 직접 구현과 Spring Session JDBC 중 세션 저장 방식
- 서비스 세션 유지 기간·연장 방식·동시 로그인 수
- AI 작업 재시도 간격과 워커 복구 방식
- MVP 웹 푸시 포함 여부와 FCM 구독 저장 구조
- 단일·다중 서버와 ShedLock 도입 여부
- 랭킹 공식의 `C`·`m` 값
- PDF 렌더러와 응답 시간·파일 크기·동시 실행 한도
- PG사·승인·웹훅·멱등 계약
- 클라우드·모니터링·로그 수집 제품과 백업 정책
