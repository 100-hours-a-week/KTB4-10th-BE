## 1. 결론과 읽는 방법

현재 서비스는 5개 도메인의 관계형 데이터와 생성권 정합성이 중심이다. 주 DB는 최신 테이블·SQL에 맞춰 **MySQL 8.x / InnoDB / utf8mb4**를 기준으로 한다. PostgreSQL·PostGIS를 전제로 했던 이전 권장안은 대체한다.

AI 생성은 저장된 작업을 비동기로 처리하지만, PDF는 MVP에서 동기 다운로드다. 랭킹은 평가 저장 후 변경 지역과 전국 범위를 비동기 재집계한다. Outbox·Redis·벡터 DB·오브젝트 스토리지는 현재 구현에 필요한 것으로 일괄 확정하지 않는다.

문서의 상태 표기는 다음 의미다.

- **기준 반영**: 제공된 요구사항·테이블·SQL에 이미 명시된 전제.
- **선정**: 기술 스택 초안에서 채택한 기술. 정확한 버전·설정·실제 구현 검증까지 완료했다는 뜻은 아니다.
- **권장안**: 전제에 맞는 구현 제안. 팀 경험·호환성·실험을 확인한 뒤 결정한다.
- **조건부**: 명시한 부하·운영·기능 조건이 성립할 때 도입한다.
- **결정 필요**: 현재 자료만으로 제품·버전·정책을 정할 수 없음.
- **후순위**: 도입 조건이 생기기 전에는 MVP 의존성으로 추가하지 않음.

## 2. 기술을 나누고 선택하는 기준

1. **요구사항 충족**: 어떤 FR/BR/NFR을 해결하는지 설명한다.
2. **정합성**: 중복 요청·동시 처리·외부 성공 후 내부 실패를 감당할 수 있는가?
3. **팀 역량과 일정**: 구성원이 직접 실행·디버깅·복구할 수 있는가? 현재 숙련도는 별도로 확인한다.
4. **운영 비용**: 서버 수뿐 아니라 모니터링·백업·장애 대응·업그레이드 비용을 포함한다.
5. **필요한 확장만 준비**: 공급자 어댑터와 도메인 경계는 두되, 미래 가능성만으로 별도 DB·브로커를 추가하지 않는다.

제품 선택과 업무 정책은 다르다. MySQL을 정해도 평가 부분 제출, 랭킹 기간 경계, PG 공급자가 자동으로 결정되는 것은 아니다.

## 4. 애플리케이션 구조: 모놀리식 아키텍처

### 선택 이유

한 백엔드 애플리케이션으로 빌드·배포하는 **모놀리식 아키텍처**를 사용한다. 다만 내부 코드는 회원, 관광 콘텐츠·탐색, 가이드북, 평가·랭킹, 생성권·결제 도메인별 패키지로 분리한다. `모듈러 모놀리스`는 이 내부 분리 방식을 설명할 때만 보조 용어로 사용한다.

AI 서비스와 PG는 외부 시스템으로 취급한다. 생성 결과 저장과 생성권 차감은 백엔드의 같은 MySQL 트랜잭션으로 조율한다. 현재 팀·배포 규모에서 마이크로서비스의 독립 배포보다 로컬 트랜잭션과 운영 단순성의 이익이 더 크다.

도메인 간 변경은 공개 application service를 통해 요청한다. 생성권 원본은 생성권 패키지만 변경하고, 가이드북 패키지가 지갑 repository를 직접 수정하지 않는다. 공통 오케스트레이터의 트랜잭션에 필요한 도메인 서비스가 참여하는 방향을 검토한다.

### 대안과 단점

마이크로서비스는 독립 배포에 유리하지만 현재는 분산 정합성·배포·추적 부담이 크다. 모놀리스는 한 부분의 자원 고갈이 다른 API에 영향을 줄 수 있으므로 AI/PDF 실행 수·DB 커넥션·요청 큐를 제한해야 한다. 단순히 패키지를 나누었다고 장애 격리가 되는 것은 아니다.

ArchUnit 같은 의존성 검사 도구는 권장 후보다. 별도 모듈 빌드나 이벤트 버스를 처음부터 도입하기보다 의존 규칙을 코드 리뷰와 테스트로 먼저 지킨다.

## 5. Java·Spring·빌드 도구

### Java 21 + Spring Boot / MVC: 선정

Java는 컴파일 시 정적 타입 검사를 제공하고, JVM을 통해 같은 바이트코드를 운영체제별 JVM 위에서 실행한다. JVM은 JIT 컴파일, GC, 스레드·동시성 도구와 heap dump·thread dump·JFR 같은 운영 분석 수단을 제공한다. 회원·가이드북·지갑처럼 상태와 규칙을 가진 객체를 타입으로 모델링하고 Spring 생태계를 이용하기에 적합하여 Java를 선택한다.

Java 21을 기준 버전으로 선택한다. Java 21과 25는 모두 LTS이므로 25를 불안정하다고 평가하지 않는다. 다만 현재 요구에 25 전용 기능이 없고, 21도 가상 스레드를 정식 지원한다. 따라서 팀 개발 환경과 Spring Boot·Hibernate·JDBC 드라이버·빌드 도구의 검증 범위를 줄일 수 있는 21을 우선한다. JDK 배포판과 Boot의 정확한 버전은 실제 구현 조합으로 확인한 뒤 고정한다.

Spring Boot는 IoC/DI를 통해 객체 생성과 연결을 관리하고, AOP 기반 트랜잭션·보안·로깅 같은 횟단 관심사를 일관되게 적용한다. Spring Boot의 자동 설정·의존성 관리·내장 서버·운영 기능으로 개발·테스트·배포 환경의 차이를 줄인다. 단, 자동 설정의 적용 조건과 실제 등록된 Bean·트랜잭션 범위를 이해해야 한다.

공식 시스템 요구사항과 springdoc 호환표를 참고한다. Boot 3에는 springdoc 2.x, Boot 4에는 대응하는 3.x 계열을 검토하되 정확한 minor/patch는 동일 프로젝트에서 검증한다. [Spring Boot 시스템 요구사항](https://docs.spring.io/spring-boot/system-requirements.html), [springdoc 공식 호환 안내](https://springdoc.org/)

MVC는 blocking JPA/JDBC와 실행 모델이 맞고 일반 CRUD·트랜잭션 흐름을 순차적인 코드로 표현하기 쉽다. 모놀리식이므로 WebFlux가 불필요한 것은 아니다. WebFlux의 채택 기준은 서비스 분리 방식이 아니라 대량의 동시 I/O·장기 연결을 요구하고 HTTP부터 DB까지 non-blocking으로 구성할 수 있는지다. 현재는 JPA/JDBC가 DB 응답을 기다리는 blocking API이므로 MVC를 선택한다. AI 생성을 저장형 비동기 작업으로 분리하는 것과 웹 스택 전체를 reactive로 바꾸는 것은 별개 결정이다.

### 가상 스레드와 JVM 메모리: 조건부 적용·운영 검증

가상 스레드는 플랫폼 스레드보다 생성·대기 비용이 작아 blocking I/O를 `thread-per-task`의 순차적인 코드로 유지하면서 많은 동시 작업을 다룰 수 있다. 콜백·reactive chain에 비해 stack trace, 예외 전파, 디버깅이 기존 동기 코드와 가깝다. 이 서비스에서는 외부 AI·관광 API 호출과 JDBC 대기가 후보다. PDF 렌더링과 대규모 집계 같은 CPU·메모리 작업을 빠르게 만들지는 않는다.

초기에는 가상 스레드를 성능 보장책으로 일괄 활성화하지 않는다. 선택한 Spring Boot 버전에서 `spring.threads.virtual.enabled=true` 또는 `Executors.newVirtualThreadPerTaskExecutor()`를 이용해 AI worker 부하 테스트를 수행한다. 가상 스레드가 많아도 AI 공급자의 쿼터, DB 커넥션 풀, 호출 비용은 늘지 않으므로 semaphore·bulkhead·제한된 worker 수로 동시 호출을 따로 제한한다. [Java 21 가상 스레드](https://docs.oracle.com/en/java/javase/21/core/virtual-threads.html), [Spring Boot 작업 실행·스케줄링](https://docs.spring.io/spring-boot/reference/features/task-execution-and-scheduling.html)

GC는 더 이상 참조되지 않는 객체만 회수하므로 OOM과 메모리 누수를 없애지 못한다. 크기 제한 없는 캐시·작업 큐·static 컬렉션, `ThreadLocal` 정리 누락, 종료된 SSE listener, 대형 AI 응답·PDF의 동시 적재, JPA 영속성 컨텍스트에 대량 entity 누적이 주요 위험이다. 모든 큐·캐시·동시 작업에 상한을 두고 heap/GC·스레드·작업 대기 지표를 모니터링한다. OOM 시 heap dump를 남기고 JFR·Eclipse MAT 등으로 GC root까지의 참조 경로를 분석한다. 힙 크기를 늘리는 것만으로 누수를 해결하지 않는다.

### Gradle과 버전 관리

Gradle을 선택하고 Wrapper를 포함해 로컬·CI 버전을 맞춘다. Task 기반 구성·증분 빌드·캐시를 활용할 수 있지만 Maven보다 항상 빠르다는 주장은 하지 않는다. Gradle 정확한 버전과 Kotlin/Groovy DSL은 결정 필요다. JDK·Boot·JDBC 드라이버·Flyway·springdoc·테스트 라이브러리는 독립적으로 최신 버전을 조합하지 않는다. Boot의 의존성 관리와 공식 호환표를 기준으로 고정하고 CI에서 확인한다. JUnit major도 선택한 Boot 테스트 구성을 기준으로 정한다.

## 6. 주 DB: MySQL을 선택하는 근거

### 우리 서비스에 맞는 이유

- 회원·가이드북·장소·평가·원장은 참조와 유일성 제약이 필요한 관계형 데이터다.
- 생성권 잔액, 원장, 작업 완료, 가이드북을 하나의 트랜잭션으로 저장해야 한다.
- 현재 ERD가 이미 MySQL의 GENERATED 컬럼, UNIQUE, JSON, POINT와 공간 인덱스를 사용한다.
- MVP에서 PostgreSQL만의 특정 기능이 반드시 필요하다는 근거가 확인되지 않았다. 기존 MySQL 설계를 유지하면서 실제 쿼리와 장애 복구를 검증하는 편이 범위가 작다.

'한국에서 많이 사용한다'는 참고 요소일 수 있지만 기술적 충분조건은 아니다. 'MySQL이 무조건 빠르다'거나 'PostgreSQL이 복잡하니 나쁘다'고 설명하지 않는다.

### InnoDB 스토리지 엔진: 선정

MySQL은 DBMS이고 InnoDB는 테이블의 저장·트랜잭션·동시성을 담당하는 스토리지 엔진이다. '다른 엔진보다 압도적으로 좋다'는 표현 대신 현재 요구에 필요한 다음 기능과 연결한다.

- 가이드북·일정 저장, 작업 완료, 지갑 차감, 원장 삽입을 하나의 ACID 트랜잭션으로 처리한다.
- `SELECT ... FOR UPDATE`의 행 단위 잠금으로 같은 회원의 마지막 생성권이 두 번 사용되는 경쟁을 제어한다.
- FK로 존재하지 않는 회원·콘텐츠·가이드북 참조를 차단한다.
- MVCC로 일반 읽기와 쓰기의 불필요한 충돌을 줄이고, redo/undo 기반으로 장애 후 커밋·롤백 상태를 복구한다.
- 현재 필요한 일반 및 공간 인덱스를 같은 엔진에서 사용한다.

트랜잭션·FK가 중심인 이 서비스에서는 MyISAM같은 비트랜잭션 엔진을 비교 후보로 두지 않는다. 다만 InnoDB 사용만으로 정합성이 자동 보장되는 것은 아니며, 적절한 인덱스·잠금 순서·트랜잭션 범위·멱등성 제약을 함께 설계해야 한다.

관련 잠금·거래 모델은 [MySQL InnoDB 잠금과 트랜잭션](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-transaction-model.html)을 기준으로 검증한다.

### PostgreSQL과의 비교

| 판단 항목 | 현재 MySQL 선택 | PostgreSQL 대안 및 트레이드오프 |
|---|---|---|
| 관계·트랜잭션 | 현재 요구에 필요한 제약과 행 잠금 사용 | PostgreSQL도 가능하므로 이것만으로 우열을 정하지 않음 |
| 공간 조회 | 현재 POINT/SRID/공간 인덱스의 조회 성능 검증 | 고급 공간 연산이 필요해지면 PostGIS를 포함해 재평가 |
| JSON | 요청·장소 스냅샷에 MySQL JSON 사용 | JSONB가 있다는 이유만으로 주 DB를 바꿀 필요는 없음 |
| 조건부 유일성 | active_member_id 등 생성 컬럼 + UNIQUE | PostgreSQL의 부분 인덱스 등과 표현 방식이 다름 |
| AI 벡터 검색 | 백엔드 주 DB 요구로 확정되지 않음 | AI 팀의 실제 검색 요구가 있으면 별도 검토 |
| 전환 비용 | 현재 DDL/JPA/테스트를 같은 DB로 맞춤 | 전환하면 타입·SQL·마이그레이션·운영 검증을 다시 수행 |

이 비교는 전체 DB 성능 순위가 아니라 현재 설계에 대한 선택 근거다. MySQL 정확한 버전은 운영 서비스의 지원 수명·공간 함수·JDBC 호환성을 확인해 결정하며 로컬·CI·운영을 맞춘다.

### AI DB와 업무 DB의 책임

AI 서비스가 벡터 저장소를 쓰더라도 회원·소유권·가이드북 최종본·잔액의 원본은 백엔드 MySQL이다. AI는 job_id와 합의한 입력을 받아 결과를 반환하고, 백엔드가 콘텐츠 ID·일정·출력 구조를 검증한다.

AI의 검색 인덱스와 MySQL 사이에는 공통 FK나 단일 트랜잭션이 없다. 콘텐츠 갱신/비활성화 전파, 재색인, 버전 불일치 대응이 추가되므로 벡터 DB를 자동으로 필수화하지 않는다. 모델·벡터 엔진 선택은 AI 담당과 별도 합의한다.

### NoSQL과 크롤링 원본: 초기 미도입

관광 콘텐츠에 nullable 컬럼이 있다는 사실만으로 MongoDB를 선택하지 않는다. 전화번호·홈페이지·이미지는 원래 없을 수 있는 값이므로 SQL `NULL`로 표현해도 된다. 서비스에 적재된 후에는 지역·일정·관심·평가·랭킹과 연결되므로 검증된 표준 콘텐츠는 MySQL이 원본이다.

공급자별 응답 구조가 다르거나 필드 누락·파싱 실패를 재처리해야 한다면 서비스 테이블에 바로 쓰지 않고 `raw_payload JSON`, 공급자 ID, 수집 시각, 상태·오류를 가진 MySQL 수집 staging 테이블을 먼저 검토한다. 정제·검증에 성공한 값만 `tourism_contents`와 상세 테이블에 upsert한다.

MongoDB는 공급자 수·원본 용량·쓰기량이 크게 늘고, 스키마가 매우 다른 원본 문서를 독립적으로 보존·재처리하는 것이 MySQL JSON보다 운영상 유리해질 때만 **수집 원본 저장소**로 재검토한다. 그 경우에도 검색·소유권·일정·평가에 사용하는 표준 콘텐츠의 원본은 MySQL에 둔다.

## 7. 현재 스키마를 구현할 때의 기술 판단

| 설계 요소 | 구현 기준 | 주의점 |
|---|---|---|
| 사건 시각 | DATETIME(6)에 UTC, DB 세션/JDBC도 UTC | 컬럼 자체가 타임존을 보관하지 않음; 표시만 Asia/Seoul |
| 여행·행사 날짜 | DATE, 일정 방문 시각 TIME | 날짜와 시각을 무조건 Instant로 통일하지 않음 |
| 상태·취향 | Java Enum을 VARCHAR로 매핑 | ordinal 저장 금지; 코드와 부모 관계 검증은 서비스 책임 |
| 삭제 | deleted_at + 업무 status 분리 | 컬럼만 추가하면 soft delete가 자동 적용되는 것이 아님 |
| 좌표 | location POINT SRID4326, NOT NULL | API는 latitude/longitude 숫자로 변환; 축 순서 테스트 |
| URL | 상세 정의와 SQL의 VARCHAR(2048) | 인터넷 공통 상한이 아니라 서비스 제한; 초과값 잘라 저장하지 않음 |
| 이미지 중복 | URL 정규화 후 SHA-256 BINARY(32) | 정규화 규칙 합의; URL이 같다는 것과 이미지 내용이 같다는 것은 다름 |
| 관심 장소·취향 선택 | 대리 PK + 복합 UNIQUE | 대리키가 생겨도 API의 관계 식별자를 바꿀 필요는 없음 |
| 회원별 활성 작업 | 생성 컬럼 active_member_id + UNIQUE | 비활성 작업의 NULL은 여러 개 허용; JPA에서 생성 컬럼 쓰기 제외 |
| 전국 랭킹 | scope_region_id=COALESCE(region_id,0) | 실제 지역 ID는 1 이상이어야 함; SQL 제약 누락 여부 확인 |
| 최종 점수 | SMALLINT, 0~5 정수 또는 NULL | 0 포함, NULL 제외; DB 타입 변환 전 API에서 소수 입력 차단 |
| 원장 | 불변 이력 + 원인별 idempotency_key | 지갑 변경과 원장 INSERT를 같은 트랜잭션으로 처리 |

알림은 읽을 때 실제 행을 삭제한다. 모든 테이블에 공통 soft delete를 일괄 적용하면 오히려 요구사항과 달라진다. 원장·결제 데이터를 회원 삭제에 CASCADE로 지우는 설계도 현재 보존 전제와 맞지 않는다.

## 8. 지도와 검색

### 공간 조회

MySQL은 SRID가 지정된 NOT NULL 공간 컬럼과 SPATIAL INDEX를 지원한다. 현재 SQL이 이 구조이므로 PostGIS 설치를 전제로 하지 않는다. [MySQL 공간 타입](https://dev.mysql.com/doc/refman/8.4/en/spatial-type-overview.html)

조회는 영역으로 후보를 줄인 뒤 필요한 정확 거리/영역 조건을 적용하는 방식을 검토한다. ‘거리 함수 사용 = 공간 인덱스 사용’이라고 단정하지 않고 실행 계획을 확인한다. 좌표는 지도 SDK·AI·DB 간 순서와 단위를 고정하고, 유효 좌표가 없는 콘텐츠는 지오코딩 성공 전 삽입/활성화 대상에서 제외한다.

지도 화면의 디바운스·영역 요청·마커 제한은 프론트와 합의한다. 공급자 SDK, 최대 반경·줌·클러스터 응답은 아직 미확정이다. POINT를 저장한다고 지도 SDK가 대체되는 것은 아니다.

### 제목 검색

초기 제목 검색은 MySQL LIKE로 시작한다. 현재 `(region_id, category)` 인덱스만으로 `LIKE '%검색어%'` 제목 부분 검색을 최적화했다고 주장할 수 없다. 작은 데이터에서 LIKE를 사용하더라도 p95와 데이터 증가 시 한계를 측정한다.

MySQL FULLTEXT ngram은 한국어 검색 후보지만 기존 부분 문자열 검색과 결과가 동일하지 않다. 토큰 크기·한 글자 검색·띄어쓰기·검색 결과 품질을 비교해야 한다. 현재 SQL에는 FULLTEXT 인덱스가 없으므로 이미 적용된 기술로 쓰지 않는다. [MySQL ngram 설명](https://dev.mysql.com/doc/refman/8.4/en/fulltext-search-ngram.html)

검색 엔진은 오타 교정·관련도·형태소 품질 또는 DB 성능 한계가 실제 문제일 때 검토한다. 도입하면 DB와 색인의 반영 지연·재색인·장애 대응도 필요하다.

### 인메모리 DB·캐시: 초기 미도입, 측정 후 단계적 도입

인메모리 저장소는 RAM에 데이터를 두어 지연을 줄이지만, 원본 DB와의 불일치·메모리 상한·만료·장애 복구를 추가로 설계해야 한다. 따라서 초기 관광 콘텐츠는 MySQL의 일반·공간 인덱스, 페이지네이션과 응답 상한으로 직접 조회한다. 관광 정보의 쓰기 빈도가 낮더라도 동일 데이터가 실제로 반복 조회되는지, DB CPU/I/O·커넥션 풀·API p95에 문제가 있는지를 먼저 측정한다.

HTTP 캐시는 가장 먼저 검토할 수 있다. 공개 콘텐츠 상세·지역 목록에 `Cache-Control`, `ETag`/`If-None-Match`를 적용하면 클라이언트는 유효 기간 동안 요청을 생략하거나 `304 Not Modified`로 body 전송을 피할 수 있다. 단, `304`도 네트워크 왕복과 서버 검증 비용은 발생한다. 회원별 관심 여부를 포함한 응답은 공용 캐시와 분리하고 `private` 캐시 또는 캐시 금지를 적용해 회원 데이터 노출을 막는다. TanStack Query 등의 클라이언트 서버 상태 캐시는 동일 브라우저의 반복 렌더링·요청을 줄이지만, 여러 사용자와 서버가 공유하는 DB 부하 제어를 단독으로 대체하지는 못한다.

쿼리·HTTP 캐시 후에도 반복 조회가 병목이면 단일 인스턴스에서 Spring Cache + Caffeine Cache-Aside를 적용한다. 콘텐츠 상세, 지역 코드, 이미 계산된 랭킹처럼 키가 제한되고 반복률이 높은 결과부터 대상으로 한다. 임의 검색어·지도 영역·반경·페이지 조합은 키 수가 폭발할 수 있어 초기 캐시 대상에서 제외한다. Caffeine에는 반드시 `maximumSize`/용량 상한과 TTL을 두고, 콘텐츠 갱신 커밋 후 관련 키를 무효화한다.

백엔드가 다중 인스턴스로 확장되어도 MySQL `auth_sessions`를 모두가 조회하면 이미 중앙 세션이므로 Redis가 자동으로 필요해지지는 않는다. Redis는 다음 조건 중 하나 이상이 측정될 때 공유 저장소로 재검토한다.

- 인스턴스별 Caffeine 값 차이가 문제이고 즉시 공유·무효화가 필요하다.
- 모든 인스턴스가 공유하는 AI API rate limit·일회성 TTL 상태가 필요하다.
- 인증 요청의 MySQL 세션 조회가 실제 DB 병목이 되어 Redis 세션 저장소를 사용해야 한다.
- AI 완료 처리 인스턴스와 프론트 SSE 연결 인스턴스가 달라 실시간 알림을 전달할 공유 채널이 필요하다.

Redis를 도입해도 생성권 잔액·거래 원장·결제·평가·AI 작업의 최종 상태는 MySQL을 원본으로 유지한다. Redis Pub/Sub을 SSE 실시간 신호에 사용하더라도 연결 단절 시 유실될 수 있으므로 재접속 후 `generation_jobs`를 조회해 최종 상태를 복구한다.

Memcached는 단순 분산 key-value 캐시만 필요할 때의 대안이다. 이 서비스에서 향후 세션·rate limit·서버 간 이벤트까지 하나의 공유 저장소에서 필요해진다면 자료구조·원자 연산·Pub/Sub·Streams를 제공하는 Redis가 더 적합하다. Hazelcast는 분산 Map·분산 연산까지 필요한 데이터 그리드 후보이지만 현재는 해결할 요구가 없으므로 선정 후보에서 제외한다.

## 9. JPA·SQL·마이그레이션

요구사항에서 장기간 식별·보존할 회원, 콘텐츠, 가이드북, 일정, 평가, 주문, 지갑을 찾고 각 데이터의 생명주기·관계·유일성·트랜잭션 경계를 명확히 하기 위해 ERD를 설계했다. 애플리케이션의 entity는 이 중 식별자와 상태·생명주기를 가지고 업무 규칙을 수행하는 객체다. 예를 들어 `CreditWallet.consume()`은 잔액 부족을 거부하고, `GenerationJob.complete()`는 허용된 상태 전이만 수행해야 한다. entity를 API DTO나 테이블 행의 단순 복사본으로 사용하지 않는다.

Java는 객체 참조·컬렉션·상속으로 모델링하지만 RDB는 행·외래 키·JOIN으로 표현한다. ORM은 이 객체-관계 패러다임 불일치를 매핑하고, 조회 결과 변환·CRUD SQL·외래 키 연결의 반복 코드를 줄인다. JPA는 Java ORM 표준, Hibernate는 그 구현체, Spring Data JPA는 repository 추상화다. 영속성 컨텍스트는 트랜잭션 안에서 식별자별 같은 entity 인스턴스를 관리하고 변경 감지로 상태 변화를 SQL로 반영한다. 이는 동일 조회를 항상 빠르게 만드는 범용 캐시가 아니라 **트랜잭션 내 객체 동일성과 변경 관리 수단**으로 설명한다.

회원·가이드북·일정·지갑처럼 관계형 CRUD와 상태 변경이 많은 현재 서비스는 JDBC/MyBatis로 모든 매핑·저장 SQL을 반복 작성하는 것보다 JPA로 업무 상태 변경을 표현하는 편이 유리하다. 다만 ERD의 모든 FK를 JPA 연관관계로 기계적으로 복사하지 않는다. 생명주기와 트랜잭션이 밀접한 객체만 연관관계로 매핑하고, 도메인 경계를 넘는 참조는 ID로 보관하는 방식을 우선 검토한다.

일반 CRUD는 Spring Data JPA를 사용하고 복잡한 지도 조회·랭킹 집계·조건부 업데이트·대량 처리는 JPQL·native SQL·JDBC를 병행한다. 생성 컬럼은 read-only 매핑하고 POINT 매핑은 Hibernate Spatial로 PoC한다. N+1, lazy loading, 불필요한 dirty checking과 실제 생성 SQL을 통합 테스트·쿼리 로그·실행 계획으로 검증한다. JPA만으로 모든 SQL을 숨기려 하지 않는다.

DTO와 entity는 분리한다. BIGINT 식별자의 JSON 문자열화, null/0/false 구분, UTC 직렬화, PDF의 별도 Content-Type을 계약 테스트한다. `guidebooks.version`은 재생성 버전이므로 일반 `@Version` 낙관 잠금 컬럼으로 재사용하지 않는다.

Flyway를 스키마 변경 이력 관리 도구로 선택한다. ERDCloud_schema.sql은 다이어그램 import용 원본이므로 실제 MySQL에서 실행·검증한 migration으로 옮겨야 한다. ORM의 자동 DDL 변경을 운영 배포의 기준으로 삼지 않는다. MySQL 지원 모듈과 JDBC 드라이버의 구성도 선택 버전에 맞춰 확인한다. [Flyway MySQL 지원](https://documentation.red-gate.com/flyway/reference/database-driver-reference/mysql)

운영 변경은 컬럼 추가 → 데이터 이관 → 구 코드 호환 확인 → 이전 컬럼 제거 순서를 검토한다. MySQL DDL의 implicit commit과 작업별 잠금 영향을 고려해야 하며, 애플리케이션 롤백이 DB 변경을 자동 복구하지 않는다. [MySQL 암시적 커밋](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html)

## 10. AI 비동기 작업과 생성권

이 서비스의 비동기 대상은 AI 최초 생성·재생성, 관광 데이터 수집, 랭킹 재집계, 알림·푸시다. PDF는 현재 API 계약상 동기이며 처리 시간·메모리가 한계를 넘을 때만 작업 ID 기반으로 전환한다. '비동기'는 스레드 하나를 더 만드는 것만을 뜻하지 않고, HTTP 요청의 수명과 장시간 작업의 수명을 분리해 상태·재시도·복구를 저장하는 것을 포함한다.

### 현재 데이터로 표현 가능한 범위

generation_jobs에는 요청 스냅샷, 상태, attempt_count, 시작/완료 시각과 오류가 있다. 다음 실행 시각·worker 소유권·lease 만료·heartbeat·별도 결과 보관 컬럼은 없다. 따라서 ‘DB job 테이블만으로 완전한 내구성 큐와 재시작 복구가 구현된다’고 쓰지 않는다.

### 권장 처리 흐름

1. 회원·요청 멱등 키를 확인한다. 동일 재요청이면 저장된 작업을 반환한다.
2. 짧은 트랜잭션에서 지갑 행을 잠그고 잔액≥1 및 활성 작업 부재를 검사한 뒤 PENDING 작업을 저장한다. 이때 잔액은 바꾸지 않는다.
3. 제한된 worker가 작업을 조건부 선점하고 PROCESSING으로 변경한다. 선점 트랜잭션을 종료한 뒤 AI를 호출한다.
4. 결과 JSON·기간·콘텐츠·순서를 검증한다. 성공 시 가이드북/일정·COMPLETED·잔액 -1·CONSUME를 한 번에 커밋한다.
5. 최종 실패는 FAILED만 반영하고 차감하지 않는다. 재생성 실패라면 기존 결과를 보존한다.

지갑의 `reserved_count`나 RESERVE/RELEASE 원장은 사용하지 않는다. 논리 예약은 PENDING/PROCESSING 작업으로 표현한다. 회수·관리자 조정도 같은 잠금 규칙으로 마지막 1개를 보호해야 한다.

### 복구에서 결정할 사항

- 단일 worker로 시작할지, 다중 worker를 지원할지와 선점 경쟁 처리.
- 서버 종료 후 PROCESSING 작업의 완료 여부를 AI에 조회할 수 있는지.
- 단순 타임아웃 재실행으로 이전 작업과 중복 실행되지 않게 할 장치.
- BR-GDE-16·DEC-09에 따라 시도당 300초, 추가 재시도 최대 3회(최초 포함 4회), attempt_count는 재시도 횟수 0~3을 적용한다. 재시도 간격·백오프와 전체 작업 시간 제한은 별도 결정한다. 워커와 HTTP 라이브러리가 재시도를 중첩하지 않도록 한다.
- 결과 수신 후 DB 저장 실패 시 동일 결과를 재전달/재조회할 계약.

필요하면 lease·작업 결과 저장 등의 확장을 제안하되 이번 문서에서 기존 컬럼인 것처럼 추가하지 않는다. `@Async`는 실행 수단이지 프로세스 종료 후 복구 저장소가 아니다. AI 모델·프롬프트 버전·사용량은 현재 전용 컬럼이 없으므로 합의한 JSON/로그로 수집할지 따로 정한다.

### 프론트·백엔드·AI 통신 경계

기본 원칙은 백엔드가 AI 생성 완료까지 사용자의 초기 HTTP 요청을 장시간 점유하지 않는 것이다. 현재 API의 `202 Accepted + job_id + 상태 조회`는 유지하며 구체적인 전달 방식은 다음과 같이 구분한다.

| 구간 | 초기 구현 | 향후 후보 | 판단 기준 |
|---|---|---|---|
| 프론트 → 백엔드 | 생성 요청 후 202/job_id 수신 | 동일 | 장시간 요청에서 분리 |
| 프론트 ← 백엔드 | 상태 API polling | SSE + 상태 API 복구 | 폴링 부하·완료 알림 지연이 실제 문제일 때 SSE |
| 백엔드 → AI | 내부 요청 계약 확정 필요 | 비동기 접수 + webhook 우선 비교 | AI가 장시간 연결을 요구하지 않고 대상 BE를 명확히 호출할 수 있는지 |
| 백엔드 ← AI | 폴링·webhook·SSE 중 미확정 | webhook + 상태 재조회 권장 후보 | 서명·job_id·중복 콜백·늦은 응답·재시도 계약 필수 |

SSE는 서버에서 클라이언트로 보내는 단방향 장기 연결이다. WebSocket은 양방향 실시간 통신이 핵심일 때 적합하다. 현재 프론트는 작업 상태를 주로 수신하므로 SSE가 WebSocket보다 작은 후보다. 다만 SSE를 선택해도 연결 단절·재접속을 감안해 상태 API를 복구 기준으로 유지한다.

백엔드–AI 간에는 완성 결과만 필요하고 AI가 백엔드 주소를 호출할 수 있다면 webhook이 장기 연결을 피할 수 있다. 중간 token·진행률을 실시간으로 소비해야 할 때만 SSE/streaming 응답의 이점이 커진다. 어떤 방식을 선택해도 MySQL의 `generation_jobs`가 최종 상태와 재접속 복구의 기준이다. 백엔드–AI 통신 방식을 변경하면 V3 API의 내부 AI 계약과 요구사항을 함께 갱신한다.

### 큐·브로커 선택 경계

큐는 작업 폭증을 버퍼링하고 producer와 consumer를 분리하며, 재시도·acknowledgement·실패 작업 보관을 통해 프로세스 종료 후에도 작업을 복구하기 위해 사용한다. 현재는 `generation_jobs`가 작업 상태를 저장하므로 SQS·RabbitMQ·Kafka를 초기 의존성으로 추가하지 않는다.

- SQS는 AWS 관리형 큐가 필요하고 복수 consumer가 작업을 확장 처리할 때의 후보다.
- RabbitMQ는 routing·ack·재시도·DLQ가 필요한 작업 큐 후보다.
- Kafka는 다수 consumer가 독립적으로 재생할 대규모 이벤트 로그·스트리밍이 필요할 때의 후보이며 현재 AI 작업 하나를 위해 도입하지 않는다.

DB polling의 선점 경쟁·지연·부하·고아 `PROCESSING` 복구가 현재 목표를 충족하지 못하거나 worker를 독립 확장해야 할 때 큐 제품을 선택한다. '유실을 막아야 한다'는 목표만으로 제품을 선택하지 않고, delivery semantics·중복 소비·순서·DLQ·운영 환경을 함께 결정한다.

## 11. 평가·랭킹·스케줄러

평가 초안은 프론트 상태로 관리하고 최종 ratings 배열을 한 번에 제출한다. 별점은 회원·장소별 현재값이므로 여행별 과거 제출 원문을 복원하는 이력 테이블로 사용하지 않는다. 부분 제출·기존 점수의 덮어쓰기·제출 후 수정은 DEC-05와 API 논의 항목이다.

랭킹은 서비스가 변경 지역과 전국을 판단하고, 커밋 후 스케줄러 또는 백그라운드 작업으로 계산한다. DB 트리거나 평가 요청 안 전체 집계는 현재 선택이 아니다. 같은 기간·범위의 snapshot과 entries는 한 트랜잭션으로 교체한다.

`place_ratings.updated_at` 변경 탐지가 현재 MVP 방향이다. 이 값은 집계 기간 귀속 시각과 다른 개념이다. 워터마크 저장 위치·지연 커밋·동일 시각·콘텐츠 비활성화·점수 삭제로 누락되는 경우를 검증해야 한다. 주기적 재집계나 겹침 구간 재조회는 후보이며 주기와 비용을 합의한다.

Spring Scheduling을 사용한다. DEC-03에 따라 Asia/Seoul 기준 일간 00시·주간 월요일 00시·월간 1일 00시를 기간 경계로 삼되, 갱신은 10분마다 수행하며 최대 반영 지연 10분을 검증한다. 초안의 ‘다음 날 00시 반영’은 현재 요구사항과 충돌하므로 채택하지 않는다.

다중 인스턴스에서는 각 서버가 같은 집계를 실행할 수 있어 MySQL 기반 ShedLock을 조건부로 검토한다. 단일 서버에는 필수가 아니다. 잠금 유효 시간·작업 시간 초과·재시작과 중복 결과 반영을 함께 검증하며 정확히 한 번 처리된다고 가정하지 않는다. 메시지 브로커는 작업 전달·소비자 확장이 필요한 별도 선택이지 ShedLock의 다음 단계가 아니다. Spring Batch·Quartz는 재시작/체크포인트·복잡한 스케줄 요구가 확인될 때 비교한다. 현재 스키마에 이 도구들의 메타데이터 테이블이 있다고 가정하지 않는다.

C·m·공식 버전은 현재 애플리케이션 설정이며 과거 결과 완전 재현은 MVP 제외다. 응답의 calculated_at으로 마지막 반영 시점을 알리고 최대 반영 지연 10분을 측정한다. C·m 값 자체는 추가 결정이 필요하다.

## 12. 인증·보안·알림

### 인증과 소유권

Spring Security를 인증·인가 기반으로 사용한다. 웹 Authorization Code + `oauth2Login()`을 사용하며 시작·콜백·코드 교환을 백엔드에서 처리한다. Google OIDC와 Kakao OAuth 사용자 정보 매핑을 구성한다. 식별자는 `oauth_provider + oauth_subject`이고 서비스 로그인은 `auth_sessions`에 저장한 서버 세션과 HttpOnly 쿠키로 관리한다. 서비스 액세스·리프레시 토큰은 발급하지 않는다. 별도 기기 ID와 자체 약관 동의 이력은 현재 없다.

불투명한 세션 ID는 쿠키에만 두고 DB에는 해시를 저장한다. 매 요청 DB 조회 비용은 발생하지만 로그아웃·탈퇴 시 즉시 폐기할 수 있고 현재 MySQL/JPA 기반 구조와 단순하게 맞는다. 다중 인스턴스에서도 같은 DB를 세션 저장소로 사용하는 방향이다. 초안의 직접 구현 대 Spring Session JDBC는 구현 방식 검토 항목으로 남긴다. 현재 API·테이블 계약은 auth_sessions의 해시 기반 저장이므로 Spring Session 표준 테이블이 이를 자동 대체한다고 가정하지 않는다. 전환 결정 시 스키마·쿠키·폐기·마이그레이션 계약을 함께 갱신하고 두 저장 방식을 중복 구현하지 않는다.

OAuth는 API-DEC-01로 확정했다. state·PKCE S256 verifier를 서버 HttpSession 기반 시도 저장소에 10분 보관하고 브라우저·provider 결속과 원자적 일회 소비를 검증한다. 로그인 시작/콜백은 MEM-01/15, 성공 후 서비스 세션 쿠키는 HttpOnly·Secure·SameSite=Lax를 적용한다. 로그인 전 HttpSession과 로그인 후 auth_sessions를 연결하는 구현은 별도이며 다중 서버 배포 전 임시 저장소 공유가 필요하다. Spring 버전과 두 공급자의 S256 실패 검증은 배포 전 테스트 항목이다. 서비스 세션 수명·연장·동시 로그인 수와 CSRF 토큰 전달 계약·배포 origin은 별도 운영/구현 결정으로 남긴다. 소유권은 모든 상세·수정·삭제·PDF·작업 상태 조회에서 검사한다. 난수 ID는 권한 검사를 대신하지 않는다.

### 알림과 푸시

인앱 알림은 회원 하위 책임이며 읽으면 DELETE한다. push_enabled=false여도 필요한 인앱 알림은 남긴다. FCM 등의 푸시 제품은 후보이며 현재 스키마에는 기기 토큰/웹 푸시 구독 저장 구조가 없다. 실제 푸시를 제공하려면 대상 플랫폼·구독 등록/폐기·저장 모델을 함께 정해야 한다.

BR-NOT-01~02에 따라 원본 업무 커밋 후 별도 트랜잭션으로 알림을 생성한다. 제한 재시도 후 실패는 로그·모니터링에 남기고 원본을 롤백하지 않는다. 영속 Outbox가 없으므로 커밋 후 프로세스 종료 시 알림 누락 복구는 보장하지 않는다. 같은 트랜잭션에서 발생한 오류를 단순히 catch하는 것으로 분리했다고 간주하지 않는다.

웹 푸시를 MVP에 포함하면 FCM/Firebase Admin SDK를 후보로 사용한다. 포함 여부·구독 저장 구조·여러 브라우저 중복 처리·토큰 폐기·재시도 간격을 먼저 정한다. 푸시 실패는 인앱 저장과 원본 업무를 롤백하지 않으며 인앱만 제공하면 SDK를 추가하지 않는다.

### Outbox의 위치

기존 문서의 ‘초기 필수 Outbox’는 철회하고 **조건부 도입**으로 바꾼다. 최신 요구사항은 MVP에 범용 사건 ID/큐 없이 원본 멱등 처리를 우선하며, 유실 방지가 더 필요해지면 Outbox를 검토한다. 현재 SQL에 outbox 테이블은 없다. 도입 시 저장 구조·publisher·중복 소비·청소 정책까지 함께 설계해야 한다.

## 13. PDF·HTML·파일 저장

현재 계약은 POST 내보내기 → 성공 200 `application/pdf`, 실패 JSON 오류다. export_id·PDF 상태 조회·파일 영구 보관을 전제로 하지 않는다. 동기 응답이어도 렌더러 시간/동시성/메모리 제한과 임시 파일 정리는 필요하다.

| 후보 | 장점 | 감수할 점 | 선택을 위한 실험 |
|---|---|---|---|
| Chromium/Playwright 계열 | 브라우저 HTML/CSS와 가까운 출력 | 런타임 이미지·메모리·프로세스 관리 | 한글·이미지·지도·페이지 분할·동시 처리 |
| OpenHTMLtoPDF 등 JVM PDF 렌더러 | JVM 중심 배포로 구성 가능 | 지원 CSS·글꼴·레이아웃 제약 | 실제 가이드북 템플릿 출력 비교 |
| 외부 PDF 서비스 | 자체 렌더러 운영 감소 | 비용·개인정보 전송·공급자 장애 | 허용 데이터와 비용·장애 대응 확인 |

렌더러는 PoC 전 확정하지 않는다. HTML 정제에는 OWASP Java HTML Sanitizer를 검토한다. HTML은 AI가 생성했더라도 신뢰하지 않는다. 스크립트·이벤트 핸들러를 제거하고, 서버 렌더러가 내부 IP/메타데이터 URL에 접근하지 못하도록 외부 리소스 로딩을 제한한다. 한글 글꼴의 배포 권한과 지도 이미지 사용 조건도 확인한다.

현재 HTML 본문은 guidebooks.content_html, 이미지 정보는 외부 URL로 저장한다. 따라서 S3 호환 스토리지는 기본 필수가 아니다. 보관·재다운로드·이미지 자체 호스팅 또는 PDF 비동기화가 결정되면 object key·만료·권한·삭제 정책과 비용을 함께 설계한다. 현재 DB에 해당 파일 메타데이터가 저장된다고 쓰지 않는다.

## 14. 외부 호출과 PG

관광·OAuth·AI·PG·푸시는 어댑터로 분리하고 외부 DTO를 내부 모델에 직접 확산시키지 않는다. 동기 HTTP 클라이언트는 Spring RestClient를 선택하되 연결/응답 시간 제한·호출 수 제한·오류 분류는 필수다. Resilience4j는 회로 차단·백오프 등 필요한 기능을 확인한 뒤 추가한다.

관광 API는 마지막 정상 데이터를 DB에 저장해 공급자 장애 시 조회를 유지한다. 제공처+콘텐츠 ID로 중복 수집을 막고 사라진 콘텐츠는 비활성화한다. 좌표·URL 길이·카테고리 검증과 수집 실패 격리가 필요하다.

PG는 공급자 결정 전이다. 주문 금액은 서버 상품 스냅샷이며, 검증된 승인만 PAID·PURCHASE_GRANT에 반영한다. 외부 호출과 DB 변경은 하나의 로컬 트랜잭션이 아니므로 승인 재조회와 원장 재처리가 필요하다. 부작용이 있는 승인 POST는 무조건 자동 재시도하지 않는다.

현재 payment_attempts에는 결제 시도 요청 멱등 키가 없고, 문서에 언급된 별도 웹훅 처리 키도 저장 위치가 정해지지 않았다. 공급자 계약과 함께 확정해야 한다. 환불은 MVP 이후이며 초기 환불 SDK·테이블·보상 원장을 필수 목록에 넣지 않는다. 테스트용 stub은 장애 재현 도구이지 실제 PG 연동 완료의 대체물이 아니다.

## 15. 프론트엔드 후보와 API 문서화

프론트 스택은 해당 팀이 결정한다. 아래는 현재 요구와 연결한 비교 기준이지 확정된 채택 목록이 아니다.

| 영역 | 후보/방향 | 현재 요구와 연결 |
|---|---|---|
| 언어 | TypeScript | Enum·ID 문자열·nullable 점수·작업 상태 표현 |
| 화면 | React + Vite SPA, 필요 시 Next.js 비교 | 공개 공유 SEO/미리보기 필요성과 배포 대상에 따라 선택 |
| 서버 상태 | TanStack Query 등 | 생성 상태 polling·목록 캐시·오류 분리, mutation 무조건 재시도 금지 |
| 로컬 상태 | React state 우선, 필요 시 상태 라이브러리 | 지도 범위·모달·제출 전 평가 초안 |
| 라우팅·지도 | 팀 라우터 + 공급자 SDK | ONBOARDING/ACTIVE 분기·공유 복귀·위치 권한 UX |
| 오프라인 | 별도 범위 확정 후 검토 | 로컬 캐시와 서버 초안 저장을 혼동하지 않음 |

현재 계약은 Excel과 V3 API Markdown에 있고 이유는 API 설계 근거.md에 분리되어 있다. 존재 여부·검토가 확인되지 않은 openapi.yaml을 이미 단일 기준인 것처럼 선언하지 않는다. OpenAPI 3.1 계열은 도입 후보이며 명세 전환 후 요청/응답 schema와 실제 생성 문서의 차이를 검사한다.

springdoc-openapi를 문서화 도구로 선정한다. 정확한 버전은 Boot와 함께 고정하며 OpenAPI 파일 형식·관리 흐름은 별도 정한다. OpenAPI·springdoc 검증에는 204 무본문, PDF 바이너리/실패 JSON, 정수 0~5와 null, ID 문자열, 오류 code, 인증·공개 경로를 포함한다. 도구가 생성하는 schema만으로 소유권·멱등성·트랜잭션이 검증되는 것은 아니다.

### 테스트 도구와 검증 범위

| JUnit/AssertJ, 선택적 Mockito | 단위 로직 | 기간 1~7일·Enum 계층·0점/null·상태 전이 |
| Spring Boot Test/MockMvc | API 계약 | 인증·소유권·HTTP 코드·직렬화·PDF |
| Testcontainers MySQL | 실제 DB 통합 | GENERATED/UNIQUE/POINT/FK·행 잠금·migration |
| WireMock | 외부 장애 | 타임아웃·잘못된 AI JSON·중복/역순 응답 |

| ArchUnit·OpenAPI 검사 | 구조·계약 | 도메인 의존 규칙과 문서/실제 응답 일치 |

Testcontainers는 MySQL 컨테이너 실행을 지원한다. H2로 공간 타입·MySQL 제약·잠금 의미까지 검증했다고 대체하지 않는다. [Testcontainers MySQL](https://java.testcontainers.org/modules/databases/mysql/)

필수 통합 시나리오는 잔액 1개에 동시 생성, 동일 작업 완료 중복, 재생성 저장 실패 시 원본 유지, 다른 링크의 동일 원본 가져오기, 탈퇴/삭제와 진행 작업 경합, 0점/null 제출, 집계 중 실패, PG 중복 지급 방지다. PDF 동기 실패와 알림 실패가 원본을 손상시키지 않는지도 확인한다.

### 관측성

Actuator·Micrometer와 구조화 로그를 권장한다. HTTP 오류율/p95, DB 커넥션·잠금 대기, PENDING/PROCESSING 작업 수·체류 시간, AI 실패/시도 수, PDF 시간/메모리, 랭킹 calculated_at 지연, 원장 반영 실패를 측정한다.

### 로드밸런서 헬스체크: API-OPS-01

NFR-OPS-05~06과 d96b07c1의 계약에 따라 Spring Boot Actuator를 사용한다.

| 항목 | 구현 계약 |
|---|---|
| 경로·메서드 | GET /actuator/health. 업무 API의 /api/v1 prefix 제외 |
| 인증 | 세션 인증 없음. 가능하면 로드밸런서·배포 인프라 네트워크로 접근 제한 |
| 포함 | 애플리케이션과 MySQL 연결 등 필수 의존성의 요청 처리 가능 상태 |
| 제외 | AI·관광·PG·푸시 공급자. 별도 메트릭·경보로 감시 |
| 정상 | UP → 200, {"status":"UP"} |
| 비정상 | DOWN 또는 OUT_OF_SERVICE → 503, 상태만 반환 |
| 응답 예외 | 일반 업무 API의 {message,data} wrapper 적용 안 함 |
| 정보 제한 | DB URL·자격증명·예외 상세·컴포넌트 상세를 노출하지 않음 |

외부 공급자 장애를 이유로 정상 BE 인스턴스까지 트래픽에서 제외하지 않는다. 포함할 health contributor와 응답 상세 설정을 명시적으로 검증한다. LB 검사 주기·timeout·연속 실패/성공 기준은 배포 환경에서 결정한다. 이 계약을 프로세스 재시작용 liveness와 동일시하지 않는다.

Micrometer로 계측하되 Prometheus를 사용하기로 결정한 경우에만 대응 registry를 추가한다. 메트릭·로그 수집 제품과 경보 임계값은 미확정이다.

HTTP는 request/trace ID, AI는 job_id, 결제는 주문/시도/PG 거래 ID로 연결한다. 동기 PDF에는 요청 ID를 사용하고, 범용 배치에는 실행 로그 ID를 둘 수 있으나 이를 현재 job 테이블이나 outbox event_id가 존재한다는 뜻으로 쓰지 않는다. 회원 ID 같은 내부 식별자도 접근과 보존을 제한하고 토큰·OAuth 코드·PG 원문을 로그에 남기지 않는다.

### 배포와 운영

Docker를 실행 환경 패키징 도구로 선택하고 GitHub Actions는 CI/CD 후보로 둔다. 로컬/CI/운영의 JDK와 MySQL 버전을 맞추고 단위·DB 통합·계약 검사 후 이미지와 migration을 검토한다. DB 백업은 생성 여부가 아니라 실제 복원 시간과 결과로 검증한다. 운영 계정·비밀키는 소스와 분리하고 관리 엔드포인트를 공개하지 않는다.

배포 플랫폼·가용 인스턴스·메모리·예산·백업 주기·RPO/RTO는 미확정이다. 단일 인스턴스는 단순하지만 배포/장애 중 가용성이 낮고, 다중 인스턴스는 worker/스케줄러 중복 실행 제어가 필요하다. Kubernetes는 이 요구가 구체화되기 전 필수로 선정하지 않는다.

| Caffeine | 초기 MySQL·HTTP 캐시로 시작 | 단일 인스턴스의 반복 조회가 DB/API 병목으로 측정 |
| Redis | 다중 인스턴스도 MySQL 세션을 공유할 수 있으므로 초기 필수 아님 | 공유 rate limit·캐시 무효화·SSE 신호·세션 조회 병목이 측정 |
| MongoDB | nullable 콘텐츠는 MySQL로 표현 가능, 초기는 MySQL JSON staging으로 원본 보존 | 다수 공급자의 대량·이종 원본 문서 보존·재처리가 독립 DB를 요구 |
| Outbox | 현재 테이블·publisher·consumer 멱등 계약이 없어 선정하지 않음 | DB 커밋과 외부 이벤트 발행 사이 유실을 허용할 수 없고 재시도·중복 소비·청소 정책을 함께 설계 |
| SQS/RabbitMQ/Kafka | 처리량·소비자 수·전달 의미·운영 환경 미확인 | DB 작업 선점·복구가 목표를 충족하지 못하거나 독립 worker·다중 consumer가 필요 |
| Elasticsearch/OpenSearch | 별도 색인 동기화 부담 | 검색 품질/성능 목표를 MySQL로 충족 못 함 |
| S3 호환 파일 저장소 | 동기 PDF·외부 이미지 URL로 시작 | 파일 보관·자체 호스팅·비동기 다운로드 결정 |
| Spring Batch/Quartz | 단순 집계에 메타데이터/운영 복잡성 추가 | 체크포인트·재시작·복잡한 스케줄 필요 |
| Kubernetes/마이크로서비스 | 현재 독립 운영 필요 미확인 | 배포·확장·조직 경계의 구체적 필요 |
