# AI 접수 트랜잭션 경계 변경 전후 부하테스트 (#305)

## 추가 실험: 변경 후 구조에 1분간 200건 (2026-10-30)

- 이전 변경 후 격리 BE·콜백 지원 fake AI 컨테이너를 재기동해 사용했다.
  이전 10건과 구분되는 사용자 201~400 및 고유 멱등 키로 새 작업 200건을 생성했다.
- k6 constant-arrival-rate: 분당 200건, 1분, 상태 폴링 없이 접수만 측정했다.
  AI 조건은 워커 3개, 생성 지연 60초, 대기 큐 100개로 유지했다.
- 200건 모두 실행됐고 dropped iteration은 0이었다. BE는 모두 202를 반환했다.
  생성 POST 평균 51.51ms, p95 91.86ms, p99 531.88ms였다.
- DB 이력 200건 중 AI ID가 저장된 작업은 103건이었다. 나머지 97건은 AI 큐 포화로
  503을 받았으며, AI queue_full 로그도 97건이었다. BE는 이를 접수 결과 불확실로
  분류해 PENDING과 타이머를 유지하고 FE에는 202를 반환했다. 자동 재접수는 없다.
- Hikari 250ms 간격 관측 최대 active 3, pending 0, 획득 timeout 증가 0이었다.
  샘플링 지표이며 순간적인 점유 피크를 모두 포착한다는 의미는 아니다.
- 집계 시점 상태는 COMPLETED 3, PROCESSING 3, PENDING 194였다.
  완료 처리량이나 15분 타임아웃 결과는 이번 1분 접수 실험에서 검증하지 않았다.
- 접수 HTTP 기준 k6 임계값은 통과했지만, 200건 모두 AI에 전달된 것은 아니다.
  커넥션 풀 고갈 대신 AI 수용량 초과와 BE의 503 처리 정책이 드러났다.
- 결과: `results/load-test/issue305-arrival200-20261030-k6.json`,
  `results/load-test/issue305-arrival200-20261030-hikari.json`.
  실행 스크립트: `/private/tmp/kgb-tx305-benchmark.tT8B4p/arrival-200.js`.
- 큐에 남은 작업과 타이머를 강제로 유실시키지 않도록 이번 격리 컨테이너는 실행 상태로
  유지했다. 기존의 다른 로컬 서버는 변경하지 않았다.

실행일: 2026-10-29. 관련 요구사항: BR-GDE-16, FR-GDE-01/07/08/09, NFR-AVL-03.

## 비교 조건

- 변경 전: dev의 PR #304 머지 커밋 `349108a`.
- 변경 후: `refactor/305-ai-submission-boundary` 작업 트리. 아직 커밋하지 않은 변경이다.
- 기존 `scripts/load-test/guidebook-generation.js` 재사용: 10 VU, 사용자당 생성 1회,
  2초 상태 폴링, 요청 시작부터 약 110초 제한. SSE 부하테스트가 아니다.
- 임시 wrapper는 POST/GET 지연 submetric만 추가하며 기존 실행·폴링·종료 조건은 유지한다.
- 양쪽 BE: 2 CPU, 메모리 2GB, Hikari 최대 10개. AI는 같은 콜백 지원 이미지
  `kgb-ai-callback-smoke:local`을 사용한다.
- AI: fake LLM, 생성 지연 60초, 워커 3개, 대기 큐 100개. 접수 HTTP 자체에는
  강제 지연을 넣지 않았다. 이번 부하에서 AI 큐 포화·503은 시험하지 않았다.
- fixture 회원 999명, 인증 우회 OFF. 별도 DB·Redis 네임스페이스에 동일한 지역정보와
  종로구 관광 콘텐츠 839건을 복사했다. BE의 AI 후보 상한은 요청당 100개다.
- 원래 실행 중이던 서버·DB 데이터는 변경하지 않았다. 두 격리 BE·AI 조합을 순차 부하로
  비교했으며 Hikari는 약 250ms 간격으로 118초 수집했다.

## 결과: 콜백 지원 이미지로 맞춘 A/B

| 지표 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| BE 접수 202 | 10/10 | 10/10 |
| 생성 POST 평균 | 30,621.64ms | 790.87ms |
| 생성 POST p95 | 30,720.49ms | 796.94ms |
| 생성 POST p99 | 30,797.42ms | 798.66ms |
| Hikari 커넥션 획득 timeout 증가 | 9건 | 0건 |
| 관측된 Hikari pending 최대 | 10 | 0 |
| 실제 AI 접수 확인(AI ID 저장) | 1/10 | 10/10 |
| k6 제한 시간 내 완료 | 1건 | 3건 |
| k6 제한 시간 초과 | 9건 | 7건 |
| HTTP 오류율 | 0% | 0% |

POST p95는 이 실행에서 약 97.4% 감소했다. 표본은 각 10개이고 단일 A/B 1회이므로
운영 처리량·보편적인 성능 개선율로 해석하지 않는다.

### 변경 전 병목

동기 AFTER_COMMIT 리스너가 원래 트랜잭션의 커넥션 정리 전에
REQUIRES_NEW 트랜잭션의 추가 커넥션을 요청한다. 10개 풀을 채운 동시 접수에서
추가 커넥션 확보가 대기하고 약 30초 뒤 timeout이 발생했다.

로그에는 `Connection is not available, request timed out after 30009ms`가 기록됐다.
테스트 종료 시 DB는 COMPLETED 1건, PENDING 9건이었고, 남은 9건은 AI ID와
attempt_started_at이 모두 없었다. BE가 202를 반환했어도 AI 접수까지 진행하지 못한 것이다.

### 변경 후와 남은 AI 큐 대기

10건 모두 AI ID를 받았으며 커넥션 획득 timeout은 없었다. k6 종료 후에도 큐 처리를
관찰해 **10건 전부 COMPLETED, 서버 FAILED 0건**을 확인했다.

- DB 기준 완료 시간은 약 60.53초 → 120.71초 → 180.82초 → 240.79초였다.
- AI 진행·완료 콜백 30회는 전부 HTTP 204였다.
- 생성권 차감 원장 10건, 실제 잔액 감소 10개, 완료 알림 10건을 확인했다.

워커 3개가 60초 작업 10개를 처리하므로 기존 110초 검증 창에는 첫 3개만 완료된다.
`generation_failed=7`은 이 실행에서 BE FAILED가 아니라 **클라이언트 관찰 시간 초과**다.
양쪽 k6는 기존 `generation_failed: count==0` 조건을 만족하지 못해 exit code 99로 종료됐다.
이를 전체 부하테스트 통과로 표기하지 않는다.

Hikari 샘플링에서 변경 후 active/pending 최대는 0이었지만, 짧은 DB 조회·쓰기 점유는
샘플 사이에 누락될 수 있다. DB를 커넥션 없이 처리했다는 뜻이 아니다. HTTP 대기 중
트랜잭션·커넥션을 보유하지 않는 경계는 별도의 단일 풀 MySQL 통합 테스트로도 검증했다.

## 실행 중 발견한 환경 문제

처음에는 기존 부하테스트 AI 이미지 `kgb-ai-loadtest:local`을 재사용했으나 이 이미지에는
콜백 구현이 없었다. 해당 시도에서는 변경 후 10건을 AI가 접수해도 BE가 결과를 받지 못했다.
이 시도를 E2E 결과에서 제외하고, 위 비교는 양쪽 모두 콜백 지원 이미지로 재실행한 결과다.
초기 시도의 JSON도 진단 기록으로 별도 보관했다.
