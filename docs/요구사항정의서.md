# **V3 요구사항정의서**

## **0단계 프로젝트 요구사항 분석**

> 이 문서는 V3 화면설계서와 기능정의서를 개발 관점에서 해석한 설계 초안이다.
> 
> 
> 확정되지 않은 내용은 **결정 필요**로 표시하며, 이후 ERD·API·테크스펙은 본 문서의 용어와 요구사항 ID를 기준으로 연결한다.
> 

### **1. 문서 목적**

V3 서비스의 업무 영역을 5개 도메인으로 구분하고 각 도메인의 책임과 데이터 소유권을 정한다.

화면 단위 설명을 개발 가능한 비즈니스 규칙과 기능·비기능 요구사항으로 변환한다.

ERD, API, 배치 작업, 외부 연동 설계가 어떤 요구사항에서 시작됐는지 추적할 수 있게 한다.

정상 동작뿐 아니라 중복 요청, 실패, 경계값, 복구가 필요한 상황을 미리 정의한다.

PL 미팅에서 “왜 이렇게 나눴는가”와 “어떤 선택을 했는가”를 설명할 근거로 사용한다.

### **2. 분석 범위와 전제**

#### **2.1 기준 범위**

Figma의 **V3 프레임 내부 화면**을 우선 기준으로 한다.

V1·V2는 V3에서 의미가 불명확할 때 참고만 하며, V3 요구사항으로 자동 승계하지 않는다.

화면에 보인다는 이유만으로 별도 도메인이나 영속 엔티티로 만들지 않는다.

결제처럼 V3에 정책 화면만 있더라도 생성권과 직접 연결된 핵심 업무는 설계 범위에 포함한다.

#### **2.2 도메인 분리 기준**

도메인은 화면이나 메뉴가 아니라 다음 기준으로 나눈다.

함께 변경되는 비즈니스 규칙과 데이터인가?

해당 데이터의 생성·변경·삭제 권한을 한 책임 주체가 설명할 수 있는가?

독립적인 상태 전이와 정합성 규칙이 있는가?

다른 영역이 원본을 수정하는 대신 식별자로 참조할 수 있는가?

현재 팀 규모에서 별도 모듈로 나누는 실익이 복잡도보다 큰가?

#### **2.3 병합 결정과 트레이드오프**

| **병합 결정** | **선택 근거** | **감수할 단점** |
| --- | --- | --- |
| 취향 → 회원 | V3의 취향은 여행별 별도 객체가 아니라 회원의 현재 기본 취향으로 사용됨 | 추천 기능이 커지면 취향 모듈을 다시 분리해야 할 수 있음 |
| 서비스 설정 → 관련 도메인 | 언어·푸시 수신 설정은 회원, 결제 정책은 결제가 소유하는 편이 책임이 명확함. 이용약관·개인정보 처리방침은 정적 콘텐츠로 제공하고 서버에서 동의 이력을 관리하지 않음 | 정책 개정 동의 여부를 회원별로 추적하거나 재동의를 강제할 수 없음 |
| 탐색·지도 → 관광 콘텐츠 | 검색·필터·지도는 관광 콘텐츠의 대표 조회 방식이며 원본을 소유하지 않음 | 검색 인덱스가 커지면 별도 조회 모듈로 분리할 가능성이 있음 |
| 공유·가져오기 → 가이드북 | 공유 대상과 복제 결과가 모두 가이드북이며 독립 상품이 아님 | 공유 정책이 복잡해지면 가이드북 모듈이 커질 수 있음 |
| 평가·랭킹 유지 | 평가 원본의 무결성과 랭킹 집계·보정 규칙이 독립적임 | 관광 콘텐츠 조회 시 랭킹 데이터를 결합해야 함 |
| 알림 → 회원 | 알림은 수신 회원에게 귀속되고 V3 범위가 인앱 목록·삭제·푸시 설정 중심이라 독립 도메인으로 둘 실익이 작음 | 회원 모듈이 다른 도메인의 사건을 받는 접점이 되므로 내부 알림 패키지의 경계를 분명히 해야 함 |
| 생성권·결제 유지 | 금액·결제·잔액은 강한 정합성과 감사 이력이 필요함 | 외부 PG 연동과 생성권 차감·웹훅 재처리로 구현 복잡도가 큼 |

### **3. 도메인 개요**

| **ID** | **최종 도메인** | **병합 대상** | **핵심 책임** |
| --- | --- | --- | --- |
| DOM-01 | 회원 | 회원·인증 + 취향 + 알림 + 서비스 설정 일부 | OAuth, 회원, 프로필, 세션, 기본 취향, 언어 설정, 인앱 알림, 삭제, 푸시 수신 설정 |
| DOM-02 | 관광 콘텐츠·탐색 | 관광 콘텐츠 + 탐색·지도 | 장소·행사 원본, 검색, 필터, 현재 위치, 지도, 마커, 관심 장소 |
| DOM-03 | 가이드북 | 가이드북·일정 + 공유·가져오기 | 생성 조건, AI 생성, 일정, 공유 링크, 가져오기, HTML/PDF |
| DOM-04 | 평가·랭킹 | 기존 유지 | 여행 종료 후 평가, 별점, 집계, 일간·주간·월간 랭킹 |
| DOM-05 | 생성권·결제 | 기존 유지 | 생성권, 상품, 주문, 결제, 잔액 |

### **4. 도메인 상세 정의**

#### **4.1 DOM-01 회원**

**정의**

서비스를 사용하는 사람을 식별하고, 로그인 상태와 회원에게 지속적으로 귀속되는 기본 설정 및 사용자 대상 알림을 관리하는 영역이다.

**핵심 책임**

소셜 OAuth 인증과 공급자 사용자 식별자 관리: V1은 KAKAO, V2 이상은 KAKAO·GOOGLE 모두 지원. 회원당 하나의 소셜 계정 연결을 유지하며 다중 계정 연결은 별도 범위

회원 생성, 조회, 프로필 수정, 로그아웃, 탈퇴

액세스·리프레시 세션의 발급, 갱신, 폐기

최초 취향 선택과 마이페이지의 기본 취향 조회·수정

표시 언어 저장

평가 요청, 공유·가져오기, 가이드북 생성 완료 등의 인앱 알림 생성

미읽은 알림 목록 조회와 개별·전체 삭제

푸시 수신 설정 저장과 푸시 실패 처리

**소유 데이터**

Member(OAuth 식별 정보 포함), AuthSession

MemberPreference와 애플리케이션 취향 Enum

Notification

**경계**

콘텐츠 카테고리와 회원 취향은 별개다. 콘텐츠는 DOM-02의 단일 카테고리를 가지며, 회원 취향은 DOM-01이 Enum 코드로 관리한다.

푸시 수신 설정과 회원별 알림은 DOM-01 내부 알림 모듈이 소유하고, 결제 정책은 DOM-05가 소유한다. 이용약관·개인정보 처리방침은 정적 콘텐츠로 제공하며 회원별 동의 여부나 이력은 영속화하지 않는다.

알림은 다른 도메인의 성공 여부를 결정하지 않는다. 원본 업무 성공 후 발생한 사건을 받아 생성하며, 알림 생성·푸시 실패가 원본 업무를 롤백하지 않는다.

생성권 잔액은 회원 속성이 아니라 DOM-05의 원장으로 관리한다.

#### **4.2 DOM-02 관광 콘텐츠·탐색**

**정의**

장소·행사·문화유산·명소의 기준 정보를 보유하고, 사용자가 검색·필터·지도·랭킹 화면에서 이를 찾도록 제공하는 영역이다.

**핵심 책임**

외부 관광 데이터 수집·정규화·갱신

장소 및 행사의 명칭, 위치, 기간, 운영 정보, 이미지, 출처 관리

키워드 검색, 지역·월·카테고리 필터, 페이지네이션

현재 위치 및 지도 범위 기반 조회

마커·클러스터 표시용 조회 모델 제공

회원의 관심 장소 등록·해제

DOM-04가 만든 랭킹 결과와 관광 콘텐츠 상세정보 결합

**소유 데이터**

TourismContent, EventDetail

ContentImage, ContentSource, Location

FavoriteContent

**영속 데이터가 아닌 조회 모델**

SearchCondition, MapViewport, Marker, Cluster, SearchResult

**경계**

관광 콘텐츠의 원본 정보는 이 도메인만 변경한다.

가이드북 일정은 콘텐츠 ID를 참조하되 제목·위치 등 원본을 임의 변경하지 않는다.

별점 원본과 랭킹 순위는 DOM-04가 소유한다.

#### **4.3 DOM-03 가이드북**

**정의**

회원의 여행 조건과 기본 취향을 이용해 가이드북을 생성하고, 생성된 일정을 조회·공유·가져오기·내보내기 하는 영역이다. 사용자는 일정을 직접 편집하지 않고 자연어 피드백으로 재생성을 요청한다.

**핵심 책임**

여행 지역, 기간, 인원 등 생성 조건 검증

DOM-01의 현재 기본 취향 조회

생성권 잔액과 진행 중 작업을 확인해 AI 생성 작업을 시작하고, 생성 성공 시 생성권 차감을 요청한다.

기존 가이드북을 갱신하는 재생성 작업과 변경 이력 관리

AI가 생성한 일자별 일정과 방문 순서 저장·조회

관광 콘텐츠와 일정 항목 연결

공유 링크 발급·만료·미리보기

다른 회원의 가이드북 가져오기와 중복 처리

HTML 보기 및 PDF 생성·다운로드

**소유 데이터**

Guidebook, TripCondition, GenerationJob

ItineraryDay, ItineraryItem

ShareLink, GuidebookImport

**경계**

콘텐츠 원본은 DOM-02를 참조한다.

기본 취향 원본은 DOM-01을 조회한다.

생성권 잔액 확인과 생성 성공 시 차감은 DOM-05에 요청한다. DOM-03은 생성권 잔액을 직접 변경하지 않는다.

여행 종료 후 평가 원본은 DOM-04가 관리한다.

#### **4.4 DOM-04 평가·랭킹**

**정의**

종료된 여행의 일정에 포함된 장소에 대해 회원 평가를 수집하고, 평가 데이터를 보정·집계하여 일간·주간·월간 순위를 제공하는 영역이다.

**핵심 책임**

여행 종료 후 평가 가능 여부 판단

평가 안내 연기, 장소별 건너뛰기, 가이드북을 통한 재진입 상태 관리

방문 장소별 별점 입력·수정·제출

중복 제출 방지와 평가 원본 보존

일간·주간·월간 집계 구간 생성

베이지안 가중 평점 계산과 랭킹 스냅샷 제공

평가가 변경된 지역과 전국 범위의 랭킹 비동기 갱신

**소유 데이터**

GuidebookEvaluation, PlaceRating

RankingSnapshot, RankingEntry

**랭킹 산정**

표본이 적은 장소가 소수의 높은 별점만으로 상위에 오르는 현상을 줄이기 위해 다음 베이지안 가중 평균을 사용한다.

가중 평점 = (v / (v + m)) × R + (m / (v + m)) × C

R: 해당 장소 평균 평점

v: 해당 장소의 유효 평가 수

C: 같은 집계 대상 전체의 평균 평점

m: 신뢰 가능한 최소 평가 수

m 값과 동점 처리 기준은 운영 데이터 확인 후 확정한다. 랭킹 기간은 **일간·주간·월간을 제공**한다.

**경계**

별점은 이 도메인의 원본 데이터다.

랭킹은 별점 원본에서 계산된 파생 결과이며 관광 콘텐츠 원본을 수정하지 않는다.

평가 대상은 DOM-03 일정의 방문 장소와 DOM-02 관광 콘텐츠를 참조한다.

#### **4.5 DOM-05 생성권·결제**

**정의**

가이드북 생성에 필요한 사용 권한을 수량으로 관리하고, 상품 주문·결제 결과에 따라 잔액을 일관되게 변경하는 영역이다. 환불은 MVP 이후 범위다.

**핵심 책임**

무료·유료 생성권 지급과 잔액 조회

상품, 주문, 결제 시도, 결제 완료 관리

결제 검증과 웹훅 중복 처리

생성 요청 시 잔액과 회원별 진행 중 작업 확인

생성 성공 시 생성권 차감

MVP 이후 환불 가능 여부 판단과 환불 이력 관리

모든 증감 사유를 원장으로 보존

**소유 데이터**

CreditWallet, CreditTransaction, CreditProduct

Order, PaymentAttempt

**경계**

가이드북은 생성권 잔액을 직접 수정하지 않고 잔액 확인과 성공 차감만 요청한다.

결제 금액과 상품 구성은 서버 데이터가 기준이다.

PG 응답은 검증 전까지 결제 완료로 확정하지 않는다.

### **5. 도메인 관계와 데이터 소유권**

#### **5.1 핵심 관계**

DOM-01 회원
 ├─ 기본 취향 제공 ───────────────▶ DOM-03 가이드북
 ├─ 관심 장소 회원 식별 ──────────▶ DOM-02 관광 콘텐츠·탐색
 ├─ 사용자 식별 ─────────────────▶ DOM-04/05
 └─ 회원별 알림·삭제·푸시 설정 소유

DOM-02 관광 콘텐츠·탐색
 ├─ 장소 원본 제공 ───────────────▶ DOM-03 가이드북
 └─ 장소 원본 제공 ───────────────▶ DOM-04 평가·랭킹

DOM-03 가이드북
 ├─ 생성권 잔액 확인/성공 차감 요청 ─────────────▶ DOM-05 생성권·결제
 ├─ 여행 종료·방문 장소 제공 ───────▶ DOM-04 평가·랭킹
 └─ 생성/공유 사건 발행 ───────────▶ DOM-01 회원의 알림 모듈

DOM-04 평가·랭킹
 ├─ 랭킹 결과 제공 ───────────────▶ DOM-02 관광 콘텐츠·탐색
 └─ 평가 요청/완료 사건 발행 ───────▶ DOM-01 회원의 알림 모듈

#### **5.2 데이터 소유 원칙**

한 데이터의 최종 수정 권한은 하나의 도메인만 가진다.

다른 도메인은 원본을 복제해 수정하지 않고 식별자로 참조한다.

화면 응답은 여러 도메인의 데이터를 조합할 수 있으나, 조합 화면이 데이터 소유권을 갖지는 않는다.

랭킹·검색 결과처럼 재생성 가능한 데이터는 파생 데이터로 구분한다.

결제·생성권·평가 원본은 이력 보존이 중요하므로 물리 삭제보다 상태 전이와 감사 기록을 우선한다.

#### **5.3 공통 불변식**

탈퇴·정지 회원은 인증이 필요한 신규 작업을 수행할 수 없다.

존재하지 않거나 비공개인 관광 콘텐츠는 새 일정에 추가할 수 없다.

동일한 외부 결제 결과는 여러 번 수신돼도 잔액을 한 번만 변경한다.

한 회원에게 `PENDING` 또는 `PROCESSING` 생성 작업은 하나만 존재한다. 생성권은 생성 성공 시 한 번만 차감하고 실패·취소 시에는 잔액을 변경하지 않는다.

동일 회원은 동일 평가 세션의 동일 장소에 하나의 최종 별점만 가진다.

만료되었거나 존재하지 않는 공유 링크로는 가이드북을 가져올 수 없다.

알림 실패가 원본 업무의 성공을 취소하지 않는다.

### **7. 핵심 사용자 시나리오**

#### **US-01 가입과 초기 설정**

사용자는 V1에서 KAKAO, V2 이상에서 KAKAO 또는 GOOGLE로 가입한 뒤 기본 취향을 선택한다. 시스템은 회원·세션·기본 취향을 저장하고 메인 화면으로 이동시킨다. 이용약관·개인정보 처리방침 안내가 필요하면 정적 콘텐츠로 제공한다.

#### **US-02 관광 콘텐츠 탐색**

사용자는 검색어와 지역·월·카테고리 필터를 AND 조건으로 적용한다. 검색 결과를 목록이나 지도에서 확인하고 관심 장소를 저장할 수 있다.

#### **US-03 가이드북 생성**

사용자는 여행 조건을 입력한다. 시스템은 생성권 잔액과 진행 중 작업 유무를 원자적으로 확인한 뒤 회원 기본 취향과 관광 콘텐츠를 사용하여 AI 생성 작업을 수행한다. `PENDING`·`PROCESSING` 작업은 생성권 1개가 논리적으로 예약된 상태를 나타내지만 별도 예약 수량은 저장하지 않는다. 최초 생성에 성공하면 새로운 가이드북을 저장하고 같은 트랜잭션에서 생성권 1개를 차감한다. 실패하거나 취소되면 가이드북을 생성하지 않고 잔액도 변경하지 않는다. 사용자가 기존 결과를 재생성하면 기존 가이드북을 참조하는 새로운 생성 작업을 만들고 입력 스냅샷을 보존한다. 재생성 성공 시 기존 가이드북과 일정 내용을 원자적으로 갱신하고, 실패 시 기존 내용을 유지한다.

#### **US-04 초안 확인과 재생성**

사용자는 최초 생성된 가이드북 초안의 날짜별 추천 장소와 순서를 확인한다. 사용자가 변경을 원하면 일정 항목을 직접 추가·삭제·이동·수정하지 않고 자연어 피드백을 제출해 재생성을 요청한다. 재생성이 성공하면 같은 가이드북의 본문과 일정을 새 초안으로 교체하고, 실패하면 기존 초안을 유지한다. 각 일정 항목은 관광 콘텐츠 원본을 참조한다.

#### **US-05 공유와 가져오기**

사용자는 가이드북 공유 링크를 발급하거나 파일로 내보낸다. 로그인한 수신자는 유효한 링크를 열어 미리 본 뒤 자신의 가이드북으로 가져온다.

#### **US-06 여행 종료 후 평가**

일정 종료 다음 날 이후 첫 앱 접속 시 평가 안내가 표시된다. 모달에서 `다음에 하기`를 선택하면 자동 모달은 다시 표시하지 않지만 가이드북 목록의 평가 버튼으로 재진입할 수 있다. 평가 중에는 방문 장소를 일정 순서대로 확인하며, 0~5점을 입력하거나 해당 장소만 건너뛸 수 있다.

#### **US-07 랭킹 확인**

사용자는 랭킹 보기로 이동해 지역과 일간·주간·월간 조건을 선택한다. 시스템은 평가 수를 보정한 순위와 관광 콘텐츠 정보를 조합해 제공한다.

#### **US-08 생성권 구매**

사용자는 상품을 선택하고 결제한다. 서버가 PG 결과와 금액을 검증한 뒤 생성권 원장을 증가시킨다. 중복 콜백은 같은 거래로 처리한다.

### **8. 비즈니스 규칙**

#### **8.1 DOM-01 회원**

**BR-MEM-01** OAuth 공급자와 공급자 사용자 ID 조합은 중복될 수 없다. V1은 `KAKAO`만, V2 이상(V3 포함)은 `KAKAO`와 `GOOGLE`을 모두 지원한다. 두 공급자를 지원해도 한 회원에 여러 소셜 계정을 연결하는 것은 아니며, 이메일이 같다는 이유로 공급자가 다른 계정을 자동 병합하지 않는다.

**BR-MEM-02** 로그인 성공 후에만 인증 세션을 발급한다.

**BR-MEM-03** 탈퇴 회원의 활성 세션은 모두 폐기한다.

**BR-MEM-06** 회원은 하나의 현재 기본 취향 프로필을 가진다.

**BR-MEM-07** GUIDE-02에서 저장한 취향은 별도 여행 취향이 아니라 회원 기본 취향을 갱신한다.

**BR-MEM-08** 언어 설정이 없으면 서비스 기본 언어를 사용한다.

**BR-MEM-09** 탈퇴 상태에서는 신규 가이드북 생성, 평가, 결제를 허용하지 않는다.

**BR-MEM-10** 취향 선택지는 관리자 운영 데이터가 아닌 애플리케이션 Enum으로 관리하며, DB에는 회원이 실제 선택한 취향 유형과 코드만 저장한다.

**BR-MEM-11** 대분류는 최소 1개, 최대 3개까지 선택할 수 있다. 중분류는 연결된 대분류가 선택된 경우에만 저장하며, 대분류 해제 시 소속 중분류 선택도 함께 삭제한다.

**알림 하위 책임 규칙**

**BR-NOT-01** 알림 생성 실패는 원본 업무를 롤백하지 않는다.

**BR-NOT-02** 같은 업무 상태 전이를 반복 처리하더라도 동일 수신자에게 같은 알림을 중복 생성하지 않는다. MVP에서는 범용 원본 사건 ID나 메시지 큐 없이 원본 업무의 멱등 처리와 알림 생성 트랜잭션으로 보장한다.

**BR-NOT-03** 회원은 자신의 알림만 조회·삭제할 수 있다.

**BR-NOT-04** 알림을 읽으면 해당 알림 행을 삭제한다. 전체 삭제는 요청 시점에 존재하는 해당 회원의 알림을 대상으로 한다.

**BR-NOT-05** 푸시 수신 거부 시에도 필요한 인앱 알림은 저장할 수 있다.

**BR-NOT-06** 목록 최대 노출 수는 V3 기준 20개로 해석하되 초기 노출 개수는 4개이다.

#### **8.2 DOM-02 관광 콘텐츠·탐색**

**BR-CON-01** 관광 콘텐츠의 외부 출처 ID와 출처 조합은 유일해야 한다.

**BR-CON-02** 검색어와 복수 필터는 AND 조건으로 적용한다.

**BR-CON-03** 지역 ‘전체’, 월 ‘전체’는 해당 조건을 제한하지 않는 것과 같다.

**BR-CON-04** 월 필터는 기간을 가진 행사에 적용한다. 상시 장소에 대한 적용 방식은 별도 확정한다.

**BR-CON-05** 검색어는 최대 10자이며 엔터 입력 시 서버 검색을 수행한다.

**BR-CON-06** 결과가 없으면 검색·필터 공통 빈 상태를 제공한다.

**BR-CON-07** 관심 장소 등록은 회원과 관광 콘텐츠 조합당 하나만 존재한다.

**BR-CON-08** 현재 위치 권한이 허용되지 않은 채로 앱을 사용하려 하면 허용 요청 알림이 지속된다.

**BR-CON-09** 검색·필터·랭킹 조회는 관광 콘텐츠 원본을 변경하지 않는다.

**BR-CON-10** 관광 콘텐츠는 `EVENT`, `CULTURAL_HERITAGE`, `ATTRACTION` 중 하나의 카테고리만 가진다. 자연·미식·힐링 등의 대분류·중분류·여행 스타일은 콘텐츠 카테고리가 아니라 회원 취향이다.

**BR-CON-11** 지역 기준정보에는 17개 광역 시·도만 저장한다. 화면의 `전체`는 DB 행이 아니라 지역 조건을 적용하지 않는 조회 상태다.

**BR-CON-12** 외부 제공처에서 사라진 관광 콘텐츠는 물리 삭제하지 않고 비활성화한다. 비활성 콘텐츠는 검색·신규 가이드북 후보·신규 랭킹에서 제외하고, 기존 가이드북과 평가의 참조는 유지한다. 다시 수집되면 활성화할 수 있다.

#### **8.3 DOM-03 가이드북**

**BR-GDE-01** 시작일은 종료일보다 늦을 수 없으며 최대 여행 기간인 7일을 초과할 수 없다.

**BR-GDE-02** 유효한 여행 조건과 회원 기본 취향이 존재하고 생성권 잔액이 1개 이상이며 진행 중 생성 작업이 없어야 생성 작업을 시작한다.

**BR-GDE-03** 하나의 생성 요청 키는 하나의 생성 작업에만 대응하며, 한 회원은 동시에 하나의 생성 작업만 진행할 수 있다.

**BR-GDE-04** 최초 AI 생성이 성공하면 새로운 가이드북을 저장한다. 최초 생성에 실패하면 가이드북을 생성하지 않는다.

**BR-GDE-05** 생성이 최종 실패하거나 취소되면 생성권 잔액을 변경하지 않는다.

**BR-GDE-06** 일정 항목의 날짜는 가이드북 여행 기간 안에 있어야 한다.

**BR-GDE-07** AI 생성 결과의 같은 일자 내 방문 순서는 중복되지 않고 1부터 연속되어야 한다.

**BR-GDE-08** 공유 링크는 원문 ID를 노출하지 않는 난수 토큰을 사용하며 만료 시 사용할 수 없다.

**BR-GDE-09** 가져온 가이드북은 수신 회원이 소유하는 독립 복사본으로 저장한다. 원본 이후 변경은 복사본에 전파하지 않는다.

**BR-GDE-10** 동일 회원은 공유 링크가 다르거나 복사본이 다시 공유된 경우에도 같은 최초 원본 가이드북을 한 번만 가져올 수 있다. 중복 요청은 새 복사본을 만들지 않고 기존에 가져온 가이드북으로 안내한다.

**BR-GDE-11** PDF 생성 실패가 가이드북 원본 상태를 변경하지 않는다.

**BR-GDE-12** HTML/PDF에 포함되는 개인정보 범위는 최소화한다.

**BR-GDE-13** 사용자의 재생성 요청은 기존 가이드북과 공백이 아닌 자연어 피드백을 참조하는 새로운 생성 작업으로 처리한다. 재생성 작업은 `guidebook_id`, 피드백, 요청 시점의 입력 스냅샷을 보존한다. 성공하면 같은 가이드북 ID를 유지한 채 가이드북 본문과 일정을 하나의 트랜잭션으로 갱신하고 버전을 증가시킨다. 실패하면 기존 가이드북과 일정을 변경하지 않는다.

**BR-GDE-14** 사용자가 가이드북을 삭제하면 즉시 목록·상세에서 숨기고 공유 링크 접근을 차단하되, DB에는 소프트 삭제 상태로 두어 생성 작업·원장·평가 참조를 유지한다. 이미 가져간 독립 복사본은 삭제하지 않는다. 보존 기간 후 물리 삭제 또는 개인정보 제거 정책은 별도로 확정한다.

#### **8.4 DOM-04 평가·랭킹**

**BR-RNK-01** 일정 종료 다음 날 이후의 가이드북만 평가할 수 있다.

**BR-RNK-02** 평가 대상은 해당 가이드북 일정에 포함된 장소다. 시스템은 실제 방문 여부를 별도로 검증하지 않는다.

**BR-RNK-03** 별점은 0점부터 5점까지의 정수만 허용한다. 0점도 유효한 평가로 저장하고 평균과 랭킹 집계에 포함한다. 장소를 건너뛴 경우 점수는 `NULL`로 처리하고 유효 평가 수와 평균 계산에서 제외한다.

**BR-RNK-04** 이전·다음 이동 중 입력값을 보존하고 제출 전에는 수정할 수 있다. 별점을 선택한 상태에서 다음 장소로 이동하면 해당 점수를 반영한다.

**BR-RNK-05** 평가 안내 모달에서 `다음에 하기`를 선택하면 이후 앱 접속 시 자동 모달을 다시 표시하지 않는다. 평가를 포기한 것은 아니며 가이드북 목록의 평가 버튼을 통해 다시 시작할 수 있다.

**BR-RNK-06** 장소 평가에서 `이 장소 건너뛰기`를 선택하면 해당 장소의 점수를 `NULL`로 두고 다음 장소로 이동한다. 제출 전 이전 장소로 돌아가 점수를 입력하거나 변경할 수 있다.

**BR-RNK-07** 현재 V3에서는 같은 회원·관광 콘텐츠 조합의 최종 평가를 하나만 유지한다. 특정 여행·일정 항목별 반복 평가 이력은 이번 설계 범위에서 제외한다.

**BR-RNK-08** 제출 요청이 중복돼도 평가와 집계 반영은 한 번만 수행한다.

**BR-RNK-09** 랭킹은 베이지안 가중 평점을 기준으로 산정한다.

**BR-RNK-10** 랭킹 기간은 일간·주간·월간을 지원한다.

**BR-RNK-11** 유효 평가가 없는 집계 구간은 ‘랭킹 결과 없음’으로 제공한다.

**BR-RNK-12** 동점은 가중 평점, 유효 평가 수, 원평균, 콘텐츠 ID 등 확정된 보조 기준으로 안정 정렬한다.

**BR-RNK-13** 삭제·무효 처리된 평가와 점수가 `NULL`인 장소는 다음 집계에서 제외한다.

**BR-RNK-14** 장소 평가가 등록·수정되면 애플리케이션 서비스가 해당 장소의 지역을 확인하여 그 지역과 전국 랭킹을 갱신 대상으로 판단한다. 이 판단은 DB 트리거가 아니라 비즈니스 로직에서 수행한다.

**BR-RNK-15** 평점 저장 요청 안에서 랭킹 전체를 즉시 계산하지 않는다. 평점 트랜잭션이 커밋된 후 스케줄러 또는 비동기 작업이 변경된 지역과 전국 범위만 다시 계산한다. MVP에서는 `place_ratings.updated_at` 이후 변경된 지역을 조회하여 대상을 찾고, 갱신 요청 유실 방지가 필요해지면 별도 갱신 요청 또는 아웃박스 구조를 도입한다.

**BR-RNK-16** 랭킹 결과 저장 시 동일 기간·범위의 스냅샷과 항목은 하나의 트랜잭션으로 교체하여 조회 중 일부 결과만 노출되지 않도록 한다.

#### **8.5 DOM-05 생성권·결제**

**BR-PAY-01** 생성권 잔액은 회원 테이블이 아니라 회원별 생성권 지갑에서 관리한다. 생성권 예약 여부는 회원의 `PENDING` 또는 `PROCESSING` 생성 작업 존재 여부로 판단한다.

**BR-PAY-02** 원장 항목은 무료 지급·구매 지급·사용·회수·관리자 조정 사유와 처리 후 잔액을 기록한다. 각 원인은 멱등 키를 가져 같은 변경을 두 번 반영하지 않는다.

**BR-PAY-03** 생성권 잔액이 1개 미만이거나 해당 회원에게 진행 중 생성 작업이 있으면 새로운 AI 생성 작업을 시작하지 않는다.

**BR-PAY-04** 생성 요청 시 지갑 행을 잠그고 잔액을 확인한 뒤 진행 중 작업을 생성한다. 한 회원에게 진행 중 생성 작업은 하나만 허용하고, 생성 성공 트랜잭션에서 생성권 1개를 한 번만 차감한다. 생성 실패·취소는 잔액을 변경하지 않는다. 진행 중 작업이 있으면 다른 회수·조정이 성공 차감에 필요한 마지막 1개를 제거하지 못하게 한다.

**BR-PAY-05** 주문 금액은 클라이언트 값이 아니라 서버의 상품 정보로 검증한다.

**BR-PAY-06** 동일 PG 거래 ID 또는 멱등 키는 한 번만 결제 완료 처리한다.

**BR-PAY-07** 검증되지 않은 웹훅은 주문과 잔액을 변경하지 않는다.

**BR-PAY-08** 결제·원장 내역은 감사와 분쟁 대응을 위해 보존한다. 환불은 MVP 이후에 정책·상태·저장 구조·API를 함께 설계한다.

### **10. 비기능 요구사항**

#### **10.1 성능**

**NFR-PERF-01** 검색·필터·랭킹 목록 API는 정상 부하에서 p95 1초 이내를 목표로 한다.

**NFR-PERF-02** 지도 이동 중 조회는 디바운스와 영역 기반 요청을 사용하고 한 응답의 마커 수를 제한한다.

**NFR-PERF-03** AI 생성과 랭킹 집계는 동기 HTTP 요청을 장시간 점유하지 않도록 작업 단위로 처리한다. PDF는 MVP에서 동기 응답으로 생성하며 응답 대기 동안 프론트엔드가 로딩 상태를 표시하고, 처리 시간이 길어지면 작업 ID 기반 비동기로 전환한다.

**NFR-PERF-04** 랭킹은 요청마다 전체 평가를 계산하지 않고 스냅샷 또는 캐시를 사용한다.

#### **10.2 보안과 개인정보**

**NFR-SEC-01** OAuth 토큰, PG 비밀키, 서명키는 클라이언트와 로그에 노출하지 않는다.

**NFR-SEC-02** 모든 회원 데이터 조회·변경 API는 리소스 소유권을 검증한다.

**NFR-SEC-03** 공유 토큰은 추측이 어려운 난수이며 접근 시 `expires_at`을 검증한다.

**NFR-SEC-04** 결제 웹훅은 서명·거래 ID·금액·주문 상태를 검증한다.

**NFR-SEC-05** 로그와 내보내기 파일에는 불필요한 개인정보를 포함하지 않는다.

**NFR-SEC-06** 탈퇴 시 개인정보 파기와 법정 보존 데이터 분리를 지원한다.

**NFR-SEC-07** OAuth 응답은 로그인 시작 요청과 요청 브라우저에 결속해 검증하고, 공급자 혼동·인가 코드 탈취·재사용을 방어해야 한다. 검증 실패 시 회원/세션 및 서비스 토큰을 발급하지 않는다. state 저장·일회성·TTL, 공급자별 PKCE S256 적용과 verifier 보관, OIDC 사용 시 토큰 검증의 구체 방식은 API-DEC-01에서 결정한다. 이 항목은 공급자 지원 여부의 미확정이 아니라 보안 구현 방식의 미확정을 뜻한다.

#### **10.3 데이터 정합성**

**NFR-DAT-01** 회원, 평가, 가이드북, 원장 변경은 DB 제약과 트랜잭션으로 불변식을 보장한다.

**NFR-DAT-02** 결제 웹훅, 평가 제출, 생성 요청, 가져오기는 멱등 키 또는 유일 제약을 가진다.

**NFR-DAT-03** 외부 시스템과의 분산 작업은 재시도 가능한 상태와 보상 처리를 둔다.

**NFR-DAT-04** 랭킹 파생 데이터는 평가 원본과 집계 기간을 기준으로 재생성할 수 있어야 한다. 계산식 설정이 변경된 뒤 과거 결과를 완전히 동일하게 재현하는 기능은 MVP 범위에서 제외한다.

**NFR-DAT-05** 시각 데이터는 MySQL `DATETIME(6)`에 UTC로 저장하고 DB 세션과 JDBC 타임존도 UTC로 고정한다. 한국 사용자에게 표시할 때는 `Asia/Seoul`로 변환하며, API에서는 ISO 8601 오프셋을 포함해 전달한다. 날짜만 의미하는 여행일·행사일은 `DATE`를 사용한다.

#### **10.4 가용성과 복구**

**NFR-AVL-01** 외부 관광 API 장애 시 마지막 정상 데이터 또는 명확한 오류 상태를 제공한다.

**NFR-AVL-02** AI·PG·푸시 실패를 구분해 재시도 가능 여부를 기록한다.

**NFR-AVL-03** 작업 재시도 후에도 중복 가이드북, 중복 진행 작업, 중복 생성권 차감, 중복 알림이 생성되지 않아야 한다.

**NFR-AVL-04** 중요 데이터는 백업과 복원 절차를 갖고 복원 검증을 수행한다.

#### **10.5 확장성과 운영**

**NFR-OPS-01** 도메인별 패키지와 의존 방향을 구분해 추후 모듈 분리가 가능하게 한다.

**NFR-OPS-02** 생성 성공률, 생성 시간, 결제·웹훅 실패, 생성권 차감 실패, 랭킹 집계 실패, 푸시 실패를 모니터링한다.

**NFR-OPS-03** 모든 비동기 작업은 작업 ID, 회원 ID, 원인 ID를 이용해 추적 가능해야 한다.

**NFR-OPS-04** 운영자가 실패 작업과 원장 변경 이력을 조회할 수 있어야 한다.

### **11. 주요 상태 모델**

#### **11.1 회원**

ONBOARDING → ACTIVE

상태 전이와 별개로 세션은 즉시 폐기할 수 있어야 한다.

#### **11.2 가이드북 생성 작업**

```
GenerationJob
PENDING → PROCESSING → COMPLETED
                      └→ FAILED
```

최초 생성 작업이 `COMPLETED`로 전환될 때 새로운 가이드북을 생성한다. 재생성 작업이 `COMPLETED`로 전환될 때에는 기존 가이드북 ID를 유지하고 본문과 일정을 원자적으로 교체한다. 최초 생성이 `FAILED`이면 가이드북을 생성하지 않고, 재생성이 `FAILED`이면 기존 가이드북을 변경하지 않는다.

시스템 오류에 대한 재시도는 동일한 생성 작업에서 최대 3회 수행하고 `attempt_count`로 관리한다. 사용자가 결과를 확인한 뒤 요청하는 재생성은 새로운 생성 작업이며, `guidebook_id`와 입력 스냅샷으로 갱신 대상을 참조한다.

#### **11.3 생성권 사용**

```
PENDING → PROCESSING → COMPLETED
                     └→ FAILED
```

`PENDING` 또는 `PROCESSING` 작업은 생성권 1개가 논리적으로 예약된 상태를 의미한다. 별도 예약 수량은 저장하지 않는다. `COMPLETED` 전환과 같은 트랜잭션에서 생성권 1개를 차감하며, `FAILED` 전환 시에는 잔액을 변경하지 않는다. 회원별 진행 중 작업 유일 제약과 원장 멱등 키로 중복 작업과 중복 차감을 막는다.

#### **11.4 공유 링크**

공유 링크는 별도의 `ACTIVE`·`EXPIRED` 상태값을 저장하지 않는다. 생성 시 `expires_at`을 저장하고 접근 시 현재 시각과 비교해 유효성을 판단한다. 공유 화면의 취소는 링크 상태를 변경하지 않으며, 만료되었거나 존재하지 않는 링크는 동일한 오류로 안내한다.

#### **11.5 가이드북 평가 진행**

```
PENDING → SUBMITTED
```

평가 안내 모달에서 `다음에 하기`를 선택하면 상태를 별도로 분기하지 않고 `prompt_dismissed_at`을 기록해 자동 모달 재노출만 중단한다. 사용자는 가이드북 목록의 평가 버튼으로 다시 평가 화면을 열 수 있다.

장소별 입력 상태는 제출 전 프론트엔드에서 다음과 같이 관리하고, 제출 시 전체 평가를 한 번에 서버로 전송한다.

```
UNANSWERED → RATED(score: 0~5)
           └→ SKIPPED(score: NULL)
```

0점은 유효한 평가이며 랭킹 집계에 포함한다. `NULL`은 해당 장소를 평가하지 않은 것으로 보고 집계에서 제외한다. 제출 전에는 이전 장소로 돌아가 `RATED`와 `SKIPPED`를 변경할 수 있다.

서버는 평가 초안을 저장하지 않으므로 앱 종료 시 제출 전 입력값이 유실될 수 있다. 초안 복구가 필요해지면 별도 임시 저장 API를 추가한다.

#### **11.6 주문·결제**

주문: CREATED → PAYMENT_PENDING → PAID | FAILED | CANCELED

주문과 결제 시도는 1:N으로 두어 재시도를 표현한다.

#### **13.4 ERD에 만들지 않을 항목**

검색 조건, 드롭다운 열림 상태, 현재 지도 범위는 요청 또는 UI 상태다.

Marker와 Cluster는 지도 응답 모델이며 원본 테이블이 아니다.

베이지안 계산식과 C·m은 MVP에서 애플리케이션 설정으로 관리하고 계산 결과만 랭킹 항목에 저장한다. 과거 계산 근거를 완전히 재현해야 할 때 스냅샷 메타데이터를 확장한다.

V3에서 근거가 없는 여행별 PreferenceSnapshot 엔티티는 만들지 않는다.

관리자 운영 대상이 아닌 취향 선택지는 `preference_groups`, `preference_options` 테이블로 만들지 않고 애플리케이션 Enum으로 관리한다.

콘텐츠는 `tourism_contents.category`로 행사·축제, 문화유산, 명소 중 하나만 가진다. 자연·미식·힐링 등은 콘텐츠 카테고리가 아니라 회원 취향이므로 `content_categories`, `content_category_mappings`를 만들지 않는다.

#### **14.3 도메인 간 정합성 방식**

한 DB 트랜잭션으로 처리 가능한 도메인 내부 변경은 즉시 일관성을 사용한다.

AI·PG·푸시처럼 외부 시스템이 개입하는 작업은 상태 머신, 멱등 키, 재시도, 보상 작업을 사용한다.

가이드북 생성과 생성권 잔액 확인·성공 차감은 초기에는 동일 애플리케이션 서비스에서 오케스트레이션하되 각 도메인의 변경 책임을 분리한다.

도메인 사건 발행이 DB 커밋과 분리돼 유실될 위험이 있으면 Outbox 패턴을 적용한다.

### **19. PL 미팅 설명용 결정 요약**

#### **“왜 5개인가?”**

화면 수가 아니라 데이터 소유권과 상태 전이, 현재 서비스 규모를 기준으로 나눴다. 회원에게 붙는 기본 취향과 언어 설정은 회원에 합쳤고, 관광 콘텐츠를 조회하는 검색·지도는 콘텐츠에 합쳤다. 공유·가져오기는 가이드북의 전달 생명주기라 가이드북에 포함했다. 알림도 수신 회원에게 귀속되고 현재 범위가 목록·삭제·푸시 설정 중심이므로 회원의 하위 책임으로 합쳤다. 반면 평가·랭킹과 생성권·결제는 독립적인 집계·무결성·실패 복구 규칙이 강해 별도 도메인으로 유지했다.

#### **“왜 더 합치지 않았는가?”**

평가를 콘텐츠에 합치면 콘텐츠 원본과 사용자 생성 원본·집계 규칙이 섞인다.

생성권·결제를 회원이나 가이드북에 합치면 금전·원장 정합성과 중복 PG 처리가 약해진다.

알림은 회원에 합치되, 회원의 핵심 인증 로직이 다른 도메인의 사건이나 푸시 실패 처리에 직접 의존하지 않도록 내부 알림 패키지와 이벤트 처리 경계를 둔다.

#### **“왜 더 나누지 않았는가?”**

현재 규모에서는 검색, 지도, 공유, 취향, 알림이 독립 배포나 별도 저장소를 요구할 정도의 생명주기를 갖지 않는다. 특히 알림은 수신 회원 중심의 단순 전달 기능이므로 회원 내부 모듈로도 충분하다. 먼저 모듈러 모놀리스의 패키지 경계를 지키고, 트래픽·팀 규모·변경 빈도가 커질 때 분리하는 편이 구현 가능성과 유지보수에 유리하다.

#### **“이 결정의 단점은?”**

DOM-01, DOM-02, DOM-03의 책임 범위가 넓어질 수 있다. 이를 완화하기 위해 도메인 내부에서 회원/취향/알림, 수집/검색/지도, 생성/일정/공유 같은 하위 패키지를 구분한다. 향후 알림 채널·발송량·재시도 운영, 검색 인프라, 공유 정책이 독립적으로 커지면 현재 내부 경계를 기준으로 하위 모듈을 분리한다.

### **20. 설계 셀프 리뷰**

#### **요구사항 연결**

각 도메인 책임을 사용자 시나리오, 비즈니스 규칙, 기능 요구사항과 ID로 연결했는가?

화면 요소가 아니라 실제 업무 규칙을 설명하고 있는가?

#### **설계 근거**

9개에서 5개로 병합한 기준과 유지한 이유를 설명할 수 있는가?

원본 데이터와 조회·파생 데이터를 구분했는가?

#### **대안과 트레이드오프**

취향, 알림, 탐색, 공유, 정책을 독립 도메인으로 두는 대안을 검토했는가?

5개 경계로 인해 커지는 모듈과 향후 분리 조건을 기록했는가?

#### **정상·예외 시나리오**

중복 생성·평가 제출·결제 웹훅을 멱등하게 처리하는가?

외부 API, AI, PDF, PG, 푸시 실패 후 복구 경로가 있는가?

결과 없음, 만료, 권한 거부, 동점, 잔액 부족 등 경계값을 다뤘는가?

#### **문서 간 일관성**

V3 화면설계서, 기능정의서, 본 문서, ERD, API에서 동일 용어와 상태를 쓰는가?

여행별 취향처럼 V3 근거가 없는 개념이 남아 있지 않은가?

#### **구현 가능성**

초기 구현이 5개 마이크로서비스가 아니라 하나의 모듈러 모놀리스임을 팀이 동일하게 이해하는가?

P0 결정 항목을 ERD와 API 작성 전에 확정할 수 있는가?

팀 일정상 P1·P2 항목을 뒤로 미뤄도 핵심 시나리오가 완성되는가?

### **21. 현재 결론**

V3 도메인은 **회원, 관광 콘텐츠·탐색, 가이드북, 평가·랭킹, 생성권·결제**의 5개로 정의한다.

취향과 알림은 회원의 하위 책임, 탐색·지도는 관광 콘텐츠의 조회 기능, 공유·가져오기는 가이드북의 하위 책임으로 병합한다.

서비스 설정은 독립 도메인으로 두지 않고 언어·푸시 설정은 회원, 결제 정책은 생성권·결제가 소유한다. 이용약관·개인정보 처리방침은 정적 콘텐츠로 제공하며 동의 이력은 저장하지 않는다.

랭킹은 여행 종료 후 제출된 장소 평가를 기반으로 베이지안 가중 평점을 계산하며 **일간·주간·월간을 제공**한다.

다음 단계에서는 P0 결정 항목을 확정한 뒤 이 5개 경계를 기준으로 ERD와 API를 작성한다.
