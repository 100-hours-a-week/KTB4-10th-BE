## 1. 문서 목적과 사용 방법

이 문서는 V3 화면설계서와 기능정의서를 개발 가능한 요구사항 단위로 재구성한 0단계 산출물이다. 이후 ERD, API 명세, 기술 선정, 테크스펙에서는 본 문서의 요구사항 식별자(`US`, `BR`, `FR`, `NFR`)를 참조한다.

요구사항 출처는 다음과 같이 구분한다.

- **확정(V3)**: Figma 기능정의서에 명시된 내용
- **설계 제안**: 구현 가능성·정합성·운영을 위해 0단계에서 보완한 권장안
- **확인 필요**: Figma 내 충돌, 누락 또는 해석이 둘 이상 가능한 내용

## 2. 서비스 개요와 범위

콜인원은 사용자의 로그인 정보, 여행 취향, 여행 조건을 바탕으로 주변 행사·명소 정보를 제공하고 AI 맞춤 가이드북을 생성·저장·공유하는 여행 서비스다.

V3에서 확인한 핵심 범위는 다음과 같다.

1. 카카오·구글 OAuth 로그인 및 신규/기존 회원 분기
2. 신규 회원의 초기 여행 취향 설정과 기존 회원의 취향 수정
3. 현 위치 기반 지도 및 주변 문화유산·행사·축제·명소 조회
4. 행사 검색·필터·랭킹·상세 정보 조회
5. 여행 조건 입력, 지역 추천, AI 가이드북 생성·실패 복구·수정·조회
6. 가이드북 다운로드·삭제·즐겨찾기·공유와 여행 종료 후 장소 평가
7. 마이페이지, 인앱/푸시 알림, 설정, 로그아웃, 회원 탈퇴
8. AI 생성권 조회·구매, 언어 설정, 서비스·약관·정책 조회

### 4.1 도메인 경계 원칙

- 인증 성공은 회원 도메인이 판정하고, 화면 이동은 그 결과(`EXISTING`, `NEW`, `PREFERENCE_INCOMPLETE`)를 받아 프론트가 수행한다.
- 장소·행사 원천 데이터와 사용자의 관심 장소는 분리한다. 원천 데이터가 갱신되어도 사용자 저장 관계는 추적 가능해야 한다.
- 가이드북 생성 요청은 동기 API가 아니라 상태를 가진 작업(`QUEUED → RUNNING → SUCCEEDED/FAILED/CANCELLED`)으로 취급한다.
- 생성권은 단순 잔여 숫자보다 증감 이력을 보존하는 원장 방식으로 관리한다.
- 결제 성공 여부는 클라이언트 화면이 아니라 PG 검증 결과를 기준으로 확정한다.
- 평가 원본과 랭킹 집계 결과를 분리하여 재집계와 기준 변경이 가능해야 한다.

## 9. 상태 모델 초안

### 9.1 회원

`OAUTH_PENDING → ACTIVE(PREFERENCE_INCOMPLETE | READY) → WITHDRAWAL_PENDING → WITHDRAWN`

- 인증 실패·취소는 회원 상태를 만들거나 변경하지 않는다.
- 탈퇴 처리 실패 시 기존 `ACTIVE` 상태를 유지한다.

### 9.2 가이드북 생성 작업

`QUEUED → RUNNING(FIND_PLACES → CHECK_EVENTS → BUILD_ITINERARY) → SUCCEEDED | FAILED | CANCELLED`

- `SUCCEEDED` 전환은 한 번만 가능하다.
- 생성권 차감은 최초 `SUCCEEDED` 전환과 함께 처리한다.
- 실패 코드는 최소 `NETWORK`, `TIMEOUT`, `UPSTREAM`, `SERVER`, `VALIDATION`, `QUOTA`로 구분한다.

### 9.3 주문·결제

`CREATED → PAYMENT_PENDING → PAID → FULFILLED`

실패 분기: `CANCELLED | FAILED | REFUND_PENDING → REFUNDED`

- `PAID`는 PG 서버 검증 후에만 진입한다.
- `FULFILLED`는 생성권 지급 완료를 뜻하며 재처리되어도 중복 지급하지 않는다.

### 9.4 다운로드

`IDLE → DOWNLOADING ↔ PAUSED → COMPLETED | FAILED`

앱 재실행 후 일시정지 상태 초기화 요구와 실제 부분 다운로드 파일 처리 방식은 FE·BE가 함께 확정해야 한다.

## 15. 셀프 리뷰 결과

- **요구사항 연결**: 각 기능·비기능 요구사항을 사용자 시나리오, 비즈니스 규칙, 화면 ID와 연결했다.
- **설계 근거**: 비동기 생성, 생성권 원장, PG 서버 검증, 관광 데이터 캐시 등 주요 선택의 서비스상 근거를 명시했다.
- **대안과 트레이드오프**: 8개 주요 설계 결정에 대해 대안과 감수할 단점을 정리했다.
- **정상/예외 시나리오**: 인증 취소, 권한 거부, 검색 결과 없음, 생성·결제 중복, 오프라인, 탈퇴 실패 등 16개 시나리오를 포함했다.
- **문서 간 일관성**: 중복 화면 ID, 버전, 화면 이동 대상, 취향 적용 범위, 생성권 정책 충돌을 `GAP-*`로 식별했다.
- **구현 가능성**: 외부 연동과 장시간 작업을 분리하고 P0/P1 우선순위를 제안했다. 다만 결제·생성권·GUIDE-05 흐름은 구현 전 기획 확정이 필요하다.

## 16. 구현 전 반드시 확정할 P0 질문

1. GUIDE-05는 ‘초안 확인’인가, ‘최종 생성 성공’인가? 생성권 차감은 어느 시점인가?
2. 월 무료 3회와 유료 생성권은 별도 잔액인가? 월 1일 초기화 시 유료 잔액은 유지되는가?
3. 20회 상한은 유료분만인지 전체 잔액인지, 18회 보유 시 3회 상품 결제를 허용할지?
4. PREF-02를 GUIDE-02에서 열어 저장할 때 프로필 기본 취향도 변경하는가?
5. 결제 성공·실패·취소·환불과 PG 사업자/플랫폼별 정책은 무엇인가?
6. 회원 탈퇴 시 가이드북, 다운로드 파일, 결제 기록, 평가, 공유 링크를 각각 삭제·익명화·보존할 기준은 무엇인가?
7. 공유받은 가이드북은 원본의 독립 복제본인가, 원본 변경을 따라가는 참조본인가?
8. 알림 유형별 정확한 목적 화면 ID와 필수 파라미터는 무엇인가?
9. 위치 권한을 영구 거부한 사용자의 앱 이용을 완전히 차단할지, 제한 모드를 제공할지?
10. 랭킹 집계 시간대, 기간 경계, 평가가 전혀 없는 장소의 노출 규칙은 무엇인가?

위 10개를 확정하면 ERD와 API 설계를 큰 재작업 없이 시작할 수 있다.
