# API 설계 근거

> 2026-09-04 · 최신 로컬 문서, 8f028284·ea330328 커밋 및 OAuth 지원 범위 확정 반영
> V3 API 명세서.md의 API ID로 연결하는 내부 검토·미팅 준비 문서다. 엑셀은 사용자 요청에 따라 이번 변경을 반영하지 않았으며 다음 일괄 갱신 대상이다.
> 명세서에서는 호출 계약을 읽고, 이 문서에서는 그 계약의 이유와 남은 선택을 읽는다. 근거를 분리해도 구현에 필요한 상태·권한·검증 조건은 명세서에서 제거하지 않는다.

## 3. 트랜잭션과 외부 연동 경계

### 생성 접수와 성공 차감

1. 인증·기존 멱등 키를 먼저 확인한다. 동일 요청의 재전송은 현재 취향을 다시 읽어 새 요청으로 만들지 않는다. 저장한 요청 입력과 회원을 비교한다.
2. 지갑 행을 잠그고 잔액 및 활성 작업 유무를 검사한다. 생성 작업과 요청 시점 기본 취향 스냅샷을 같은 트랜잭션에 저장한다.
3. 활성 작업의 generated UNIQUE는 최종 동시성 방어다. UI의 can_generate 확인만으로 중복을 막을 수 없다.
4. AI 호출은 DB 잠금을 보유한 트랜잭션 바깥에서 처리한다. 기술 재시도는 동일 job_id, 사용자 재생성은 새 job_id다.
5. 성공 결과 검증 후 가이드북/일정·작업 COMPLETED·지갑 -1·CONSUME 원장을 하나의 트랜잭션으로 저장한다. 재생성은 기존 가이드북의 version을 증가시킨다.
6. 최종 실패는 FAILED를 저장하고 잔액은 바꾸지 않는다. 마지막 생성권을 보호하려면 다른 회수·조정도 동일 지갑 잠금 규칙을 따라야 한다.

대안은 별도 예약 수량/예약 원장을 두는 것이다. 현재 회원당 활성 작업 하나라는 제한으로 논리 예약을 표현하므로 제외했다. 동시 생성 허용 시 이 선택을 재검토한다. AI가 같은 결과를 재전달해도 작업 상태와 원장 키로 성공 반영은 한 번만 수행한다.

멱등 키 예시: generation:{job_id}:consume, monthly-free:{member_id}:{yyyyMM}, order:{order_id}:grant. 키는 비밀 인증 수단이 아니며 회원/요청 범위를 검증해야 한다. 원장 INSERT의 UNIQUE 실패만 잡고 지갑 증가를 커밋하는 구현은 잘못이다. 하나의 트랜잭션으로 원장과 잔액을 일치시킨다.

### 평가 제출과 랭킹

점수 0은 유효, null은 건너뛰기, 아직 입력하지 않음은 프론트 초안 상태다. place_ratings는 회원·콘텐츠별 최종값이므로 평가 진행 상태 PENDING만으로 초안 복구나 특정 여행의 과거 제출 원문을 복원할 수 없다.

최종 제출은 평가 행을 잠근 후 상태와 소유자·대상 장소를 검증하고 점수 반영 및 SUBMITTED 전환을 한 번에 처리한다. 이미 제출된 경우 재반영하지 않는다. 같은 payload 재전송과 다른 내용 재제출을 구별해 응답하려면 제출 원문/해시 보관 또는 다른 확정 정책이 필요하다. 현재 테이블만으로 정확한 응답 재생을 보장한다고 쓰지 않았다.

랭킹은 점수 커밋 후 updated_at을 기준으로 변경 지역을 찾아 지역 및 전국을 재집계한다. updated_at 워터마크는 변경 탐지용이지 점수가 일간/주간 랭킹의 어느 기간에 속하는지 결정하는 정책이 아니다. 지연 커밋, 동일 시각, 삭제/비활성화는 단순 시간 비교만으로 누락될 수 있어 워터마크 겹침 재조회·정기 재집계와 테스트가 필요하다. 대상 스냅샷/항목은 하나의 트랜잭션으로 교체하고 실패 시 이전 완료 결과를 유지한다.

대안인 요청 안 전체 집계는 응답 지연을 늘린다. 현재 선택은 약간 늦은 랭킹을 감수하는 대신 평가 저장 지연을 줄인다. calculated_at을 노출하고 배치 주기와 지연 목표를 별도 합의한다.

### 공유·삭제·알림

가져오기는 최초 원본 ID를 계속 전달하며 독립 복사한다. 회원+원본 UNIQUE가 다른 링크 및 재공유에 의한 중복을 막는다. 복사본 생성과 가져오기 이력을 같은 트랜잭션으로 처리한다. 원본 삭제가 다른 회원 복사본의 삭제로 전파되면 요구사항 위반이다.

deleted_at은 필터링에 쓰는 데이터이며 컬럼이 존재한다고 자동으로 soft delete가 구현되는 것은 아니다. 목록·상세·공유·백그라운드 작업 모두 삭제 조건을 검증해야 한다. 관리자 비활성화 status와 삭제를 혼동하지 않는다.

알림 읽기는 DELETE다. 원본 업무 실패 격리와 동일 트랜잭션 알림 생성 규칙은 현재 문구만으로 구현 방법이 완결되지 않는다. 알림 INSERT 실패로 전체 트랜잭션이 롤백되는지, 별도 트랜잭션/저장점 사용 시 누락을 어떻게 보완할지 확인해야 한다(API-DEC-11). 데이터 정의서를 임의로 outbox 모델로 바꾸지 않았다.

### 결제

브라우저 완료 화면이나 클라이언트가 전달한 가격은 결제 완료 증거가 아니다. PG의 검증된 승인과 서버 주문 스냅샷을 대조한다. 주문·결제 시도·지갑·원장의 상태 변경은 중복 승인에도 한 번만 반영한다. PG API 호출 자체와 DB 트랜잭션을 하나의 원자적 트랜잭션으로 간주할 수 없으므로 재조회·재처리 경로가 필요하다.

현재 PG의 원문 요청/응답, 시도 요청 멱등성, 웹훅 이벤트 재처리 키가 확정되지 않았다. 공통 가짜 PG payload로 명세를 완성한 것처럼 표시하지 않고 두 API를 보류 표시했다. 상품 예시 금액은 사업 정책 확정값이 아니다.

## 4. 스키마와 API가 달라도 되는 부분

- favorite_contents에 대리키를 추가했다고 URL을 /favorites/{favorite_id}로 반드시 바꿀 필요는 없다. 사용자가 아는 content_id와 토큰 회원으로 유일 관계를 찾는다.

- FK, UNIQUE, INDEX는 응답 필드가 아니다. 인증·소유권 검사나 상품 가격 검증을 대신하지 않는다.

## 8. BE 커밋 검토 — 8f028284 / ea330328

### 8.1 푸시 설정을 회원 설정으로 통합: 찬성

8f028284는 GET/PATCH /push-preferences를 없애고 MEM-10/11의 /members/me/settings로 합쳤다. 저장값이 같은 members.push_enabled이고 설정 화면의 일부이므로 중복 API·enabled/push_enabled 명칭·문서/테스트 경로를 줄이는 이점이 있다. 도메인도 이미 회원 하위 책임이므로 경계와 맞는다(FR-NOT-03, BR-NOT-05).

단, 같은 테이블이라는 이유만으로 모든 API를 합쳐야 하는 것은 아니다. 이 경우에는 소유자·권한·사용 시나리오가 같은 설정이라 통합 근거가 충분하다. push_enabled=false는 푸시 발송만 제한하며 인앱 알림을 삭제하거나 생성을 막지 않는다. 언어만 PATCH하면 푸시는 유지되고 false/null/누락은 구분해야 한다.

기존 호출자가 있다면 경로와 enabled → push_enabled 전환이 필요하다. 아직 구현 전이면 별칭 유지보다 즉시 단일화가 단순하다. 제거 ID는 재사용하지 않고 제외 목록에 남긴다. 실제 푸시의 OS 권한·구독 토큰 보관은 별도 미확정이므로 설정 API 통합만으로 푸시 구현이 완결되지 않는다.

### 8.2 제목·일정 직접 편집을 자연어 재생성으로 통일: 범위에 맞는 선택

| 변경 시점 | 초안 화면 설명만으로 공유/여행 종료/평가 이후 허용 여부가 정해지지 않음 | DEC-12의 재생성 허용 시점과 기존 공유·평가 대상 영향 |
| 캐시 | version은 저장 본문 갱신을 식별하지만 삭제/인가/링크 만료를 표현하지 않음 | 캐시 조회 전 접근 검증, gb_id+version 식별, 언어/표현이 달라지면 캐시 키 추가 |
| 실패와 재요청 | 재생성 실패·응답 유실에도 원본과 차감이 일치해야 함 | 같은 키는 같은 job, 성공 때만 version/본문/일정/CONSUME 원자 반영 |

직접 편집은 즉시·정확한 수정이라는 장점이 있지만 편집 UI, 순서 재정렬, HTML 동기화, 별도 권한/검증이 필요하다. 현재는 자연어 재생성을 선택하고 이 단점을 감수하는 것이 타당하다. 다만 이것이 항상 더 좋은 UX라는 뜻은 아니다.

### 8.3 후속 반영/검증

- 이번에 근거 문서의 제외 ID 목록도 최신 API 문서와 맞췄다. 삭제된 API를 부활시키지 않았다.
- 엑셀의 NOT-04/05·GDE-06/08 제거, 회원 설정·재생성 설명 및 이번 OAuth 변경은 다음 일괄 갱신 때 반영한다.
- 실제 프론트/AI 구현 및 Figma가 이 흐름과 일치하는지는 이번 커밋 리뷰로 확인되지 않았다. 버튼·요금 안내·재생성 오류 흐름을 팀과 대조해야 한다.

## 9. OAuth 지원 범위와 남은 보안 설계

**확정:** V1 KAKAO만, V2 이상(V3 포함) KAKAO·GOOGLE 모두 지원. 회원당 한 공급자 계정이라는 현재 모델은 유지한다. 두 공급자 지원과 계정 연결 기능은 별개다.

**state**는 인가 요청을 시작한 브라우저/로그인 시도와 응답을 연결해 로그인 CSRF 등을 방어한다. **PKCE**는 인가 코드가 최초 요청자의 verifier와 결속되도록 하여 가로챈 코드만으로 토큰을 교환하는 공격을 줄인다. 서로 다른 역할이며 우리 설계안에서는 state 결속과 지원 흐름의 S256을 함께 검토한다. [OAuth 보안 BCP](https://www.rfc-editor.org/rfc/rfc9700.html), [PKCE](https://www.rfc-editor.org/rfc/rfc7636.html)

남은 결정은 ‘보안을 넣을지’가 아니라 **누가 언제 생성·보관·검증하고 어떤 API/쿠키로 전달할지**다. API-MEM-01의 결정표에서 시작/콜백 담당, state TTL·일회 소비·브라우저 결속, 공급자별 SDK/PKCE 지원, verifier 전달, OIDC, 실패 코드와 토큰 전달을 정한다.

백엔드 관리 로그인 시도를 우선 권장하는 이유는 두 공급자의 결속 검증을 한곳에서 구현하기 쉽기 때문이다. 다만 시작/콜백 계약과 임시 저장소·다중 서버 운영 부담이 생긴다. 프론트 콜백은 UI 연결이 쉬울 수 있지만 프론트의 검증 완료 주장만 믿지 말고 서버가 확인할 수 있는 로그인 시도 결속이 필요하다. 어느 안도 현재 확정된 것으로 쓰지 않는다.

auth_sessions는 로그인 **후** refresh 세션이어서 가입 전 state/verifier 저장 구조를 대신하지 않는다. 단기 서버 세션·DB·공유 저장소를 비교하되 Redis나 새 테이블을 이번에 필수로 추가하지 않는다. 키를 해시로 저장하는 refresh 토큰과 달리 PKCE verifier는 토큰 교환에 사용할 원문 관리가 필요하다.
