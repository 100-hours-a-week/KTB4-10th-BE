## 3. 트랜잭션과 외부 연동 경계

### 생성 접수와 성공 차감

1. 인증·기존 멱등 키를 먼저 확인한다. 동일 요청의 재전송은 현재 취향을 다시 읽어 새 요청으로 만들지 않는다. 저장한 요청 입력과 회원을 비교한다.
2. 지갑 행을 잠그고 잔액 및 활성 작업 유무를 검사한다. 생성 작업과 요청 시점 기본 취향 스냅샷을 같은 트랜잭션에 저장한다.
3. 활성 작업의 generated UNIQUE는 최종 동시성 방어다. UI의 can_generate 확인만으로 중복을 막을 수 없다.
4. AI 호출은 DB 잠금을 보유한 트랜잭션 바깥에서 처리한다. 기술 재시도는 동일 job_id, 사용자 재생성은 새 job_id다.
5. 성공 결과 검증 후 가이드북/일정·작업 COMPLETED·지갑 -1·CONSUME 원장을 하나의 트랜잭션으로 저장한다. 재생성은 기존 가이드북의 version을 증가시킨다.
6. 최종 실패는 FAILED를 저장하고 잔액은 바꾸지 않는다. 마지막 생성권을 보호하려면 다른 회수·조정도 동일 지갑 잠금 규칙을 따라야 한다.

대안은 별도 예약 수량/예약 원장을 두는 것이다. 현재 회원당 활성 작업 하나라는 제한으로 논리 예약을 표현하므로 제외했다. 동시 생성 허용 시 이 선택을 재검토한다. AI가 같은 결과를 재전달해도 작업 상태와 원장 키로 성공 반영은 한 번만 수행한다.

멱등 키 예시: generation:{job_id}:consume, monthly-free:{member_id}:{yyyyMM}, order:{order_id}:grant. 키는 비밀 인증 수단이 아니며 회원/요청 범위를 검증해야 한다. 원장 INSERT의 UNIQUE 실패만 잡고 지갑 증가를 커밋하는 구현은 잘못이다. 하나의 트랜잭션으로 원장과 잔액을 일치시킨다.

### 평가 제출과 랭킹

점수 0은 유효, null은 건너뛰기, 아직 입력하지 않음은 프론트 초안 상태다. place_ratings는 회원·콘텐츠별 최종값이므로 평가 진행 상태 PENDING만으로 초안 복구나 특정 여행의 과거 제출 원문을 복원할 수 없다.

최종 제출은 평가 행을 잠근 후 상태와 소유자·대상 장소를 검증하고 점수 반영 및 SUBMITTED 전환을 한 번에 처리한다. 이미 제출된 경우 재반영하지 않는다. 같은 payload 재전송과 다른 내용 재제출을 구별해 응답하려면 제출 원문/해시 보관 또는 다른 확정 정책이 필요하다. 현재 테이블만으로 정확한 응답 재생을 보장한다고 쓰지 않았다.

랭킹은 점수 커밋 후 updated_at을 기준으로 변경 지역을 찾아 지역 및 전국을 재집계한다. updated_at 워터마크는 변경 탐지용이지 점수가 일간/주간 랭킹의 어느 기간에 속하는지 결정하는 정책이 아니다. 지연 커밋, 동일 시각, 삭제/비활성화는 단순 시간 비교만으로 누락될 수 있어 워터마크 겹침 재조회·정기 재집계와 테스트가 필요하다. 대상 스냅샷/항목은 하나의 트랜잭션으로 교체하고 실패 시 이전 완료 결과를 유지한다.

대안인 요청 안 전체 집계는 응답 지연을 늘린다. 현재 선택은 약간 늦은 랭킹을 감수하는 대신 평가 저장 지연을 줄인다. calculated_at을 노출하고 배치 주기와 지연 목표를 별도 합의한다.

### 공유·삭제·알림

가져오기는 최초 원본 ID를 계속 전달하며 독립 복사한다. 회원+원본 UNIQUE가 다른 링크 및 재공유에 의한 중복을 막는다. 복사본 생성과 가져오기 이력을 같은 트랜잭션으로 처리한다. 원본 삭제가 다른 회원 복사본의 삭제로 전파되면 요구사항 위반이다.

deleted_at은 필터링에 쓰는 데이터이며 컬럼이 존재한다고 자동으로 soft delete가 구현되는 것은 아니다. 목록·상세·공유·백그라운드 작업 모두 삭제 조건을 검증해야 한다. 관리자 비활성화 status와 삭제를 혼동하지 않는다.

알림 읽기는 DELETE다. 원본 업무 실패 격리와 동일 트랜잭션 알림 생성 규칙은 현재 문구만으로 구현 방법이 완결되지 않는다. 알림 INSERT 실패로 전체 트랜잭션이 롤백되는지, 별도 트랜잭션/저장점 사용 시 누락을 어떻게 보완할지 확인해야 한다(API-DEC-11). 데이터 정의서를 임의로 outbox 모델로 바꾸지 않았다.

### 결제

브라우저 완료 화면이나 클라이언트가 전달한 가격은 결제 완료 증거가 아니다. PG의 검증된 승인과 서버 주문 스냅샷을 대조한다. 주문·결제 시도·지갑·원장의 상태 변경은 중복 승인에도 한 번만 반영한다. PG API 호출 자체와 DB 트랜잭션을 하나의 원자적 트랜잭션으로 간주할 수 없으므로 재조회·재처리 경로가 필요하다.

현재 PG의 원문 요청/응답, 시도 요청 멱등성, 웹훅 이벤트 재처리 키가 확정되지 않았다. 공통 가짜 PG payload로 명세를 완성한 것처럼 표시하지 않고 두 API를 보류 표시했다. 상품 예시 금액은 사업 정책 확정값이 아니다.

## 4. 스키마와 API가 달라도 되는 부분

- favorite_contents에 대리키를 추가했다고 URL을 /favorites/{favorite_id}로 반드시 바꿀 필요는 없다. 사용자가 아는 content_id와 토큰 회원으로 유일 관계를 찾는다.
- POINT는 DB 저장 방식이다. API는 latitude/longitude 숫자로 제공한다. ST_Longitude/ST_Latitude로 읽고 축 순서를 테스트한다.
- Enum 옵션은 테이블이 없어도 조회 API로 제공할 수 있다. 반대로 API의 options 배열이 반드시 DB 테이블이어야 하는 것은 아니다.
- can_generate, unread_count, next_cursor는 계산값이다. 이를 저장 컬럼으로 추가할 필요는 없다.
- FK, UNIQUE, INDEX는 응답 필드가 아니다. 인증·소유권 검사나 상품 가격 검증을 대신하지 않는다.

## 7. 동기화 검토 범위와 남은 검증

- 최신 세 원본 문서와 API 필드/상태/저장 책임을 대조했다. 원본 요구사항·테이블·SQL은 수정하지 않았다.
- 원본의 FR-MEM-04(프로필 수정)와 테이블(직접 닉네임 수정 없음), 일부 남은 동의 시나리오 문구는 팀 확인 대상이다.
- API-MEM-05 등 제외 ID는 재사용하지 않았다. 기존 클라이언트가 있다면 변경 URL과 JSON 필드에 대한 마이그레이션이 필요하다.
- JSON 예시, API ID 및 엑셀/Markdown 동기화를 파일 수준으로 검사한다. 이는 실제 서버 통합 테스트나 DB 실행 검증이 아니다.
- 실제 구현에서는 동시 생성 2건, 성공 콜백 중복, 동일 원본의 다른 링크 가져오기, 0점/null 평가, 삭제 중 생성 완료, 반복 결제 웹훅을 테스트해야 한다.
- 서비스 전체 API는 DB 테이블 수와 일치하지 않는다. 내부 관광 수집·AI 호출·배치·PG 세부 콜백은 별도 내부 계약을 확정해야 하며 본 문서의 프론트 API와 동일시하지 않는다.
