# KGB 성능 측정 및 모니터링 계획

## 1. 목적

KGB 서비스의 성능 문제를 감으로 판단하지 않고 다음 질문에 답할 수 있는 측정 기준을 정의한다.

- 어떤 API에 트래픽이 집중되는가?
- 어떤 API가 느리거나 실패하는가?
- 지연 원인이 애플리케이션, DB, 외부 AI 서버 중 어디에 있는가?
- 요청량이 증가할 때 CPU, 메모리, 스레드, DB 커넥션이 포화되는가?
- 코드나 쿼리 변경 후 실제로 성능이 개선되었는가?

초기에는 모든 로그·메트릭·분산 추적을 한 번에 구축하지 않는다. 전체 API의 기본 지표와 핵심 사용자 흐름을 먼저 측정하고, 원인 파악에 부족한 영역만 단계적으로 확장한다.

## 2. 기본 측정 관점

| 대분류 | 측정 항목 | 확인 목적 |
|---|---|---|
| 트래픽 | 요청 수, RPS | 자주 호출되는 API와 트래픽 증가 확인 |
| 지연 시간 | 평균, p95, 최대 응답 시간 | 일반적인 지연과 간헐적인 느린 요청 확인 |
| 에러 | 4xx, 5xx, timeout | 사용자 오류와 서버·외부 연동 오류 구분 |
| 포화도 | CPU, JVM 메모리, HTTP 스레드, DB 커넥션 풀 | 처리 용량의 한계와 대기 발생 확인 |

초기에는 전체 API에 대해 다음 지표를 공통 수집한다.

- HTTP method와 정규화된 API 경로별 요청 수
- 평균 및 p95 응답 시간
- 상태 코드별 4xx·5xx 수
- 프로세스 CPU 사용률
- JVM heap 사용량과 GC
- HTTP 처리 스레드 사용량
- HikariCP active·idle·pending connection과 timeout

API는 실제 식별자가 아닌 `/api/v1/guidebooks/{guidebookId}` 같은 경로 템플릿 단위로 집계한다. 회원 ID, 가이드북 ID, 작업 ID, trace ID는 메트릭 태그로 사용하지 않는다.

## 3. 환경별 측정 범위

모든 측정을 스테이징에서 수행하지 않는다. 코드와 쿼리의 원인은 로컬에서 찾고, 시스템 전체의 처리 특성은 스테이징에서 검증하며, 실제 사용자 영향은 운영에서 관찰한다.

### 3.1 로컬

로컬은 코드와 쿼리 개선 전후를 반복 비교하는 환경이다.

- 핵심 쿼리의 `EXPLAIN ANALYZE`
- 지도 범위 조회의 공간 인덱스 사용 여부
- API 한 번당 SQL 호출 횟수
- N+1 및 중복 조회 여부
- 가이드북 상세 조회의 데이터 조립 과정
- 낮은 동시성의 간단한 API 반복 테스트
- Actuator 메트릭과 요청 로그의 정상 생성 여부

로컬 장비와 데이터는 운영 환경과 다르므로 절대 응답 시간을 성능 목표로 사용하지 않는다. 다음과 같은 변경 전후 상대 비교에 활용한다.

```text
쿼리 21회 → 3회
full scan → spatial index scan
동일 조건 응답 시간 300ms → 120ms
```

### 3.2 스테이징

스테이징은 운영과 유사한 애플리케이션·DB·외부 연동 환경에서 동시 요청과 자원 사용량을 검증한다.

- 핵심 API의 RPS, 평균·p95 응답 시간, 4xx·5xx
- 지도 이동에 따른 연속 범위 조회
- 여러 사용자의 가이드북 동시 생성
- 가이드북 생성 상태 polling 트래픽
- 외부 AI 서버 호출 시간, timeout, 실패율
- 가이드북 생성 완료까지의 전체 시간
- CPU, JVM heap, GC, HTTP 스레드, DB 커넥션 풀
- 코드·쿼리 변경 전후 동일 시나리오 비교

부하 테스트 전에는 스테이징 AI 서버의 호출 제한과 비용, 테스트 데이터 정리 방법을 확인한다.

### 3.3 운영

운영은 실제 사용 패턴과 장기 추세를 관찰하는 환경이다.

- 실제 API별 트래픽과 p95 응답 시간
- 실제 4xx·5xx 및 timeout
- CPU·메모리·DB 커넥션 풀 추세
- 외부 AI 호출 실패율
- 가이드북 생성 성공률과 전체 생성 시간
- 배포 전후 성능 변화

운영에서는 의도적인 대규모 부하 테스트나 장애 유발 실험을 수행하지 않는다. 운영에서 발견한 문제는 가능한 경우 로컬이나 스테이징에서 재현한다.

### 3.4 환경별 측정표

| 측정 항목 | 로컬 | 스테이징 | 운영 |
|---|:---:|:---:|:---:|
| API 요청 수·RPS | 비교용 | O | O |
| 평균·p95 응답 시간 | 비교용 | O | O |
| 4xx·5xx | 기능 확인 | O | O |
| 쿼리 실행 계획 | O | 필요 시 | X |
| 공간 인덱스 전후 비교 | O | O | X |
| 요청당 SQL 수·N+1 | O | O | 문제 발생 시 |
| CPU·JVM 메모리·GC | 참고 | O | O |
| DB 커넥션 풀 | 참고 | O | O |
| AI 서버 호출 시간 | mock 중심 | O | O |
| 가이드북 전체 생성 시간 | 기능 확인 | O | O |
| 상태 polling 트래픽 | X | O | O |
| 부하 테스트 | 소규모 | O | X |
| 실제 사용자 패턴 | X | X | O |

## 4. 서비스 핵심 측정 대상

### 4.1 지도 콘텐츠 범위 조회

대상 API:

```text
GET /api/v1/map/contents
```

지도 이동과 확대·축소 과정에서 반복 호출될 수 있어 트래픽과 DB 부하에 가장 민감한 API다.

측정 항목:

- 요청 수와 RPS
- 평균·p95 응답 시간
- 4xx·5xx
- 요청 한 건이 반환하는 콘텐츠 수
- 응답 데이터 크기
- DB 쿼리 실행 시간
- 조회한 row 수와 반환한 row 수
- 공간 인덱스 사용 여부
- 조회 영역이 넓어질 때의 응답 시간 변화

주요 확인 사항:

- 지도 이동 중 요청이 과도하게 발생하는가?
- 조회 범위나 반환 콘텐츠 수가 증가할 때 응답 시간이 급격히 증가하는가?
- 공간 인덱스가 실제 실행 계획에서 사용되는가?
- 전체 지연 중 DB 조회가 차지하는 비중이 큰가?

위도·경도와 같은 연속적인 값은 메트릭 태그로 사용하지 않는다.

### 4.2 가이드북 생성 요청과 재시도

대상 API:

```text
POST /api/v1/guidebook-generations
POST /api/v1/guidebook-generations/{jobId}/retry
```

측정 항목:

- 최초 생성 및 재시도 요청 수
- 생성 접수 API의 평균·p95 응답 시간
- 정상 접수·실패·timeout 수
- AI 서버 요청 시간과 응답 상태
- 생성 최종 성공·실패 수
- 생성 작업 시작부터 완료까지의 전체 시간

다음 두 시간은 구분해서 측정한다.

```text
접수 응답 시간 = 클라이언트 요청부터 생성 접수 응답까지
전체 생성 시간 = 생성 작업 생성부터 가이드북 최종 완료까지
```

이를 통해 사용자 응답이 느린 문제와 AI 생성 자체가 오래 걸리는 문제를 구분한다.

### 4.3 가이드북 생성 상태 조회

대상 API:

```text
GET /api/v1/guidebook-generations/{jobId}
```

측정 항목:

- 상태 조회 요청 수와 RPS
- 평균·p95 응답 시간
- 생성 작업 한 건당 평균 polling 횟수
- 상태별 응답 수
- 완료 또는 실패 이후 계속되는 요청 여부

작업 ID는 로그 조회에는 사용할 수 있지만 메트릭 태그에는 포함하지 않는다.

### 4.4 가이드북 목록·상세·뷰어 조회

대상 API:

```text
GET /api/v1/guidebooks
GET /api/v1/guidebooks/{guidebookId}
GET /api/v1/guidebooks/{guidebookId}/viewer
```

측정 항목:

- API별 요청 수
- 평균·p95 응답 시간
- 4xx·5xx
- 요청당 DB 쿼리 수
- DB 쿼리 실행 시간
- 목록 페이지 크기
- 상세 응답의 일정·콘텐츠 수
- 응답 데이터 크기

상세 및 뷰어 조회에서 가이드북, 일정 일자, 일정 항목, 관광 콘텐츠 조회 사이에 N+1 또는 중복 쿼리가 발생하는지 확인한다.

## 5. 기본 측정만 적용할 API

다음 기능은 초기에는 요청 수, 평균·p95 응답 시간, 4xx·5xx만 수집한다. 기본 지표에서 문제가 발견된 경우에만 세부 측정을 추가한다.

- 회원 정보·설정·탈퇴
- 로그인·로그아웃·CSRF
- 사용자 취향 조회·수정
- 알림 조회·삭제
- 찜 추가·삭제
- 크레딧 지갑·쿠폰 등록
- 약관·개인정보 처리방침 조회

성능 외에 중복 요청이나 데이터 정합성이 중요한 찜, 쿠폰, 탈퇴 기능은 기능 테스트와 DB 제약조건 검증으로 별도 확인한다.

## 6. 우선 확인할 DB 쿼리

초기에는 모든 SQL을 장기간 기록하지 않고 다음 쿼리만 집중 분석한다.

| 우선순위 | 대상 | 주요 확인 내용 |
|---:|---|---|
| 1 | 지도 범위 내 콘텐츠 조회 | 공간 인덱스, 실행 시간, 조회 row 수 |
| 2 | 가이드북 상세·뷰어 조회 | 쿼리 수, N+1, 중복 조회 |
| 3 | 가이드북 목록 조회 | pagination, 정렬, 인덱스 |
| 4 | 생성 작업 상태 조회 | polling 증가 시 DB 부하 |
| 5 | 생성 결과 저장 | 트랜잭션 시간과 다수 insert |
| 6 | 알림 목록 조회 | 데이터 누적에 따른 조회 성능 |

운영에서 JPA `show-sql`을 상시 활성화하지 않는다. 로컬 실행 계획, 스테이징 검증, DB slow query를 조합하여 분석한다.

## 7. 백엔드와 클라우드 역할 분리

백엔드는 관측 가능한 데이터를 만들고 의미를 정의하며, 클라우드는 해당 데이터를 수집·저장·시각화한다.

### 7.1 백엔드 담당

- `/actuator/health`, `/actuator/prometheus` 제공 및 동작 검증
- HTTP method·정규화된 API 경로·상태 코드·응답 시간 제공
- 요청별 trace ID 생성 및 오류 로그 연결
- 느린 요청과 5xx를 식별할 수 있는 로그 제공
- 외부 AI 요청 결과와 소요 시간 기록
- 토큰, 쿠키, 세션 ID, 요청 본문 등 민감정보 로그 제외
- 핵심 쿼리의 실행 계획과 요청당 쿼리 수 점검
- 성능 변경 전후 동일 조건의 측정 결과 기록

### 7.2 클라우드 담당

- Prometheus의 `/actuator/prometheus` 수집 설정
- Grafana datasource와 기본 대시보드 구성
- 애플리케이션 stdout 로그 수집·저장·검색 환경 구성
- CPU·메모리·컨테이너·DB 인프라 지표 구성
- health endpoint를 로드밸런서 또는 배포 환경의 health check에 연결
- 지표와 로그 보존 기간 및 접근 권한 관리

### 7.3 공동 합의 항목

- 서비스 및 환경 이름
- Prometheus 수집 경로와 주기
- 운영 Actuator endpoint 접근 방식
- 느린 요청의 초기 기준
- 스테이징 부하 테스트 시나리오와 목표 요청량
- metric·log에서 사용하는 API 경로 및 오류 분류 기준

## 8. 현재 기반과 1차 구현 범위

현재 백엔드는 Spring Boot Actuator, Prometheus registry, health·prometheus endpoint 및 요청 trace ID를 이미 사용하고 있다.

1차 범위에서는 다음만 추가 또는 검증한다.

1. Actuator 기본 HTTP·JVM·HikariCP 지표가 정상 노출되는지 확인한다.
2. API가 식별자별 원본 URI가 아닌 정규화된 경로로 집계되는지 확인한다.
3. 느린 요청과 5xx에서 method, route, status, duration, trace ID를 확인할 수 있게 한다.
4. AI 서버 호출의 operation, result, status, duration, trace ID를 확인할 수 있게 한다.
5. 지도 조회와 가이드북 조회의 핵심 쿼리를 로컬에서 분석한다.
6. 스테이징에서 핵심 사용자 흐름과 서버 자원을 함께 측정한다.

초기 단계에서 다음은 수행하지 않는다.

- 전 서비스 분산 추적 구축
- OpenTelemetry Collector 및 Tempo·Jaeger 구성
- 모든 Service·Repository 메서드의 개별 시간 측정
- 모든 SQL의 상시 로그 수집
- 복잡한 커스텀 비즈니스 메트릭
- 캐시 또는 메시지 큐의 선제 도입
- 운영 환경의 의도적인 부하·장애 테스트

## 9. 1차 Grafana 대시보드 요구사항

1차 대시보드는 다음 패널로 제한한다.

- 전체 요청 수와 RPS
- API별 평균·p95 응답 시간
- API별 4xx·5xx
- 프로세스 CPU 사용률
- JVM heap 사용량과 GC
- HikariCP active·pending connection

문제 원인을 확인하기에 부족한 경우에만 HTTP 스레드, 외부 AI, DB 또는 캐시 관련 패널을 추가한다.

## 10. 진행 순서

### 1단계: 로컬 기준선

- 지도 조회 쿼리의 실행 계획과 공간 인덱스 확인
- 가이드북 상세·뷰어 API의 쿼리 수 확인
- Actuator 지표 및 요청 로그 생성 검증
- 핵심 API의 변경 전 기준값 기록

### 2단계: 스테이징 검증

- 지도 연속 조회 시나리오 수행
- 가이드북 동시 생성 및 상태 polling 시나리오 수행
- API 지연·오류와 CPU·메모리·DB pool을 함께 확인
- AI 호출 시간과 전체 생성 시간 분리 확인

### 3단계: 운영 관찰

- 실제 트래픽과 p95·에러율 관찰
- 배포 전후 지표 비교

## 11. 1차 완료 기준

다음 질문에 답할 수 있으면 1차 성능 측정 구성을 완료한 것으로 본다.

- 현재 트래픽이 가장 많은 API는 무엇인가?
- 평균 및 p95 응답 시간이 가장 긴 API는 무엇인가?
- 4xx와 5xx가 어느 API에서 발생하는가?
- 지도 조회 지연에서 DB 쿼리가 차지하는 비중은 어느 정도인가?
- 가이드북 생성 지연이 접수 처리인지 AI 생성 처리인지 구분할 수 있는가?
- 가이드북 생성 작업 한 건당 polling 요청이 몇 번 발생하는가?
- 지연이 발생한 시점에 CPU, JVM 메모리 또는 DB connection 대기가 있었는가?
- 성능 개선 전후를 같은 조건으로 비교할 수 있는가?
