# 서비스 세션 저장소 이전 — #285

## 목적과 기준

서비스 세션 인증의 MySQL 의존을 단계적으로 Redis로 이전한다. 로그인 과정의 임시 OAuth HTTP 세션과는 별개다.
기준은 요구사항정의서의 BR-MEM-02/03, FR-MEM-02와 BR-NOT-08/10/11/12/16이다.
이 문서는 현재 완료한 단계와 후속 작업을 구분한다. 최종 목표를 이미 구현한 것으로 해석하지 않는다.

## 단계 1: 인증 저장소 경계 분리 — 현재 구현

- `ServiceSessionService`는 원문 쿠키를 해시하고 설정된 유휴 시간을 전달한다.
- `ServiceSessionAuthenticationStore`는 인증 검증과 성공 시 활동 갱신을 하나의 작업으로 제공한다.
  인터페이스에는 JPA 엔티티·EntityManager·트랜잭션 구현을 노출하지 않는다.
- 기본 Spring 빈은 `MySqlServiceSessionAuthenticationStore`다. 단계 2의 Redis 어댑터는 자동 등록하지 않는다.
- MySQL 구현은 기존 `SELECT ... FOR UPDATE`를 호출한 뒤 잠금 획득 후의 시각으로
  세션 폐기·절대 만료·유휴 만료·회원 탈퇴를 검사한다. 성공 시에만 마지막 사용 시각을 갱신한다.
- 트랜잭션 경계는 인증 저장소 구현체에 둔다. 호출자에게 트랜잭션이 없어도
  조회 잠금부터 JPA dirty checking UPDATE까지 한 트랜잭션 안에서 끝나야 한다.
- 미존재·만료·폐기·탈퇴는 빈 결과로 반환하지만, 저장소 장애를 세션 부재로 숨기지 않는다.
  호출 계층이 MySQL 재조회로 우회 인증하는 동작도 추가하지 않는다.
- 인증 응답의 숫자 세션 ID, 회원 상태, 쿠키 및 CSRF 정책을 그대로 유지한다.

### 유지되는 동작과 영향 검토

- 절대 8시간·유휴 30분·회원당 유효 세션 1개, 새 로그인 시 이전 세션 폐기: 변경 없음.
- 로그인 시 발급, 로그아웃의 세션/Push 구독 폐기, 탈퇴 처리: 기존 MySQL 구현을 유지한다.
- Push 구독 FK, SSE 식별자·연결 종료·인스턴스 간 이벤트: 변경 없음.
- API 경계·상태 전이·화면/오류 계약·기존 ERD 및 마이그레이션: 변경 없음.
- 배포·데이터 정리: 수행하지 않는다. 기존 작업 디렉터리의 부하 테스트 변경도 이 워크트리에 복사하지 않는다.
- 화면 동작을 변경하지 않는 내부 리팩터링으로 Figma 원본을 재검증·수정하지 않았다.
  후속 단계에서 재로그인 등 사용자 영향이 확정되면 관련 정상·실패 화면도 확인해야 한다.

### 검증 범위

- 저장소로 원문 대신 해시가 전달되고 인증 서비스가 JPA Repository를 직접 호출하지 않는지 검증.
- 저장소의 빈 결과와 장애를 구분해 그대로 전달하는지 검증.
- 정상 인증의 주체·활동 갱신, 만료 경계·폐기·탈퇴 거절, 기존 null 사용 시각의 fallback 검증.
- 활동 갱신이 절대 만료 시각을 연장하지 않고, 외부 트랜잭션 없이도 변경이 커밋되는지 검증.
- 기존 로그아웃 소유권과 관련 인증·로그인·회원 API 회귀 테스트 수행.

## 단계 2: Redis 인증 어댑터 — 구현, 기본 경로 미전환

`RedisServiceSessionAuthenticationStore`와 단일 키 Lua 스크립트를 추가한다.
발급·폐기 경로가 아직 MySQL이므로 어댑터를 Spring 빈으로 등록하거나 전환 플래그를 제공하지 않는다.
테스트가 데이터를 직접 생성하며 운영 데이터 이관은 수행하지 않는다.

### 데이터 계약

키는 `<namespace>:session:<SHA-256 소문자 hex>`이고 값은 Redis Hash다.

| 필드 | 값 |
| --- | --- |
| schemaVersion | `1` |
| sessionId, memberId | 양수 Java Long 범위의 10진 문자열 |
| memberStatus | `ACTIVE` 또는 `ONBOARDING` |
| createdAtEpochMillis, expiresAtEpochMillis | 생성·절대 만료 시각, 정수 epoch milliseconds |
| lastUsedAtEpochMillis | 마지막 사용 시각, 없으면 생성 시각 사용 |
| revoked, memberDeleted | `0` 또는 `1` |

숫자 세션 ID는 현재 인증 응답과 동일하게 유지한다. 해시는 Redis 조회 키이며 회원 ID를 대신하지 않는다.
시각은 Lua가 정확히 표현하는 0~2^53-1 범위를 사용한다. ID는 숫자로 변환하지 않아 Long 정밀도를 보존한다.

### 원자성·만료·장애

- Lua 내부 Redis `TIME`으로 검증 시각을 정한다. 애플리케이션 대기 전 시각을 사용하지 않는다.
- 모든 필드를 검증한 후에만 마지막 사용 시각과 TTL을 변경한다. 손상 데이터는 오류로 전달한다.
- 정상 인증 TTL은 `min(유휴 시간, 절대 만료까지 남은 시간)`이다. 절대 만료 필드는 변경하지 않는다.
- 미존재·폐기·탈퇴·만료는 빈 결과이며 거절 시 활동 시각을 갱신하지 않는다.
- Redis 장애는 호출자에게 전달한다. MySQL fallback은 없다.
- 조회·검증·갱신이 하나의 스크립트라 삭제와 경합해도 삭제된 키를 재생성하지 않는다.
- 자연 만료로 Push 구독을 폐기하지 않는다. 명시적 로그아웃/탈퇴 정리는 후속 단계다.

실제 격리된 Redis 컨테이너에서 정상 상태, Long ID 정밀도, TTL 상한, 사용 시각 fallback,
만료·폐기·탈퇴 거절, 손상 데이터 무변경, 두 클라이언트 동시 인증과 삭제 경합을 검증한다.
Docker가 없으면 이 테스트는 생략하지 않고 실패한다.

## 후속 단계 — 미구현

1. Redis 발급·폐기 경계와 식별자 발급, 회원 상태 변경 동기화 방식을 확정한다.
2. 로그인·온보딩·탈퇴 및 Push/SSE 연결을 전환하고 부분 실패·동시 요청을 검증한다.
3. 운영 전환·구버전 혼재·롤백 방식을 확정한 뒤 `auth_sessions` 제거 마이그레이션을 적용한다.
4. 기존 MySQL baseline과 같은 조건으로 실제 Redis 구현의 인증 지연·DB 부하를 비교한다.

숫자 세션 ID 유지 여부, Redis 식별자 발급·키 배치, 장애 응답과 복구 방식,
운영 구독 폐기·재등록 시점은 후속 구현 전 결정 사항이다. 해시 식별자 변경을 필수로 전제하지 않는다.
Redis로 이전해도 세션 자연 만료 시 Push 유지, 명시적 로그아웃 시 해당 구독 폐기 정책은 구분해서 보존해야 한다.
