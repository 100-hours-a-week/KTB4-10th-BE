# 개발 전 확정 필수 내용

> 2026-09-15 · Issue #9 · V1 결정 반영
> 사용자 결정과 이번에 위임받은 보수적 구현 기준을 기록한다. “문서 반영”은 구현·연동 검증 완료를 뜻하지 않는다.
> 기준 요구사항은 [요구사항정의서](./요구사항정의서.md), 요청·응답은 [V3 API 명세서](./V3%20API%20명세서.md)를 따른다.

## 1. 개발 착수 판단

**회원·취향·무료 생성권·공통 API 개발은 착수 가능하다. 전체 V1 실연동·배포 준비가 끝난 것은 아니다.**

- 실행환경은 팀원의 초기 설정 PR을 기준으로 맞춘다(V1-02).
- 카카오 실연동 전 앱 설정·CSRF 전달·배포 주소 검증을 끝낸다(V1-04).
- 생성 워커의 외부 호출 구현 전 AI 계약을 맞춘다(V1-09). 내부 상태·잠금·원장 로직은 fake adapter로 테스트할 수 있다.
- 관광 연동·진행 표시·HTML/PDF는 담당자 데이터와 샘플 확보 후 확정한다(V1-12/13/15).
- V1-11의 멱등·잠금·트랜잭션 경계는 **구현 전에 적용**한다. 구현 후에는 테스트와 성능 수치로 검증한다.
- Redis·브로커·Kubernetes는 V1 필수가 아니다. 백업·비밀 관리·실패 감시는 배포 전 필수다.

## 3. V1 결정 상세

### V1-01. API 제공 범위

기존 명세 2장의 V1 표가 구현 목록이다. 출시 V1과 URL prefix /api/v1은 별개다. V1 미제공 엔드포인트는 등록하지 않는다. 공통 인증 필터가 먼저 응답할 수 있지만 유효한 ACTIVE 세션에서 미등록 경로는 404다. V2 입력을 화면에서만 숨겨서는 안 되며 BE도 거절한다.

### V1-02. 실행환경

다른 팀원의 설정 결과를 보고 JDK·Spring Boot·Gradle·MySQL 버전과 collation, Flyway 최초 migration, CSRF 연동을 맞춘다. ERDCloud SQL은 import용이며 운영 migration과 동일하다고 간주하지 않는다. 이번 문서 PR은 빌드 버전을 임의 변경하지 않는다.

### V1-03. 서비스 세션 기준

프로젝트가 채택하는 보수적인 초기값이며 “실무 평균”이나 표준 의무값이 아니다.

| 항목 | 기준 |
|---|---|
| ID | SecureRandom 32바이트 → base64url, padding 없음. DB는 SHA-256 해시 |
| 절대 만료 | created_at + 8시간 = expires_at, 연장하지 않음 |
| 유휴 만료 | 마지막 성공 인증부터 30분. last_used_at은 발급 시 현재 시각, 성공 인증마다 DB 시각으로 갱신 |
| 판정 | now >= expires_at 또는 now >= last_used_at + 30분이면 401. 기존 NULL은 created_at 기준 |
| 쿠키 | KGB_SESSION, Max-Age=28800, HttpOnly·Secure·SameSite=Lax·Path=/·host-only. 유휴 만료는 쿠키보다 서버 판정 우선 |
| 동시 로그인 | 회원당 유효 세션 최대 1개. 로그인 성공 TX에서 회원 행을 잠그고 기존 유효 세션을 모두 폐기한 뒤 새 세션을 발급. 마지막으로 완료된 로그인이 유일한 유효 세션이 됨 |
| 종료 | 로그아웃은 현재 세션, 탈퇴는 모두 폐기. 매일 정리 배치로 만료/폐기 후 30일 경과 행 제거 |
| 상태 변경 | TX에서 회원 삭제와 요청 세션의 폐기·만료를 재확인. 만료된 요청을 살리는 last_used_at 갱신 금지 |

유휴 갱신의 매 요청 쓰기 비용을 수용한다. 추후 1분 단위 갱신 등을 도입하면 실제 만료 오차를 먼저 정의한다. 여러 요청의 last_used_at이 역행하지 않게 DB 현재 시각과 조건부 UPDATE를 사용한다. 백그라운드 폴링도 인증 요청이므로 유휴 시간을 갱신하지만 절대 8시간은 늘리지 못한다.

| 접근자 | 허용 |
|---|---|
| 비로그인 | OAuth 시작·콜백, 정책 목록·상세. health는 내부 네트워크 |
| ONBOARDING | MEM-03/04/06/07/08/09/10/11 및 공개 API |
| ACTIVE | V1 제공 API 중 본인 소유·보관 관계를 만족하는 기능 |
| 탈퇴·만료·폐기 | 보호 API 401 |
| ONBOARDING의 관광·알림·가이드북·지갑 | 403 RESOURCE_FORBIDDEN |

근거: BR-MEM-02/03/09, FR-MEM-02. [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)는 서버 만료와 세션 관리를 안내한다. 구체적 8시간/30분/1개는 서비스의 선택이다. 단일 세션은 구현과 사용자 상태를 단순화하지만 새 로그인 시 기존 기기에서 즉시 로그아웃되는 단점을 감수한다.

### V1-04. 카카오 키 발급 시 확인

기존 BE 시작·콜백, state 10분/5개/일회 소비, PKCE S256을 유지한다. 키 발급까지 기다려도 되는 것은 콘솔 설정값이지 검증 책임 자체가 아니다.

- 개발/운영 REST API 키와 client secret 사용 설정, 서버 비밀 저장 위치·교체 담당. application.yml에는 환경 변수 placeholder만 두고 실제 값은 로컬 비추적 환경 변수와 클라우드 런타임 Secret으로 주입
- 카카오 로그인 활성화, prefix를 포함한 BE redirect URI. 로컬 `http://localhost:8080/api/v1/auth/oauth/callback/kakao`, 배포 `https://kguidebook.site/api/v1/auth/oauth/callback/kakao`를 REST API 키에 정확히 등록
- 외부 provider 경로값은 소문자 `kakao`, 내부 DB/Java 식별자는 `KAKAO`. V1은 정식 FE 완료 화면 전까지 callback 성공 후 같은 백엔드의 `GET /api/v1/members/me`로 이동해 세션을 확인하고, FE 준비 후 설정 기반 완료·오류 URL로 교체
- profile_nickname은 서비스 표시명에 사용한다. profile_image와 account_email은 nullable이므로 미제공을 가입 실패로 처리하거나 카카오계정 정보 입력을 강제하지 않는다. 필요한 최소 동의 단계와 실제 응답을 확인
- 카카오 OAuth 사용자 정보 id로 식별, 별도 OIDC 활성화는 현재 범위 아님
- challenge/verifier 전송과 틀린 verifier 거절 실측. 지원/설정 문제가 있으면 배포 전 해결하며 PKCE를 조용히 제거하지 않음
- code·state·verifier·토큰·키·이메일 원문 로그 금지, 취소·만료·중복 콜백 테스트
- CSRF 토큰 전달 경로/헤더·재발급 및 필터 실패 우선순위, CORS credentials, 쿠키와 HTTPS
- 다중 인스턴스 전 로그인 전 HttpSession 공유·원자 소비 검증

[카카오 REST API](https://developers.kakao.com/docs/ko/kakaologin/rest-api)를 앱 설정 시 다시 대조한다. 현재 CSRF 전달 경로가 미정이므로 브라우저 변경 API 실연동 완료로 표시하지 않는다.

### V1-05. 프로필·이메일

email은 VARCHAR(254) nullable, UNIQUE 없음. 공급자가 제공한 유효한 이메일만 저장하며 누락·사용 불가·길이 초과는 null이다. 식별·자동 병합·연락처 인증 근거로 쓰지 않는다. /members/me는 email:null을 반환하고 FE는 “이메일 정보 없음”을 표시한다. 공급자 동의항목이 있어도 실제 이메일을 항상 얻는다고 가정하지 않는다.

닉네임 누락/공백은 “사용자”, 초과는 표시 이름의 첫 50 Unicode code point로 정규화한다. 이미지 URL은 안전한 HTTPS 및 2048자 이내만 저장하고 그 외 null로 처리한다. V1은 가입 시 저장, 로그인마다 프로필 갱신은 V2 범위다. unread_count 조회 실패는 기존 전체 500을 유지하며 거짓 0을 반환하지 않는다.

### V1-06. 취향 Enum

[취향 Enum 코드표](./V1%20취향%20Enum%20코드표.md)의 code/label/parent_code/sort_order를 사용한다. THEME 1~3개, 선택 THEME별 DETAIL 1~3개, TRAVEL_STYLE 0~8개의 서로 다른 코드다. 스타일 선택을 강제하지 않는다.

PUT은 DB member_preferences의 현재 선택 전체를 같은 TX에서 교체한다. 생성 접수도 같은 회원 잠금 아래 현재 취향 전체를 읽어 request_payload에 복사한다. 이후 취향 변경은 이미 접수한 작업·완성된 가이드북을 바꾸지 않는다. 코드/부모/중복/선택 개수 위반은 422 PREFERENCE_INVALID, JSON 형식 오류는 400이다.

### V1-07. 무료 생성권

- 회원 가입 TX에서 지갑을 만들고 3회 지급한다. 취향 미완료도 가입 회원이지만 생성은 ACTIVE만 허용한다.
- **가입 시 3회는 가입월 무료분**이다. 같은 월에 가입분과 정기분을 합쳐 6회 주지 않는다.
- Asia/Seoul 달력월 기준 다음 달 1일부터 매월 3회 추가한다. 미사용분은 소멸·초기화 없이 누적 이월한다. V1 제품상 보유 상한은 두지 않되 INT overflow는 저장 전 차단·운영 경보한다.
- 정기 대상은 해당 월 시작 전에 가입했고 deleted_at IS NULL인 회원(ONBOARDING 포함). 로그인 여부로 지급을 제한하지 않는다.
- 1일 00:00 지급을 시작하고 매일 재대사한다. 장애로 빠진 월은 가입월부터 현재 월까지 누락 키를 확인해 월별로 보충한다. 삭제된 회원에는 보충하지 않는다.
- 원장 UNIQUE 키 monthly-free:{memberId}:{yyyyMM}를 가입월에도 공통 사용한다. 지갑 잠금·중복 키 확인·+3·FREE_GRANT 원장을 같은 TX로 묶는다.
- 차감은 월별 묶음 없이 총 credit_balance에서 1회 뺀다. **월 구분은 차감이 아닌 지급 중복 방지와 감사에 필요**하다.
- 탈퇴 TX에서 작업 취소 확정, 남은 잔액을 REVOKE 원장(withdraw:{memberId})과 함께 0으로 만든다. 잔액 0이면 0원장 없이 끝낸다. 재가입은 새 memberId로 가입월 3회 지급한다.
- 반복 탈퇴·재가입으로 무료분을 얻는 남용 가능성을 현재 정책의 제약으로 수용한다. 과거 OAuth ID 보관·재가입 차단 정책을 몰래 추가하지 않는다.

근거: FR-PAY-01/02, BR-PAY-01~04/09. 가입월 1회, 월 경계, 배치 재실행, 탈퇴 경합을 테스트한다. V2 유료분의 차감 순서·보존은 별도 정책이다.

### V1-08. 생성 입력과 저장

| companion | 의미 | people_count (본인 포함) |
|---|---|---|
| ALONE | 혼자 | 1 |
| FRIEND | 친구 | 2~4 |
| COUPLE | 연인 | 2 |
| FAMILY | 가족 | 2~6 |
| GROUP | 단체·혼합 구성 | 2~10 |

동행은 한 값만 받는다. “친구 1 + 연인 1” 같은 구성 배열은 받지 않는다. 혼합 구성은 GROUP과 총인원으로 표현한다.

- 서울 기준 today <= start_date <= end_date <= today.plusYears(1), 양끝 포함 1~7일. 윤년은 Java LocalDate.plusYears 규칙을 따른다. “예약 가능”은 생성용 여행일 선택이며 실제 예약 기능이 아니다.
- 사용자는 17개 광역 지역 중 region_code 하나만 전송한다. 세부 시·군·구는 입력받지 않는다.
- 제목은 AI가 선택한 대표 지역명(행정 접미사 제외)이며 1~15자다. 제목 선택·인접 지역 허용 범위·출력 검증은 AI 합의 전 임의 문자열 자르기나 지역 강제 이동으로 해결하지 않는다.
- preference_tags는 카드·상세·공유 응답에서 제외하고 별도 저장 컬럼을 만들지 않는다. 현재 취향으로 과거 카드 태그를 대신 표시하지 않는다.
- 기본 취향은 DB, 해당 작업의 입력 취향은 request_payload 스냅샷이다. 서로 생명주기가 다르다.
- V3 자연어 재생성에서만 세부 지역 요구를 반영하는 방향이며 기본 취향을 자동 수정하지 않는다.
- AI 결과 HTML·장소 snapshot의 타입·필수값·크기와 외부 content_id→내부 FK 매핑은 V1-09/13/15에서 확정한다.

### V1-10. DB 워커 초기 기준

- 최초 V1 배포는 단일 BE 인스턴스 기준, 워커 동시 실행 2개, 2초마다 DB 후보 조회. 메모리 큐에만 작업을 두지 않는다. 수치는 부하 검증 전 초기값이다.
- 선점 대상은 `PENDING`이면서 `next_attempt_at`이 비었거나 DB 현재 시각 이하인 작업, 또는 `PROCESSING`이면서 `lease_expires_at`이 DB 현재 시각 이하인 작업이다. 짧은 TX에서 `SELECT ... FOR UPDATE SKIP LOCKED`로 빈 실행 슬롯 수만큼 선점하며, 선점 TX를 끝낸 뒤 AI를 호출한다.
- `lease_token`(UUID), `lease_version`, `lease_expires_at`을 저장한다. 선점·재선점마다 새 토큰을 발급하고 version을 1 증가시킨다. lease는 60초, heartbeat는 AI 호출과 독립된 실행 흐름에서 15초마다 `PROCESSING`·token·version 일치 조건으로 연장한다. 갱신 실패 시 결과 저장 권한을 잃은 것으로 보고 중단한다.
- started_at은 최초 실행 시각으로 유지한다. attempt_started_at은 개별 시도 시작, attempt_count는 추가 재시도 0~3, next_attempt_at은 다음 실행 가능 시각이다.
- 개별 시도 300초, 재시도 지연 5/10/20초, 전체 처리 제한 최초 started_at부터 1,300초. 대기열 시간은 제외하므로 대기시간 무제한을 숨기지 않고 오래된 PENDING을 감시한다.
- lease 만료 자체는 재시도 횟수로 계산하지 않는다. 재선점한 워커는 `ai_job_id`가 있으면 기존 AI 작업 상태를 먼저 조회한다. 이전 워커의 heartbeat·결과는 상태·token·version·attempt_count·취소 플래그 비교로 반영하지 않는다.
- 재시작 시 AI job_id가 있으면 기존 작업 상태를 먼저 조회한다. 접수 여부 불명확하고 AI 멱등/조회 보장이 없으면 자동 재접수하지 않고 최종 실패·미차감 처리한다. 네트워크 분리 시 AI 계산 자체가 중복되지 않는다는 보장은 외부 계약 없이는 불가능하다.
- HTTP 클라이언트의 숨은 추가 재시도는 끈다. 4회 제한을 BE 워커 한 곳에서 집계한다. 재시도 가능한 오류는 AI 합의 목록만 사용한다.
- 결과 저장 TX가 실패한 경우 같은 결과로 DB 처리를 재시도하며 AI 재생성으로 보상하지 않는다. 저장 완료 전에는 COMPLETED를 반환하지 않는다.
- 재시도 가능한 것으로 확정된 실패만 `attempt_count`를 증가시키고 lease를 비운 뒤 `PENDING`으로 되돌린다. 새 count가 1·2·3이면 각각 DB 현재 시각 기준 5·10·20초 후를 `next_attempt_at`으로 둔다. 재시도 불가능하거나 최대 횟수를 소진하면 `FAILED`, 취소가 확정되면 `CANCELED`로 종료하며 두 경우 모두 생성권을 차감하지 않는다.
- 성공 저장 TX는 회원 상태·작업 상태·token·version·attempt_count·취소 여부를 검증하고, 결과·보관 관계·생성권 차감·원장·`COMPLETED` 전환을 한 번에 커밋한다.

generation_jobs 추가 컬럼은 테이블·ERDCloud SQL에 반영한다. 실제 Flyway 적용과 다중 워커 테스트는 구현 과제다.

### V1-11. 구현 전에 맞추는 정합성

**코드 작성 후로 미루지 않는다.** 서로 다른 도메인 메서드가 같은 DB 상태를 바꾸므로 책임·순서를 먼저 맞춰야 한다.

1. 공통 잠금 순서는 members → credit_wallets → generation_jobs → guidebooks → 관계·일정·원장이다. 없는 대상은 생략하고 같은 테이블 여러 행은 PK 오름차순이다. 인증 상태 재검증은 회원 잠금 후 수행한다.
2. 접수 전에 인증·요청 형식을 검사한다. 같은 키 작업을 먼저 조회해 회원·요청 본문이 같으면 현재 작업을 반환한다. **현재 취향·잔액·과거일 검증은 새 작업에만 적용**한다.
3. 본문 비교는 필드 허용목록·타입 검사 후 키 순서를 고정한 JSON으로 한다. 요청의 모든 허용 입력을 비교하고, 현재 DB 취향은 비교 대상이 아니다. 생성 요청 멱등키는 표시 가능한 ASCII 1~100자, 대소문자를 구분하며 `(member_id, idempotency_key)` UNIQUE로 원본 작업 보존기간 동안 유지한다. 같은 회원·같은 키·다른 본문은 409, 다른 회원의 같은 키는 별도 요청이다.
4. 신규 작업은 회원 잠금 아래 현재 취향을 snapshot으로 저장한다. 같은 키 INSERT 경합은 실패 TX 롤백 후 기존 작업을 읽어 비교한다.
5. 가입 오케스트레이터(회원)는 회원·지갑·가입월 지급·세션을 같은 TX로 처리한다. 생성 완료 오케스트레이터(가이드북)는 결과·일정·보관 관계·COMPLETED·잔액 -1·CONSUME를 같은 TX로 처리한다. 생성권 서비스는 REQUIRED로 참여하며 별도 커밋하지 않는다.
6. 탈퇴 오케스트레이터(회원)는 취소 요청 시각·PENDING/PROCESSING→CANCELED·lease 무효화·세션 폐기·소프트 삭제·생성권 회수를 같은 TX로 처리한다. 외부 AI 취소는 커밋 후 best effort다.
7. 먼저 잠근 TX가 성공하면 다음 TX는 그 결과를 보고 처리한다. 생성 완료 후 탈퇴라면 생성 차감 후 남은 잔액 회수, 탈퇴 후 완료라면 결과 저장·차감 금지다.
8. DB 데드락/잠금 timeout은 롤백 후 새 TX로 최대 2회 재시도(50/100ms). 외부 호출을 반복하지 않는다. 소진 시 기존 503 SERVICE_UNAVAILABLE, 원장/작업 유일 제약 충돌은 기존 결과 조회로 분기한다.

검증: 잔액 1개의 동시 생성, 같은 키·다른 본문, 취향 변경, 중복 완료, lease 만료, 탈퇴 경합. AI 계산 “정확히 한 번”과 DB 결과 “한 번 반영”은 구분한다.

### V1-17. 오류·공통 커서

기존 오류 wrapper와 세부 업무 코드를 유지한다. 잘못된 JSON·타입·미지원 필드·커서·page는 400 COMMON_VALIDATION_ERROR, 취향 업무 검증은 422 PREFERENCE_INVALID, 여행 날짜/기간은 422 GUIDEBOOK_INVALID_PERIOD로 묶는다. 인증 401·CSRF 403·접근 제한 403·자원 미존재 404·충돌 409·잔액 부족 422·내부 500은 복구 방식이 달라 합치지 않는다. CSRF 전달과 최종 실패 우선순위는 V1-04 검증 관문이다.

가이드북 상세/일정/뷰어/PDF의 활성 보관 관계 부재는 404 RESOURCE_NOT_FOUND로 통일한다. 생성 작업 조회에서 타인 작업은 기존 403을 유지한다. 알림·관심 해제의 본인 범위 대상 없음은 기존 204다.

| 목록 | 정렬/커서 키 |
|---|---|
| 가이드북 | member_guidebooks.created_at DESC,id DESC |
| 관심 장소 | favorite_contents.created_at DESC,content_id DESC (별도 id 없음) |
| 생성권 원장 | credit_transactions.created_at DESC,id DESC |

- size 기본20·1~100, size+1 조회, 다음 커서는 실제 반환 마지막 행 기준. 마지막이면 next_cursor=null/has_more=false.
- 커서는 base64url(JSON payload).base64url(HMAC-SHA256(payload)) 형식의 불투명 문자열이며 버전·endpoint·memberId·정렬·허용 filter·마지막 UTC DATETIME(6)/ID·최초 조회 상한 키·발급 시각을 포함한다.
- 24시간 유효, 최대 2048자. 서명·버전·회원·endpoint·filter 불일치·만료는 400. 서명 키는 서버 비밀 설정에 보관한다. base64는 암호화가 아니다.
- DESC 키 비교는 created_at < lastTime OR (created_at=lastTime AND tieId<lastId). 첫 요청 상한을 다음 요청에도 적용한다. 타임스탬프의 마이크로초를 자르지 않는다.
- 대상 행이 삭제돼도 커서 행을 다시 찾을 필요 없이 키로 이어간다. 권한과 활성 조건은 매 요청 세션 기준으로 검사한다.
- 이 규칙은 새 삽입/삭제가 있는 목록의 완전한 snapshot을 보장하지 않는다. 특히 관심 해제→재등록은 새 관계다. 새로고침은 cursor 없이 시작한다.

### V1-18. 운영

Redis·브로커·Kubernetes·벡터 DB는 V1 필수 아님. 필요가 생기면 재검토한다. 반면 HTTPS·비밀 관리·DB 백업·복원 시험·오류/작업/원장 감시·health 노출 제한은 배포 전 필수이며 이번 보류에 포함하지 않는다.

## 6. V3 개발 전에 확정할 내용

### V3-01. 재생성·공유 불변성의 서버 보장

현재 BR-GDE-17은 화면 이탈을 서버에 저장하지 않고 FE 흐름으로 제한한다. 그런데 GDE-09는 활성 보관 관계를 허용 조건으로 삼고, 공유/가져온 회원도 보관 관계가 생긴다.

- 생성자만 재생성 가능한지와 IMPORTED 관계의 요청을 어떻게 거절할지 정한다.
- 공유 링크 발급·가져오기와 재생성 접수가 동시에 발생할 때 검증/잠금 순서를 정한다.
- ‘화면에서 버튼을 숨김’과 ‘공유 후 원본 변경 금지’는 다른 문제다. 서버에서 공유 가능/확정 상태를 추가할지, 기존 데이터로 제한할지, 현재 MVP 한계를 수용할지 결정한다.
- 재생성 성공 시 HTML·일정·version을 한 번에 바꾸며 실패 시 보존한다. preference_tags는 응답에서 제외한다.

**완료 기준:** 직접 API 호출·동시 공유·가져온 회원 요청에서도 승인된 정책대로 동작한다. 새로운 상태를 선택하면 BR-GDE-17/DEC-12·API·스키마를 함께 바꾼다.

담당: 가이드북 BE·FE·기획. 근거: BR-GDE-09/13/17, API-GDE-09~12, 가이드북 V3.

### V3-02. 공유 토큰·복구·조회 권한

- 토큰 길이·생성/해시 방식·URL·재발급 요청 제한을 정한다.
- 24시간 만료는 확정인데 share_links.expires_at은 nullable/무기한 설명이 남아 있다. V3 쓰기에서 항상 만료값을 넣고 DB 제약도 좁힐지 결정한다.
- 소프트 삭제 관계 복구 시 created_at을 유지할지, 목록 상단으로 올릴지 정한다.
- 로그인 전 링크 진입의 안전한 복귀, 발급자 탈퇴/삭제 시 링크 차단, 다른 보관자의 접근 유지를 테스트한다.

**완료 기준:** 공유/만료/재발급/중복 가져오기/복구/탈퇴 계약이 일치한다. 가이드북을 물리 복사하는 모델로 되돌리는 안건이 아니다.

담당: 가이드북·회원 BE·FE. 근거: DEC-06/07/11, 테이블 4.3/4.6, API-GDE-10~12.

### V3-03. 평가 자격·예외·최종 제출

- CREATED 회원만 평가하는지 IMPORTED 보관자도 가능한지 확정한다. 회원+가이드북 UNIQUE만으로 생성자 전용 정책이 되지는 않는다.
- 유효 관광 콘텐츠가 0개인 일정, 비활성·삭제 콘텐츠, 전부 건너뛰기의 제출 허용 여부를 정한다.
- 기존 점수는 서버의 현재 최종값이지 해당 여행의 작성 초안이 아니다. FE 초기 표시·초안 유지 범위를 맞춘다.
- 제출 완료 후 재요청 409는 확정이다. 응답 유실 시 상태 재조회로 성공 여부를 판단하는 FE 복구를 명시한다.
- 평가 시작/제출과 재생성·삭제·탈퇴 경합의 잠금 순서를 정한다.

**완료 기준:** 평가 대상 집합·권한·0/null·미응답·동시 제출 테스트가 있다. 초안 서버 저장이나 제출 후 수정은 현재 범위를 바꾸지 않는 한 추가하지 않는다.

담당: 평가·회원·가이드북 BE·FE. 근거: BR-RNK-01~08/17/18, API-RNK-01~06, 평가 E-Q 항목.

### V3-04. 랭킹 원본과 최초 제출 시각의 의미

‘최초 제출 시각으로 기간 귀속’은 정해졌지만 현재 place_ratings는 회원·장소당 최종값 하나이며 여행 평가와 연결돼 있지 않다.

- 최초가 회원·장소의 첫 평가인지 이번 여행 제출인지 명확히 한다.
- 다른 여행에서 점수를 덮어쓸 때 created_at을 유지하면 과거 기간의 점수가 바뀔 수 있다. 그 의미를 승인한다.
- null로 행을 삭제한 후 다시 평가하면 최초 시각이 새로 생긴다. 허용할지, 별도 보존이 필요한지 결정한다.
- 과거 기간 조회 범위와 점수 변경/탈퇴 후 과거 스냅샷 재계산 범위를 정한다.
- 테이블/요구사항 관계 요약의 Guidebook 1:1 Evaluation과 실제 `(guidebook_id,member_id)` 구조를 평가 자격 정책에 맞춰 정리한다.

**완료 기준:** 같은 장소를 다른 여행에서 평가·삭제·재등록하는 날짜 예제로 어떤 기간에 반영되는지 설명할 수 있다. 과거 결과 완전 재현은 현재 MVP 제외다.

담당: 평가·랭킹 BE·기획. 근거: DEC-03, BR-RNK-17, 테이블 5.1/5.2, 랭킹 R-Q01.

### V3-05. 랭킹 계산·변경 탐지·복구

- C의 모집단 범위와 m 초기값, 반올림·정렬에 사용할 정밀도를 정한다. 동점 순서는 API/DEC의 평가 수 내림차순→content_id 오름차순과 맞춘다. BR-RNK-12의 원평균 언급은 정리가 필요하다.
- `updated_at` 스캔만으로는 물리 삭제한 평가를 발견할 수 없다. 콘텐츠 지역 변경·비활성화·지연 커밋도 반영해야 한다.
- 변경 대상을 영속 기록할지, 정기 전체 대사/재계산을 병행할지 선택한다. Outbox를 무조건 추가하는 것으로 답하지 않는다.
- 전국 평균 C를 사용하면 한 지역 변화가 다른 지역 결과에도 영향을 주는지 검토한다.
- 단일/다중 집계 실행·오래된 결과의 뒤늦은 덮어쓰기 방지·재시작 복구·워터마크 저장을 정한다.

**완료 기준:** 10분 갱신/최대 지연 목표에 대해 삭제·재시작·기간 경계·실패 후 재계산 시험을 한다. ‘10분마다 시작’만으로 ‘10분 안에 결과 반영’을 보장하지 않는다.

담당: 랭킹·평가·관광 BE·인프라. 근거: DEC-03/04, BR-RNK-12~16, NFR-DAT-04, 테이블 5.3/5.4, 랭킹 R-Q02~06.
